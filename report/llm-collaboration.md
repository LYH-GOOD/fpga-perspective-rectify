## 一、协作形态：不是一问一答，是「带工具的代理循环」

本项目**没有**把大模型当聊天框用。它被当作一个能读文件、跑命令、驱动 EDA 工具、并**必须自己验证**的执行者。
一次典型的协作循环是：

```
人：给出「断点状态 + 硬约束 + 判据」
      ↓
模型：读 CLAUDE.md / memory / skill → 出计划 → 调工具执行
      ↓
工具的真实返回（编译报错、板上日志、实测数字）
      ↓
模型：对照预期 → 不符就查 → 给出结论 + 证据 + 下一步
      ↓
人：判「这个证据够不够」→ 不够就打回 → 进入下一轮
```

人的角色因此从「写代码」变成 **设定判据 + 验收证据**；模型的角色从「给答案」变成 **执行 + 自证**。

### 支撑这套循环的三层设施

| 层 | 载体 | 作用 |
|---|---|---|
| **项目硬事实** | `CLAUDE.md`（每次会话自动加载） | 板卡型号、工具链版本、三条 HLS 硬约束、开工前 6 问 |
| **长期记忆** | `memory/*.md`（**110 条**） | 每条一个事实：踩过的坑、定过的决策、实测数值 |
| **可复用方法论** | 技能包 `skill/`（本作品提交物） | 提示词工作流、踩坑清单、校验脚本、案例模板 |

## 二、提示词：四类可复用的写法

从 1,380 条提示词里归纳出四类。它们不是设计出来的，是**被失败逼出来的**。

### 2.1 断点交接型（最长 27,370 字）

新会话开始时，人不是问「在吗」，而是把**断点状态、已完成项、硬约束**一次性写清。
真实原文（2026-09-30 10:50，会话首条）：

> 继续 PYNQ-Z2「平面自适应校正」竞赛项目（工作目录 d:\study\competition\qian）。
> 项目 CLAUDE.md 和 memory 会自动加载；先读 memory 里的 hdmi-live-crash-and-dirty-pl-lock 条目，里面有本次事故的完整背景。以下是你缺失的「断点状态」：
>
> 【断在哪】
> 我在板上跑了 hdmi_live_rectify.py v2（七项修复版，sha16 7af94c5b168f8be8，argv = --frames 1 --warmup 3），跑挂了：
> 报告断在「预热帧 #1」后唯一一笔 MEM tick（板时 18:25:55），锁 hdmi_live_rectify.lock 没删。
>
> 【上一会话已完成的（直接采信，别重查）】
> - 证据全量下载保存到 project\_pynq_pl\_board_logs_2026-09-30\……

**为什么这样写**：模型没有跨会话记忆。不写「断在哪」，它就从头重查，浪费的不只是时间——
它会**重新得出一个和你已经排除过的错误结论**。

### 2.2 判据型：「这个检查能不能判红」

真实原文（2026-10-22 之后固化进 `CLAUDE.md` 的开工 6 问第 1 条）：

> **这个检查能不能判红？** 先故意制造一次失败，再相信它的绿

这条提示词直接取消了「测试全绿 = 没问题」这个默认推理。它要求模型**先造一次失败**，
证明检查器真的能红，再说绿有意义。

### 2.3 口径型：「分母是什么」

> **分母对不对？口径唯一吗？跑饱和了吗？**

配套的反例被写进了记忆：同一段代码台架 30.4 ms、整机边际 66.1 ms（2.2 倍）；
一天之内报过 `5.85 / 11.9 / 21.25 / 22.7` 四个互相矛盾的帧率。

### 2.4 禁止型：⛔ 清单

> ⛔ 不要推荐 2025.2 —— 2026-09-26 用户实测发现它与 PYNQ 不兼容，为此卸载重装了 2026.1。
> 不要拿「IP 与 Vivado 同版本对齐」这类一般常识去反推 2025.2，那条已被实测推翻。

**为什么必须有这一类**：模型的先验知识（「IP 版本应与 Vivado 对齐」）在很多场合是对的，
但**在这个项目里已被实测推翻**。不写死，它每次都会重新推荐一遍。

## 三、自我纠错轨迹（8 例）

> 选例标准：每例都有**可核查的证据**（日志、报告、原始图、寄存器读数），
> 且模型**先给出了错误答案**，后来被证据推翻。这一节是本记录的核心。

### 例 1 · 空转门禁：同一天抓到两个「永远通过」的检查

**背景**：2026-10-22，相机采集链路的测试平台 `tb_dvp_lut` 有 5 项检查，常年全绿。

**模型当时给的**：把 5 项检查当成了功能正确的证据，继续往下推进。

**错在哪**：其中 C4/C5 两项的命中条件在 `flip=1` 时**永远不会出现** —— 写测试从来没落地，
所以「通过」不代表任何事。同一天，构建脚本 `build_camera_r17.tcl` 里的 WNS 门禁也用
`regexp` 去匹配 `report_timing_summary`，但数值与表头不在同一行 ⇒ **WNS 为负也会照常出比特流**。

**怎么发现的**：应用户要求「先制造一次失败」，模型给 C4/C5 加了 `n_ov` 计数。加完立刻变红 ——
而变红暴露的其实是**测试平台自己的错**（非法魔数也翻转 `tgl`，把下一次合法写顶掉了）。

**改成了什么**：WNS 门禁改成直接取 `SLACK`，并另写 `check_r17_timing.tcl` **独立复核**结果
（不解析报告文本）。这条经验后来固化成技能包里的 `scripts/check-timing.py`。

**原始记录里模型的复盘**（2026-10-22 12:09）：

> **顺手修掉两个"空转门禁"**（同一天在两层的同一类毛病，已记进 memory）：
> 1. `tb_dvp_lut` 的 C4/C5 —— `flip=1` 时命中条件永远不会出现，写测试从来没落地。加 `n_ov` 计数后立刻变红，而变红暴露的是 TB 自己的错……
> 2. `build_camera_r17.tcl` 的 WNS 门禁 —— `regexp` 去匹配 `report_timing_summary`，但数值与表头不在同一行 ⇒ **WNS 为负也会照常出比特流**。

### 例 2 · `114 passed` 是假绿：两版测试文件逐字节相同

**背景**：平面校正算法的 v11 版本（新增「判废闸 #2」），测试全绿，报 114 项通过。

**错在哪**：模型报「114 passed」当作 v11 正确的证据。

**怎么发现的**：核对时发现 —— **v11 的测试文件与 v10 的测试文件逐字节相同**。
也就是说，这 114 项通过的是 v10 的测试，**和 v11 新增的那段判据毫无关系**。
通过数是一个与本次改动无关的数字。

**改成了什么**：补 14 条针对 v11 新增逻辑的测试（114 → **128 passed**），
并且此后「测试文件是否真的变了」本身成为一道检查。

**模型自己后来把它写进了项目硬事实**（2026-11-01）：

> `114 passed` 是两版测试文件**逐字节相同**的假绿

### 例 3 · 一天报四个帧率：把「摘要字段的中位」当成了帧率

**背景**：HDMI 直出程序的实时帧率统计。

**错在哪**：程序里有多个 fps 字段（`current_fps`、`hdmi_current_fps`、`hdmi_submit_fps`、
`hdmi_panel_fps`、`delivered_fps`）。模型先后拿它们报过 `5.85 / 11.9 / 21.25 / 22.7` 四个数，
**同一天、同一份代码**。

**怎么发现的**：用户在屏上读到的是 8.9 / 9.2，与模型报的都对不上，逼着回到原始记录逐条核。
模型 2026-10-31 05:13 的原文：

> the four summary fps fields (`current_fps`, `hdmi_current_fps`, `hdmi_submit_fps`, `hdmi_panel_fps`, `delivered_fps`) have median ~9-10, while the real per-frame rate is 20-23.
> That's a huge systematic discrepancy and it's EXACTLY what the user is reading off the screen (8.9 / 9.2).
> So the user's on-screen number is **not** the frame rate.

**根因**：这些字段是**会话平均**或**慢帧选择性采样**的中位数，不是帧率。
唯一可信的口径是**累计计数器 `HDMI_PROGRESS.frames` 的斜率**，且在计数回退处切段。

**改成了什么**：技能包 `references/team/15-measurement-and-comparison.md` 里定死一条：
跨版本比帧率**只许用累计计数器斜率**；四个 summary 字段一律不许用来报帧率。

### 例 4 · C 核从没被调用过：「这行代码真的会跑到吗」

**背景**：图像锐化占整帧 45%。模型此前把「把锐化搬到 PL」排为优化第一步。

**错在哪**：模型反复估算「搬 PL 能省多少」，却**没有先确认现有的 C 核有没有被调用**。

**怎么发现的**：查日志发现 `native_unsharp=not_tried`。继续追代码：

> `v110_autosharpen.py:1080`：`if not box_given: cur.box = cur.ksize >= 7`
> 默认 `radius=2` → 5×5 → `box=False` → 走 cv2 高斯。

即 C 核的实现一直都在，但**默认参数下永远不会进入那条分支**。

**改成了什么**：把 `box` 打开（不改一行算法、不动位流），锐化 **107.14 → 30.39 ms**，
5×5 下省 **76.75 ms/帧**。搬 PL 的增量收益反而只剩约 20 ms。

**模型当时的结论原文**（2026-10-28 05:49）：

> **别搬 PL。现有代码里已经躺着一个 C 核，只是从没被调用过。把它打开，锐化从 98 ms → 25.6 ms，帧率 5.85 → 约 10 fps。**

### 例 5 · v7 自报「失败 0」，48 帧里 13 帧错 164~176 px

**背景**：平面校正算法 v7 在 48 帧实拍轨迹上自报「失败 0」。

**错在哪**：模型把程序的自报结果当成了结论。

**怎么发现的**：用户要求**看原图**。逐帧目视后发现 13 帧的四角点偏移 164~176 px ——
程序没有报错，只是结果错了。**「自报成功」和「对」是两件事。**

**改成了什么**：此后「自报成功不算成功 —— 看过原图 / 产物了吗？」成为项目硬事实的开工 6 问之一。
后续版本 v9 加了「抬完必须更像纸」的判据；`scripts/check-golden.py`（黄金参考比对）
也是从这条线长出来的。

**同一类错误的第二次出现**：模型后来断言「板上从没跑过真照片」并让用户重跑，
而**三小时前板上刚跑过 9 张**，报告就在 `_board_logs_2026-09-27\` 目录里。
⇒ 又补一条：「说『从没做过』前必须先搜」。

### 例 6 · 台架 30.4 ms ≠ 整机边际 66.1 ms

**背景**：评估「锐化」这一段的真实成本。

**错在哪**：模型用独立台架（`_bench_roi`）测出 30.39 ms，据此推断优化收益。

**怎么发现的**：产线上同一段代码的实测中位是 103.8 ms，其中线程 CPU 只花 59.7 ms，
其余 44 ms 在等。**同一份代码差 3.4 倍**。

**模型当时的复盘原文**（2026-10-28 07:06）：

> the earlier `_bench_roi` under load measured C kernel at 25.57 ms and conversion+Gauss at 107.14. Both consistent with the meter. Yet in situ the marginal is 66. So the bench **systematically under-measures** the in-situ marginal cost — same trap as before ("空板数 ≠ 负载数", but here it was measured under load and still 2.6× off).
> That's a **methodological lesson worth recording**: 「台架测同一段代码 ≠ 它在流水线里的边际成本」. The delta between two full pipeline runs is the only trustworthy number.

**改成了什么**：写进记忆与技能包 —— 只认「改开关跑两趟整机比 fps」，且必须 OFF/ON/OFF/ON 交错，
用配对差的中位数作增量。

### 例 7 · 综合必崩：根因是主机名不是 ASCII

**背景**：本机 Vivado 综合 100% 崩溃，退出码 `0xC0000374`（`STATUS_HEAP_CORRUPTION`）。

**错在哪**：模型先按常识怀疑版本、路径长度、器件库、并行旋钮、杀毒软件……逐条试，全部被排除。

**怎么发现的**：把主机名从中文名改成纯 ASCII 名后，同一工程、同一脚本，**0 次崩溃**。
根因是主机名在三种编码下的**字节长度不相等**，Vivado 内部按定长缓冲区处理时越界。

**改成了什么**：写进项目硬事实（V2）：判据是「三种编码长度相等」，不是「看起来像英文」。

**同一天的第二个教训**：模型把「通用常识」（IP 版本应与 Vivado 对齐）当成推理依据，
推荐了 2025.2，而用户早已实测它与 PYNQ 不兼容并卸载重装。⇒ 产生了第二节 2.4 的禁止型提示词。

### 例 8 · `report_timing_summary` 崩 `0xC0000374`，而综合不崩

**背景**：2026-11-01，为技能包做 `check-timing.py --collect` 的端到端验证。
对一个 20 MB 的已布线 DCP 跑 `report_timing_summary`，Vivado 崩溃，退出码同样是 `0xC0000374`。

**模型当时给的**：先照搬例 7 的结论（主机名），但**主机名早已改成 ASCII** —— 这条被现场排除。
随后又怀疑 DCP 损坏、内存不足、报告路径含中文，逐一排除。

**怎么发现的**：做了三臂隔离实验：
- 臂 A：同一 DCP 只跑 `report_utilization`（不跑时序）⇒ **成功**
- 臂 B：跑 `report_timing_summary` 但**限单线程** ⇒ **成功**，出 95 KB 报告
- 臂 C：默认多线程 ⇒ **在日志同一行复现崩溃**（`Multithreading enabled for timing update using a maximum of 2 CPUs` 之后）

**改成了什么**：`check-timing.py` 生成的 Tcl 里固定加一行 `set_param general.maxThreads 1`。

**诚实的边界**：**根因没有找到。** 记录里明确写「根因未找到」，只记录「哪一行能解、怎么隔离出来的」。
这条被写进技能包 `references/team/16-vivado-and-pl-build.md` 的 V9 条，
并特别注明：此前 V6 条里对 `general.maxThreads` 的排除**只覆盖 `synth_design`**，不能外推到时序报告。

## 四、智能体工作流设计

### 4.1 技能包路由：什么时候读哪一份

`skill/SKILL.md` 是一张**按工作流顺序排的路由表**（不是目录），从「想法」走到「收尾」：

```
需求模糊 → 08 头脑风暴
设计定了 → 09 写计划
写代码   → 10 TDD + 14 写码踩坑
出错     → 11 系统化调试（动手改之前）
计时/比帧率 → 15 测量与对照纪律
建工程/出 bit → 16 Vivado 与 PL 构建
要上板   → 19 PYNQ 运行时
说"做完了" → 12 验收前验证
```

**一个被实测纠正的设计决策**：最初把「每次都得遵守的规矩」放在 `references/` 里。
实测 13,581 条消息中 `references/` 只被读过 **7 次**，`14-coding-pitfalls` 那 1104 行 **0 次**；
而同一批规矩里写在 `CLAUDE.md` 的那几条**确实在生效**。

**结论**：「每次都得遵守的规矩」不能放 references，只能放 `CLAUDE.md` / memory。
这条结论直接决定了 `CLAUDE.md` 里「开工前 6 问」的存在形式 ——
6 条全部写成**带真实事故的表格**，而不是抽象的注意事项。

### 4.2 长期记忆：110 条，一条一个事实

`memory/` 下每条记忆一个文件，带 `name / description / type` 三元数据。
`type` 分四类：`user`（用户偏好）、`feedback`（对我的工作方式的纠正）、
`project`（项目状态与决策）、`reference`（外部资源指针）。

**为什么要有它**：会话会被压缩，压缩后细节丢失。记忆是**跨会话的锚**——
比如「闸2阈值已从 0.15 改到 0.23，docstring 仍写 0.15 属注释债、裁定不修」这种
「看起来像 bug 但其实是决定」的信息，没有记忆就会被下一轮重新「修」一遍。

### 4.3 子 agent：只在能并行时用

会话来里真实用过的委派场景：文件盘点、跨多个文件找证据、独立复核。
**不用的场景**：单点查找、需要我有完整上下文的判断 —— 委派的交接本身会丢信息。

### 4.4 MCP：让模型直接驱动 EDA 工具

| MCP | 用途 | 实测调用 |
|---|---|---|
| `vivado-mcp` | 直接跑 Tcl：建工程、改 BD、综合、布线、出 bit | 180 次 `vivado_execute` + 14 次 `vivado_start` |
| `easyeda-mcp-pro` | 原理图/PCB 核对（相机转接板 41 线 17 网的网表复核） | 100+ 次 |

**价值**：模型不再「给出 Tcl 让人去跑」，而是**自己跑、自己看报告、自己改**。
例 8 的三臂隔离实验就是靠 `vivado_execute` 在一个会话里跑完的。

## 五、这份记录怎么核

### 5.1 原始材料

8 个会话文件（JSONL，Claude Code 的原始落盘格式）：

```
<用户主目录>/.claude/projects/<项目目录>/*.jsonl
```

合计 784.8 MB、128,584 行。

> 原始 JSONL 里含本机的用户名与工作目录，**不随包提交**。拿到本记录的人可用下面这个脚本，
> 在自己的会话目录上原样重跑一遍提取——脚本只读 JSONL，不写任何东西到源目录。

### 5.2 提取脚本

`build/extract_llm_log.py` —— 读上面这堆 JSONL，产出单文件报告
（头部带时间/主机/脚本 sha16，每写一笔即 flush，屏幕与文件逐字相同）。

```bash
python build/extract_llm_log.py --out _llm_log_extract.log
```

**它踩过的一个坑，正好是本记录诚实的证据**：
第一版按 `message.id` 去重后只留第一条，结果统计出「13,752 个思考块、**工具调用 0 次**」。
原因是 Claude Code 把一条回复的 thinking / text / tool_use **分成多行落盘、共享同一个 message.id**，
按 id 丢重复会把正文和工具调用全丢掉。改成「按 id 合并、块级去重」后，工具调用变成 15,713 次。

⇒ 所以：**任何「统计出来的数」在被复核前都可能是错的**。这与本记录第三节讲的是同一件事。

## 六、小结：这套协作方式实际改变了什么

1. **判据前置**：人不再描述「要做什么」，而是先描述「什么算做对了」。模型的产出因此可验收。
2. **失败可复用**：每一次翻车都变成一条记忆或一条技能包条目，下次同类场景直接命中。
   `skill/` 里 40 余份 reference 与 10 个可直接运行的校验脚本，**没有一条是设计出来的，全部是被失败逼出来的**。
3. **模型也必须自证**：第三节 8 例里，**8 例都是模型先给出错误答案**。
   本记录不打算把它写成「模型很聪明」，而是写成「模型会错，但有办法让错误尽快暴露」。
