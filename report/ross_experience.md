## 一、怎么用的

### 启动方式

ROSS 以 `claude --bare` 子进程方式启动，挂载官方 plugin 与 Vivado MCP 配置：

```bash

  --plugin-dir "D:/study/competition/qian/_official_repos/ross-ai-assistant" \
  --mcp-config "D:/study/competition/ross/.mcp.json" \
  --strict-mcp-config \
  --allowedTools "Read Write Edit Glob Grep Bash(...) mcp__vivado-mcp__*" \
  --output-format stream-json --verbose \
  -p "<任务书>"
```

- **任务书写成文件**（`spec/TASK_BRIEF_*.md`），prompt 里只写"先读这个文件，严格照做"，避免 shell 转义问题。

## 三、缺点

### 1. 只验时序，不验功能（**最大短板**）

三期的全部"PASS"都停留在**时序 / DRC / 文件生成**层面，**从未真正跑过一次数据通路**。

它交付的位流，直到我拿到板上实测，才知道是能加载的。在这之前，"成功"这个词是悬空的。

### 2. 自己写的 IP 在硬件上是死的

第一期自研的 `hls_regs` 模块（AXI-Lite 从设备），板上实测：

- 4 KB 地址空间 **1024 个字全扫，非零 0 个**
- 满写 1024 个字各写唯一图案，回读 **非零 0 个**

排除项（逐条查过，均不成立）：PS 脚本、偏移、GP 口、互联、时钟、复位、BD 连线、`.bit`/`.hwh` 配对、地址未映射。

**根因定位在 `hls_regs` 内部**：AXI 握手能完成（否则 CPU 会挂死），但 RDATA 没有被寄存器文件驱动、写使能也没生成 —— 一个"礼貌地回 0"的从设备。

**关键问题不是它写错了，而是它有 cosim 流程却没测出这个。** 它的验证覆盖了算法核（remap / sharp / color），却没覆盖 AXI 协议层。

> **补记（2026-11-03 23:08，回给 ROSS 后）**：它一轮 20 分钟就修复了，且板上验证通过。
> 详见下文「七、修复表现」。

### 3. 构建互斥缺失

自己撞自己：重复启动 `run_build`，和正在跑的构建冲突，`wait_on_run impl_1` 失败。启动前不检查"是否已有构建在跑"。

### 4. PASS 口径过宽

"R1a–R1g 全部 PASS"读起来像"东西成了"，实际只是"文件齐了、时序过了"。**验收项应该分级**，否则读者会高估完成度。

### 5. 对环境残留不敏感

我这边 `F:/vivado/2026.1/Vivado/scripts/Vivado_init.tcl` 有一处注入残留，导致每个子 Vivado 都打印 `vivado-mcp: port 9999 busy, exiting`。它发现了并写进报告，但没有把"环境自检"变成流程的一部分。

**同类第二例（2026-11-04 00:0x）**：第三轮重建时 Vitis HLS 的 `set_part` 突然报
`failed to find any device libraries` / `command 'create_platform' returned error code`，
而**同一台机器、同一套 `.bat`，当天 15:38 刚跑通过**。它和我分别试了命令行直调、`cmd /c` 调 `.bat`、
去掉已废弃的 `-flow_target vivado`、新建空工程 —— 全部同样报错，到收工都没定位。
环境变量本身是对的（`RDI_DATADIR = F:/vivado/2026.1/Vitis/data`，`data/parts/xilinx/zynq` 齐全）。

这一条不计在 ROSS 头上（是工具链的问题），但它说明**"构建能不能起来"本身没有前置自检** ——
一个 10 秒的 `set_part` 冒烟，就能在任何长流程开始前把这类问题挡掉，而不是跑到阶段 4 才发现。

## 四、根因分析：为什么强在"跑通"、弱在"跑对"

| 维度 | 表现 | 原因推测 |
|---|---|---|
| **流程编排** | 很强 | 综合/实现/写位流是**有明确成功判据**的机械流程，日志里有 `end.rst`、有 timing report，Agent 只要读判据就行 |
| **故障恢复** | 很强 | 错误信息明确（`Could not open 'C'`、JVM crash），可搜索、可试错 |
| **功能正确性** | 很弱 | **没有明确的成功判据**。什么叫"这个 AXI 从设备是对的"？需要有人定义测试。ROSS 不会自己发明验收标准 |
| **硬件验证** | 无 | 它没有板子。它不知道自己的位流烧上去会怎样 |

一句话：**ROSS 擅长"有判据的任务"，不擅长"需要自己发明判据的任务"。**

## 五、改进建议

### 优先级 P0 —— 直接影响交付可用性

**1. 把"功能验证"设成交付硬门禁**

位流交付前必须至少有：
- 一条 AXI-Lite 读写回环证据（每个寄存器读默认值 + 写读回环）
- 一次端到端数据通路证据（DMA 进、DMA 出，比对输出非零/符合预期）
- 一条**容量自检**证据（**2026-11-03 新增**，实测踩到才加的）：
  - `DMA 单次传输上限 ≥ 一帧字节数`（本次：16,383 vs 1,228,800，差 75 倍）
  - `FIFO 深度 ≥ 一行像素字节数`（否则行内就会溢出）
  - `时钟带宽 ≥ 目标分辨率×帧率×像素字节数`
  - **这三条都必须在交付前用数字算一遍并写进报告**，不能靠默认值

没有这三样，不许在报告里写 PASS。

> 为什么这条特别重要：前两样能证明「通路是通的」，但**证明不了「通路的容量够用」**。
> 本次两个缺陷正好落在两个不同的层次——前一个是编码错误（双驱动），后一个是**设计时没算过账**
> （照单全收了 Vivado 的默认 `C_SG_LENGTH_WIDTH=14`）。前者考的是细心，后者考的是**有没有把需求换算成参数**。

**2. 给 AXI 从设备配自检模板**

生成任何 AXI-Lite 从设备 RTL 时，自动附带一个协议级 TB：
- 遍历所有地址，读默认值并与寄存器映射表比对
- 每个可写寄存器写图案再读回
- 检查 `rvalid`/`bvalid` 是否真的拉起来（不是只看 RDATA）

成本很低，能直接拦住第一期那个缺陷。

### 优先级 P1 —— 影响效率与可信度

**3. 构建加互斥锁**

启动构建前探测是否已有 build 在跑（进程、锁文件、`.runs` 状态都行）。

**4. PASS 分级**

拆成三档，不许混用：
- **时序 PASS**（WNS ≥ 0、DRC 0 errors）
- **加载 PASS**（配置成功、IP 枚举完整）
- **功能 PASS**（数据通路跑通、结果符合预期）

**5. 失败案例沉淀进 skill**

`tclapp` 并发竞态、JVM 崩溃、`impl_1` 静默死亡 —— 这三类它已经各自独立解决过。应该写进自己的 knowledge base，下次自动规避，而不是每次重新踩。

### 优先级 P2 —— 锦上添花

**6. 环境自检进报告头**

启动时检查：Vivado 版本、`Vivado_init.tcl` 注入、磁盘余量、已有会话，把结果写进报告第一屏。

**7. 报告里的"未验证"要前置**

`REPORT_REBUILD.md` §7 的"没有做任何功能验证"应该放在**报告开头**，而不是第 7 节。重要限制不该埋在末尾。

## 六、适用边界

| 场景 | 适不适合 | 说明 |
|---|---|---|
| 陌生工程的完整重建 | **很适合** | 本次盲测已证明 |
| 版本迁移 / 工具链适配 | **很适合** | 版本闸门、IP 自动升级都处理得干净 |
| 构建故障排查 | **很适合** | 竞态、崩溃、静默死亡都能自愈 |
| 从零设计新 IP | **谨慎** | 能写出来、能综合、能出位流，但**功能正确性没有保障** |
| 需要板上验证的任务 | **不适合** | 它没有板子，也不会主动要求验证 |
| 需要自己定义验收标准的任务 | **不适合** | 它的"PASS"只覆盖它能读到的判据 |

**最推荐的用法**：让 ROSS 干"有明确机械判据"的活（重建、迁移、排构建故障），
**功能验证和板上验证由人（或另一个有板子访问权的 Agent）接手**。

## 七、修复表现（第四期）—— 这是它最强的一次表现

把一期的板上故障（现象 + 7 条已排除项 + 测试脚本）写成任务书回给它，**一轮 20 分钟**（22:47:53 → 23:08:21，EXIT=0，无重试）完成定位、修复、验证、重建。

### 7.1 根因：`rdata_r` 双驱动

`work/rtl/hls_regs.v` 里 `rdata_r` 被**两个 `always @(posedge aclk)` 块同时赋值**：

- 读通道状态机的复位分支里：`rdata_r <= 32'd0;`
- 下方专门的读数据块里：`if (ar_cap) rdata_r <= rdata_mux;`

| 场景 | 行为 |
|---|---|
| **RTL 仿真** | 按源码顺序"后者覆盖前者" → 仿真全绿，**两份 TB 在修复前就是 PASS** |
| **综合** | 判为 multi-driven，**保留常量 GND 驱动、丢弃真实数据驱动** → `s_axi_rdata` 恒 0 |
| **硬件** | 写通道独立、握手正常，能收下写、不报总线错，但永远读不回 |

这完美解释了"从机能握手但读恒 0"的现象——我最初误以为的"写不落地"，其实写真的落地了，只是读不回来。

### 7.2 它做对的关键一步：换判据

它意识到 **RTL 仿真对这个缺陷物理上不可见**，于是主动把验收门槛从「RTL 仿真绿」改成「**综合 0 critical warning + 门级仿真绿**」，并为此新建了一个 34 项检查的板级行为复现 TB，在**未修复**的网表上先跑出 RED。

这一点很重要：它不只是修了一个 bug，而是**修正了自己用来判断"对"的那把尺子**。

### 7.3 我独立复核的数字（不是听它说）

| 项 | ROSS 声称 | 我核到的 |
|---|---|---|
| RTL 改动 | 只删一行 | `diff` 确认，仅删 `rdata_r <= 32'd0;` + 加注释 |
| 修复前告警 | 96 条 critical | Vivado 汇总行 `96 critical warnings`；64×`8-6859` + 32×`8-6858` = 96 ✓ |
| 修复后告警 | 0 条 | `0 critical warnings` ✓ |
| 门级仿真 | RED 32 errors → GREEN 0 | `FAIL (34 checks, 32 errors)` → `PASS (34 checks, 0 errors)` ✓ |
| 旧网表 | `s_axi_rdata = <const0>` | 网表确认 ✓ |
| 新位流 | 2,078,271 B / `eb5f7115…` | 一致 ✓ |
| `.hwh` 未变 | 与旧文件逐字节相同 | 两边都是 `63301e16…` ✓ |
| WNS / DRC | 0.933 ns / 0 Error | 时序报告 `0.933`，DRC 42 项全 Warning/Advisory、0 Error ✓ |

### 7.4 板上最终验证（2026-11-03 04:25，PYNQ-Z2）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 4 KB 扫描非零字数 | **0 / 1024** | **896 / 1024** |
| 寄存器默认值 | 全 0 | CTRL `0x00000002`、VERSION `0x00010000`、SRC `0x01E00280`、DST `0x016A0200`、GAIN `0x00000100` **全对** |
| 读写回环 | FAIL | **2/2 PASS** |

**896 这个数字与它门级仿真的预测值一模一样。**（896 = 14 个非零寄存器 × 64 个 64 字节别名块，正好对得上它自己指出的"ADDR_WIDTH=6 导致 64 字节镜像"这个遗留问题。）

> 首次上板时报告里 `[D]` 出现三个 FAIL，事后查明是**测试脚本自己的顺序 bug**（把破坏性的满写测试排在默认值核对之前），
> 与 RTL 无关。修正顺序后重跑，最终汇总为：
> **A=PASS　B(对照组)=PASS　C(扫描非零)=896　D(默认值)=PASS　E(回环)=PASS**，
> `[D]` 五项、`[E]` 两项全部命中预期值，报告自洽。

### 7.5 它还主动报了一个非阻塞遗留

`ADDR_WIDTH = 6` 但地址块 `RANGE = 0x1000`，实际只译码 64 字节 → 每个寄存器每 64 字节镜像一次。它在无人值守、可以自由选择的情况下**没有偷偷改掉这个**（改了要重做 module-ref IP、重生成 BD），而是记录下来并在新 TB 里按别名行为做了显式校验。**这是很成熟的工程判断。**

### 7.6 唯一的遗憾

它留下的"修复前 96 条告警"原始证据在工程目录里**被自己后来的重跑覆盖了**（`runme.log` mtime 22:59，搜不到 `8-6859`）。幸亏它的一键脚本 `verify_run_buggy.log` 完整留存了原件，证据链才没断。**证据应该在产生时就另存一份副本**，而不是指望原始日志能活到报告写完。

### 7.7 紧接着暴露的第二个缺陷：DMA 传不动一帧

寄存器通路修好、板上全绿之后，再跑一步 `smoke_phase1.py --dma`（真正的数据通路），立刻撞墙：

```
ValueError: Transfer size is 741376 bytes, which exceeds
            the maximum DMA buffer size 16383.
```

**根因在设计里，不在 PS 脚本里**：`axi_dma_0` 的 IP 参数

```
C_SG_LENGTH_WIDTH = 14     -> 单次传输上限 16,383 B
C_INCLUDE_SG      = 0      -> Simple 模式，每次传输都拉 TLAST
```

对比一帧的体量：

| | 字节数 |
|---|---|
| 源 640×480×4 | **1,228,800** |
| 目标 512×362×4 | 741,376 |
| 该 DMA 单次上限 | **16,383** |

⇒ **一帧需要 76 次传输**。而 Simple 模式每次传输结束都会拉 `TLAST`，
下游核心会看到 76 个「帧结束」。

作为对照：同类的可用设计把 `C_SG_LENGTH_WIDTH` 设为 **23**（上限 8,388,607 B），整帧一次传完。

**这一条暴露的问题比上一条更深**：

- 上一轮的双驱动是**编码错误**——写错了一行，改掉就好。
- 这一条是**设计时没有算过账**：它写了一个图像处理流水线，却从来没问过
  「我这个 DMA 一次能搬多少字节，够不够一帧」。`C_SG_LENGTH_WIDTH=14` 是 Vivado 的默认值，
  它照单全收了。

**寄存器能读能写 ≠ 数据能流过。** 这两件事在它的验收体系里是同一个 PASS。

### 7.8 第二轮（fix2）：它自己查出并交出了一个更深的缺陷

把 DMA 缺陷回给它之后，13 分 36 秒产出 `REPORT_FIX2.md`（15,958 B）。这一轮的表现**比 fix1 更有意思**。

**它改对了要它改的**

| 项 | 结果 |
|---|---|
| `C_SG_LENGTH_WIDTH` | 14 → **23**（上限 8,388,607 B，对一帧 1,228,800 B 余量 5.8 帧） |
| 落地一致性 | 活 BD 属性 / `.xci` / 交付 `.hwh` 三处一致 |
| 时序代价 | WNS **1.588 ns**、WHS 0.021 ns，仍有富余 |
| 新 `.bit` / `.hwh` | `ac3d057d…`（1,705,975 B）/ `790a9173…`（315,068 B）—— **我独立复算，与它自报逐位相同** |

**它没要它做的事，它自己也做了**

报告 §5 它主动交出了**第二个阻断点**，而且不是靠猜：

1. 从 Vivado 2026.1 自带的**未加密 datamover RTL**（`axi_datamover_v5_1_rfs.vhd:46680`）
   找到 `sig_tlast_error_* <= '0'` —— **不定长模式下 TLAST 早到不会被标成错误**；
2. 再找 `lsig_strm_eop_asserted` —— 流上**任意**一个 TLAST 都被当 EOP；
3. 由此推出：`C_INCLUDE_SG=0` 时 S2MM 会在**第一个 TLAST** 就收尾，**且不报错**。

然后它写了一句我认为是这一轮最有价值的话：

> **"位宽修好只是必要条件，不是充分条件。"**

并且**明确拒绝顺手修掉**，理由写得很清楚：任务范围只允许改一个 IP 参数，
修 TLAST 要动 HLS 语义 → 重跑综合 → 会让"本轮只改了一个参数"这个干净因果关系变模糊。
它把**精确修复点**交出来（`axis_sharp.cpp:127`），把决策权留给下一轮。

> 这是一个比"我全修好了"更成熟的判断。上一轮它的问题是**不问需求就动手**，
> 这一轮它主动划了边界、给了证据、标了未验证 —— 从"交付者"变成了"诊断者"。

**它的判据这次真的能判红**

`work/scripts/check_dma_frame_capacity.tcl`，我实测两遍：

| 对哪个产物 | 输出 | 退出码 |
|---|---|---|
| fix2 新 `.hwh`（23 位） | `summary: PASS 2 / FAIL 0`，`OVERALL: PASS` | **0** |
| fix1 旧 `.hwh`（14 位） | `shortfall = 1,212,420 B`，`VERDICT: FAIL`，`OVERALL: FAIL` | **1** |

⇒ 不是空转门禁。

**我这边补的三条复核（它没写全）**

1. `axis_sharp.cpp` 的 `o.last = (ocol == w - 1) ? 1 : 0;` 在 `if (enable)` **之外**
   —— **`enable=0` 旁路时照样逐行拉 TLAST**。
2. `remap.cpp:204` 逐行同理。本设计**没有**独立旁路模块（`.hwh` 里只有 8 个 MODULE），
   `axis_sharp` 永远在通路上 ⇒ 它的 TLAST 就是 S2MM 看到的那个。
3. ★ **我自己的验收脚本是空转门禁** —— fix2 版 `[G]` 判据原来是 `nz > 0`：
   只要目标缓冲里有**一个**非零字节就算 PASS。而"第一行就被截断"恰好是
   **写进 2,048 B 就不写了**，`nz` 依然 > 0 ⇒ **它会报 PASS**。
   已改成看 `last_nz`（最后一个非零字节的偏移）：整帧传完必落在最后一行，
   第一行截断则停在 ~2047。**这是本项目"永远通过的门禁"第 N 次复发，而且是复发在
   我自己手里。**

### 7.9 板上实测：TLAST 截断被逐数证实（2026-11-03 23:5x，PYNQ-Z2）

把 fix2 位流（`ac3d057d…`）和改好的 v3 判据一起传板，跑 `--dma`。**跑之前我先写出预期读数**，
结果逐项对上：

| 项 | 我跑之前的预测 | 板上实测 | |
|---|---|---|---|
| 最后一个非零字节 `last_nz` | ≈ 2044 | **2044** | ✅ |
| 非零字节数 `nz` | ≈ 512（一行 512 像素 × 每像素 1 个非零字节） | **512 / 741,376** | ✅ |
| `S2MM` 完成 | True | **True** | ✅ |
| `FRAME_CNT` | 不增（帧没走完） | **0 → 0** | ✅ |
| `recvchannel.error` | False（TLAST 早到**不报错**） | **False** | ✅ |
| `MM2S` 完成 | 我以为 True | **False** | ❌ 我错了 |

板上原文：

```
[G] DMA 数据通路（640x480 -> 512x362）
    MM2S 完成=False   S2MM 完成=True
    recvchannel.error = False
    FRAME_CNT: 0 -> 0
    目标缓冲非零字节数 = 512 / 741376  (0.07%)
    最后一个非零字节 off=2044 / 741375    （一行 = 2048 B，末行起址 = 739328）
    判读：数据止于 2045 B —— 疑似在**第一行**就被 TLAST 提前收尾

```

**我错的那一项本身就是证据**：S2MM 在第一行收工后不再读流，`sharp → S2MM` 的 FIFO 被灌满，
反压一路传到 `remap`，`MM2S` 的 1,228,800 B 送不完 ⇒ 10 s 超时。**这正是"下游停了"的典型指纹**，
和我以为的"两边都完成"相反。写在这里是因为：**预测写下来才能被证伪，而这次它证伪了一条。**

汇总其余全绿、与 fix1 完全一致：`A=PASS B=PASS C=896 D=PASS E=PASS`。

**这一条把 ROSS 的静态推断升格成了板上事实。** 它 §5 那段是从 Vivado 未加密 RTL 推出来的，
写得克制（"有强证据但未上板确认"）；现在有板子上的数字了：**2,045 B / 741,376 B = 0.28%**。

### 7.10 第三轮（fix3）：任务书之外它自己又找出第三处 TLAST；但构建卡在工具链

这一轮我给的任务书里有五条：改两处 TLAST、正面回答"多帧会不会塌"、加一条**必须能判红**的静态门禁、
跑双帧仿真、重建到 `out_fix3/`。它交出了前三条，第五条卡在环境。

**（1）"多帧会不会塌"它没写"应该会"，而是去 RTL 里找依据。**

我的问题很具体：`axis_sharp` 是 `ap_ctrl_none`，`orow/ocol` 是函数内局部变量，第 2 帧开始时会不会归零？
上一轮它已经在别的问题上吃过"综合语义和仿真不一致"的亏，这次它给的答案带三层证据：

| 证据 | 出处 |
|---|---|
| `ap_CS_fsm_state5` **无条件**跳回 `ap_ST_fsm_state1`，而 state1 里 `orow/ocol` 被清零 | 综合出的 `axis_sharp.v` 第 583–589 行 |
| 交叉验证：TLAST 确实由 `ocol_2_out_i == w-1` 驱动（不是靠猜计数器名） | `Pipeline_VITIS_LOOP_40_2.v` 第 1183 / 1223 行 |

理由是那会给帧同步**新增一条对输入流的依赖**，而现有证据已经表明计数器自己会归零。拒绝得对 ——
我那个建议是"多一层保险"，代价是引入新的失效面。

**（2）改了三处，第三处不在我的任务书里。**

| `remap.cpp:207`（主路） | `o.last = ((y == dh - 1) && (x == dw - 1)) ? 1 : 0;` | 是 |
| `remap.cpp:87`（**旁路**） | `p.last = ((r == sh - 1) && (c == sw - 1)) ? 1 : 0;` | **否 —— 它自己找出来的** |

`remap.cpp` 里有一条 `enable` 旁路分支，直通不插值，但**同样逐行拉 TLAST**。我在任务书里只点了主路。

### 7.11 我没等它：板上「按行收」，把"唯一阻断点"证成孤证（2026-11-04 00:2x，PYNQ-Z2）

fix3 的位流被 HLS 卡住了，但我不需要新位流也能回答一个问题：
**除了逐行 TLAST，这条数据通路还有没有别的毛病？**

办法是纯 PS 侧的：不改位流，把**一次 741,376 B 的 S2MM 拆成 362 次、每次 2,048 B（一行）**。
每收到一行就重新武装一次接收 —— 于是"每行一个 TLAST"从故障变成了**刚好匹配的协议**。

跑之前先写下预期，结果是全中：

| 项 | 跑之前的预测 | 板上实测 | |
|---|---|---|---|
| 收完的行数 | 362 / 362 | **362 / 362** | ✅ |
| `last_nz` | 落在最后一行（739,328–741,375） | **741,374** | ✅ |
| `FRAME_CNT` | 会增 | **0 → 1** | ✅ |
| `MM2S` 完成 | True（下游不再反压） | **True** | ✅ |
| `S2MM` 完成 | True | **True** | ✅ |

板上原文（三通道激励版）：

```
[G] DMA 数据通路（640x480 -> 512x362）
    按行收：完成 362 / 362 行
    按字节通道统计非零（共 185344 像素）：lane0=185343 lane1=185340 lane2=185160 lane3=0
    行0   前 16 B: 78 ef 8c 00 83 e1 8c 00 8f d2 8c 00 9a c4 8c 00
    行361 前 16 B: df 7b 16 00 d9 80 16 00 d4 84 16 00 ce 89 16 00
    MM2S 完成=True   S2MM 完成=True
    recvchannel.error = False
    FRAME_CNT: 0 -> 1
    目标缓冲非零字节数 = 555843 / 741376  (74.97%)
    最后一个非零字节 off=741374 / 741375
    判读：数据覆盖到最后一行 —— 整帧传完
    PASS
```

三个颜色通道都有数据、`lane3`（alpha）恒零 —— 这和源码里 `o.data = (ap_uint<32>)px` 而 `px` 是
`ap_uint<24>` RGB 完全吻合，**是设计本意，不是丢通道**。

**这里我自己先踩了一次假阳性，必须写进来。** 第一版激励我只填了 byte0（蓝）+ byte3=255，
板上一量是 `非零 185,343 / 741,376 = 25.00%`、`lane1 = lane2 = 0`。25.00% 这个数太整了
（741,376 ÷ 4 = 185,344），第一反应是"每 4 字节只有 1 字节有数据，丢通道了"。
回去读 `remap.cpp` 才发现：是我自己的激励只喂了一个通道，**测出来的"缺陷"是我造的**。

这和 §7.9 那次预测错 `MM2S` 是同一类错误的两个方向：
**自报成功不算成功，自报失败也不算失败 —— 都得回去看原始证据。**

**结论（这一条把 fix3 的必要性锁死了）：**

> 这条数据通路**没有第四个毛病**。整帧 741,376 B、三个颜色通道、帧计数器，全部正常。
> 唯一的阻断点就是「逐行 TLAST + Simple 模式 S2MM」这一处。
> fix3 那三行改动一旦能重建出位流并上板，`--dma` 一次性收整帧就应该直接 PASS。

也正因为这样，fix3 卡在 HLS 环境上才格外可惜 —— **差的不是能力，是一个能跑起来的编译器**。

### 对 ROSS 评价的最终修正

初次评估时我写它"强在跑通、弱在跑对"。**这个结论只对了一半，需要修正为**：

> **ROSS 的「跑对」能力取决于你有没有给它一个能判红的判据。**
>
> - 给它"位流生成成功"这种弱判据 → 它交付三个 Phase，功能一个没验。
> - 给它"这两个寄存器读回来必须等于 0x..."这种强判据 → 它 20 分钟定位到一个仿真看不见、
>   只有综合语义才会暴露的双驱动缺陷，并且**顺手把自己的验收标尺也改对了**。

所以真正的用法不是"别让它做需要判据的活"，而是：
**你负责定义"什么叫对"，它负责把"对"做出来。** 判据越硬，它表现得越好。
