| 442 | 改了包里的一个 `.py`，队友的安装 notebook 第一秒就报"上传未完成"（文案误导，包其实是对的） | 分发链**三处哈希必须同步**：① 清单里逐文件 sha256 ② zip 的 sha256 ③ 安装本里写死的两个常量。**做成一个幂等脚本**一次改全；改完用**对方脚本的判据**自检，不要只用自己的校验 |
| 443 | 用户报"点一下就闪退"，我差点顺着自己最近的改动查。真相：随包发来的日志**不是这一版代码跑的** | 拿到"能跑"的参考日志，**第一步 `grep` 一个该版本才有的 stage 名**；搜不到 ⇒ 版本不符，整条对比作废。被问"是不是你们改坏的"时，先定位**崩溃点相对自己代码的位置**，再看文件 mtime。**报错文案会骗人，stage 计数不会** |
| 444 | 拆帧耗时，把几个 `*_wall_s` 相加，**分项之和超过了总时长** | 分项之和 > 父项 ⇒ **一定是嵌套计时，不是浪费**，先修归因再修代码。新增计时器 `begin` 一律在**本函数入口**取，绝不从下游捡时间戳（除非字段名写明 `*_since_xxx`）。每加一个就打出"父项 − 已知子项 = 未归因"，**必须非负** |
| 445 | 用户问"摄像头不是只出 15 帧吗，静态怎么跑到 16.5"，我差点当测量误差 | **标称/协商/配置里的数字不能当实测**。真实出帧率 = `Δ序号 ÷ Δ时间戳`。证明"吃满上游"要同时给两条：①上游真实速率 ②**每处理 1 帧对应的上游推进量 ≈1.0**。目标帧率接近标称值时，**先怀疑标称值** |
| 446 | 算出"某段有 21~27 ms 的 Python 开销"，正准备去优化那些 numpy 运算 | 每个 `*_wall_s` 旁边必须有 `*_thread_cpu_s`；**差值 ≥10% 先怀疑"在等"**，不是代码慢。`wall−cpu` 大 ⇒ **砍线程数或砍别的线程的活**，不是砍这段代码。优化前后都用 `wall/cpu` 双指标验收 |
| 447 | 连着几天拆跟踪器（162→108 ms），动态帧率只从 5 爬到 8 | 帧率上不去，**按线程分账，不按阶段分账**（camera/prepare/owner/display/log 五个线程）。`wall−cpu` 持续 >10% 不要归因成"调度噪声"，去查**同期谁在跑**。优化前先问"**这块占整帧多少**" |

| 449 | 把双线性换成最近邻（理论快 4 倍），实测 94.0 → 92.1 ms，**一点没快** | 换算法第一版"一点没快" ⇒ **立刻停止调参，改为证伪瓶颈假设**。优化前先 `grep` "这功能是不是已经有人写好了"（本例 `FusedDisplay` 存在、比例正好、注释完整，但**全工程 0 处实例化** —— 是死代码不是没写）。**报告"优化失败"要和报告成功一样及时** |
| 451 | 我回了一句"仓库里没有生成脚本，加按钮要手工出图，**我做不了**"，差点推掉整个功能 | 说"做不了"之前把**缺什么具体化**：缺素材 ≠ 缺能力。技术限制要精确到**哪一层**（"OpenCV 不支持中文"是**运行期**限制，不等于"素材做不出来"）。**先试一条命令**（30 秒就能证伪）。决定手搓素材就必须同时交生成脚本 |
| 452 | 要做运行时切分辨率，第一反应是"把 width/height 改掉" | 先找"**这条路是不是已经存在**"（会话式架构里通常有现成的"重开"路径，原地改参数永远是最后选择）。确认变量是**容量**还是**有效值**。用一张档位表管住所有跟随项。换档后"自动重新定位"是重开会话的天然结果，别单独写 |
| 453 | 往 358 行的大函数里加代码，被**同名的老局部变量**炸了：一进实时页就崩 | 往超过 100 行的函数里加变量前，`grep` 这个名字在**当前函数**里出现过几次（1 秒）。**新变量一律带前缀**。编译器不会告诉你"覆盖了不同类型的同名变量"。改完要找到所有用旧名的地方。**这类错只在走到那一段时才炸 ⇒ 必须跑一次真正调用它的路径** |
| 454 | 新按钮"页面上找不到"。日志里明明有 `PANEL_OPEN/APPLIED`，差点据此判断"UI 没问题" | 渲染用的**可见性/布局**这类每帧都变的量，**不要在状态机里缓存**，交给画的那一端按当前上下文判。**出厂日志必须是空的**（打包前清零，单测 `P11_TEST_NO_LOG=1`）。读板子日志先看"**这条记录能不能被板子产生**"（出现测试专用字符串 ⇒ 日志被污染，整段作废） |
| 455 | 改分辨率时改了 7 处调用点，**漏了第 8 处**（藏在 `async def` 回调里）；同轮还伴随"切不了/✕只退一层/闪退"三个怪现象 | 全局性改动**必须 `grep` 全仓所有调用点**，不能按文件挑；每一处都要**逐个确认语义**，尤其藏在回调/闭包/async 里的。**初始化顺序**：被依赖的状态必须先设。按下即生效的动作必须把同一次接触的"抬起"也吃掉。**多个怪现象同时出现时，先找是不是一条因果链** |
| 456 | 按钮"点了没反应"：按下有高亮，什么都不发生。日志有 `PANEL_OPEN` 但没有目标事件 | 本项目约定：**"按下即生效"用 `consumed=True`，"要等抬起"必须 `consumed=False`** —— 抄同项目已有的正确写法，别按直觉。有面板日志但没有目标事件 ⇒ **往派发层查**，别查热区/坐标。给事件驱动 UI 打补丁前，先读懂**事件生命周期**（按下→派发？→抬起→派发？） |
| 457 | 切档成功了，但之后 25 次会话启动全部失败，用户感知是"闪退之后点不进去" | 一个字段若有**"容量/上限"和"当前值"两种语义，必须拆成两个字段**。`grep` 一个字段时，**赋值和使用（尤其比较）都要看全**。**"自己人的校验"是切档的头号杀手**（平时恒真，参数一变立刻全量拦截）。引入可切换参数前，先把该参数参与的**所有断言列成表**，逐条写"切换后是否仍成立" |
| 458 | 用户说"切换时等待很长"，按直觉会去优化"会话重启" | 凡是"慢"，**先按已有 checkpoint 拉时间线**，找最大那一段。**分段时间要看最小子项**（本例 2.1~4.1 s 里 99% 是 `camera.close()` 一行）。定位到"不是自己的代码"后，先评估改动代价；改不动就走**感知路线**（进度条/分阶段文字）。**进度条不需要动画时钟**，按"已用时间"每帧算即可，封顶 95% |
| 459 | 我提"不关相机、就地改分辨率"，写了一半才发现 `S_FMT` 同样必须先 `STREAMOFF` | 优化动到**物理约束**（必须停流/必须重开/必须等硬件）时，先把约束列出来 —— 约束没变，优化就是自欺。把耗时项按"**能否避免**"分类。**不能编译验证的原生改动默认不做**。**已经开始写了也要敢撤**（用 `cmp` 证明还原干净） |
| 460 | 进度条连续两轮"看不到"。第一轮判断"没有重绘时机"，修完**仍然看不到** | 分三层排查：**被调用？走到底？画出来？** 每层给一个可观测证据。渲染没生效，先看"渲染函数有没有被调用"（**日志计数 = 0 是强证据**），再看调用路径上有没有**早退**。项目里每道"防事故早退"都要问"新状态下它还成立吗"。**第二次没修好时，不要沿用第一次的假设** |
| 461 | 换队友基线时，我们的**软件改动全在**，据此判断"合并得很干净" —— 实际硬件 RTL **静默回退**，核慢了 1.53 倍 | 换基线时 `diff` 必须**同时覆盖软件和硬件源码两棵树**。**RTL 没有版本号自证**（IP 版本恒为 1.5，换核心算法也不变）⇒ 必须比对源文件哈希。回答"能不能做"之前，先 `grep` 本项目有没有做过（那次差点把三周前的成果说成"新实验，建议不做"） |
| 462 | 拿 `service` **中位数** 35.5 ms 去比相机周期 33.3 ms，得出"只差 2.2 ms"，用户直接反问"怎么跟 30 帧差这么多" | **谈帧率只谈均值和 p90，不谈中位数**（中位是"典型帧"，帧率是"所有帧的总时间"）。任何"只差 X ms"必须写清**和哪个统计量比**。**先确认日志采样比**（本例 `V64_FRAME` 每 4 帧一条 ⇒ 周期 = Δt/4）。优化收益按"**周期 = 均值 + 固定开销**"重算，不能拿 `1/service` 当 fps |
| 463 | 我看字段名 `parameter_queue_s`（中位 4.7 ms）推断"每帧都在重写参数"，并承诺"砍掉能 +3 fps" | 承诺收益前**必须打开产生该字段的那一行代码**，确认它是"花掉的时间"还是"**等来的时间**"。`*_wait_s`/`*_queue_s`/`*_idle_s` 一律按等待处理；真开销在 `*_work_s`/`*_copy_s`/`*_sync_s` 这类动词字段里。**两个 wait 同时非零 ⇒ 两头都没吃满**，瓶颈在 `service − 它们`。（本例积压的真实含义是"上游比下游快"，方向完全反了）|
| 464 | 切到 600P 后一点开标定就崩：`could not broadcast (600,800,3) into (480,640,3)`，480P 一切正常 | 任何"**源图贴进固定矩形**"的地方，先问"两个档位的源图一样大吗"。`canvas[a:b,c:d] = image` 这类裸赋值，**image 尺寸来自摄像头就是定时炸弹**。**缺陷只在第二个档位出现时，验收必须"每一档都完整走一遍 UI"**（那两份日志里 600P 帧数是 17 和 0，等于没测）|
| 465 | 我用逐像素 `int((long long)x*sw/dw)` 做 5:4 缩放，**比原实现还慢 49%**（114.8 vs 77.2 ms） | **ARMv7/Cortex-A9 内层循环里出现 `/` 或 `%` 一律当 bug**（没有硬件 64 位除法，走 `__aeabi_uldivmod`）。整数比例缩放先**展开成固定模式**（5:4 ⇒ 每 4 出 = 12 字节 memcpy，步进 15 字节）。**x86 主机性能测试不能代表 ARM**（主机只慢 14%，掩盖了板上的灾难）—— 主机只验正确性。已有算好的映射表就别重算 |
