## 验证方法论

| # | 坑 | 症状 | 教训 / 对策 |
|---|---|---|---|
| 42 | ⭐⭐⭐ **改了 RTL 参数但从没跑过该参数的端到端仿真** | ROWS 64→256 后小尺寸 TB 全过，上板第 0 行出错 | **改参数 = 改设计**。TB 用自己的小参数就等于没测到新配置；要有一份"与上板完全一致"的配置跑一遍 |
| 43 | ⭐⭐⭐ **计数器语义悄悄差一行** | `rows_written` 在行**开始**写时就 +1，上层提前放行读到半行 | 计数器的判据要写清楚是"开始"还是"完成"。**凡是"等某行到齐"的流控，都要问一句：怎么定义"到齐"** |
| 44 | ⭐⭐ **"只在边界暴露"的 race** | 同样的错逻辑只在第 0 行触发，之后被流控顶开 | 边界（第 0 行/第 0 帧/复位后第一次）是 race 高发区，**TB 要专门造边界场景** |
| 45 | ⭐⭐ **判据混入了固有噪声** | `max ≤ 1` 永远不满足，真 bug(57) 和固有差(3) 混在一起 | 判据要**把信号和噪声分开**；能拿逐位模型当参考就别拿浮点参考 |
| 46 | **按电平计数 vs 按边沿计数** | `frame_cnt` 每帧 +2 | 脉冲宽度不确定时一律数上升沿 |
| 49 | ⭐⭐ **生成物没进生成步骤，靠残留文件"看起来是过的"** | `run_sim.sh` 只跑了 `ref_homography.py`，漏了 `gen_core_vectors.py`；仓库里恰好有残留向量所以一直"全过"，干净检出必挂 | **用"删掉所有生成物再跑"来验证流程**。凡是 TB 要读的文件，都要确认它**本轮真的被生成过** |
| 50 | **TB 里混用 SystemVerilog 语法** | `disable fork` / `$isunknown` 在 `-g2005` 下报一堆语法错（错误位置还会指到无关的 RTL 上） | 本仓库 TB 统一按 Verilog-2005 编译；轮询用 `while` 代替 `fork/join_any`，X 检测用 `(^x === 1'bx)` |
| 56 | ⭐ **"参数化 TB"比"再加一个 TB"划算** | 尺寸写死的 TB 只能测一个配置；从文件读尺寸后同一份 TB 覆盖两档 | TB 的**编译期参数留给硬件（ROWS/MAX_W），运行时配置从向量文件读** |
| 57 | **`$readmemh` 到整个数组会报 "Not enough words"** | 数组按最大尺寸开、文件只有实际尺寸 → 一堆无害但吵人的警告 | 用带范围的 `$readmemh(f, mem, 0, N-1)` |
| 64 | ⭐⭐⭐ **"加个测量"改变了被测量对象的工作条件** | 加性能计时（连跑 4 帧）后全错，上一版（跑 1 帧）正常 | 加测量手段前先问：**它会不会改变被测对象的状态？** 重复执行 ≠ 执行多次同样的操作 —— 对**有状态**的系统，每次执行都是新场景 |
| 65 | ⭐⭐⭐ **"只支持单帧"这类已知限制，不能只写在 TODO 里** | RTL 注释里明明写了，但没人注意到连跑 2 帧会炸 | 已知限制要**变成断言**（这里是"多次运行结果必须一致"自检），写在注释里等于没写 |
| 66 | ⭐⭐ **同样的输入跑两次结果必须相同** | 是一句便宜的、能抓住一整类 bug 的检查 | 凡是**有内部状态**的加速器，都值得在驱动层加这条自检。静默垃圾比显式报错可怕得多 |
| 67 | ⭐⭐ **能在仿真里做的 A/B，别拿到板上试** | 上板一轮 10 分钟 + 占用队友；仿真 30 秒 | 这次的"复位能否修好"完全可以在仿真里验证（`two_frame_tb` 跑三帧） |
| 68 | **错误率的量级可以当指纹用** | 仿真 96% 错 vs 板上 85% 错 → 同一个根因 | 拿到故障现象先看**量级和分布**，不只是"错了" |
| 73 | **单帧跑不需要软复位** | — | 刚加载 overlay 已硬复位过，核本来就是干净的。**只在真正需要时（连跑多帧）才动硬件** |
| 81 | ⭐⭐ **"恰好能过"和"设计上能过"要分清** | test-6/8/9 只富余 31~60 行就"过"了 | 余量这么小的"通过"要当成**警告**看。写判据时算清**边界条件**，别靠试出来的几个案例 |
| 82 | ⭐⭐ **超时保护要报"现场"而不只是"超时了"** | 上一轮卡 4 分钟零信息；这轮 30 秒就定位 | 超时/异常处理里**读关键状态寄存器**，把"卡在哪"变成可诊断的数据 |
| 83 | ⭐ **构造能必然触发的回归用例** | 4 张样图里只有 1 张踩坑 | 别指望"再跑一遍真图碰运气"。**按判据反推参数**，构造一个必然复现的小尺寸 TB（这次是"输出 24 行 / 输入 48 行 / ROWS=16"） |
| 88 | ⭐ **修好了要复验下游** | 输出尺寸变了 → `fit_dma_length` 的整除约束、行缓存需求都可能变 | 改"输出尺寸的决定方式"属于改上游，**必须把下游的仿真回归全部重跑**（这次复验了 9 个 TB + 上板配置检查） |
| 102 | ⭐⭐⭐ **判据要分级，弱判据会"PASS 着掩盖 bug"** | `NDIV=8` 的误差从 0.0235 px 涨到 0.1409 px，**对着浮点真值的 TB 仍然 PASS** | "误差 < 1.0 px"这类**容差型判据**抓不到"调度/时序引入的微小系统偏差"。凡是声称"某改动不该改变结果"的优化（并行化、重定时、流水线重排），判据必须是**逐字节/逐位 diff**，不是容差。本项目：`NDIV=1/2/8 + 慢消费者` 四档逐像素 dump，`diff` 必须全空 |
| 103 | ⭐⭐ **死锁判据不能用"忙标志全零"** | TB 一直误报死锁 | 稳定运行时 8 个除法器**同时在算**，忙标志永远非零。正确判据是 **"发射/完成计数停止增长"** —— 幽灵资源正好让它停。另外要留**自愈窗口**（等若干拍看是否恢复），别在单拍上判死 |
| 104 | ⭐⭐ **同一条不变量可以在 TB 里逐拍查** | 幽灵除法器在 1 拍内就被抓到并打出 `busy/starts/dones` 三元组 | 与其"跑完看结果"，不如写出**结构不变量**（例：`busy[i] == (已发射数 != 已完成数)`、`~(start_oh[i] & busy[i])`）在每个时钟沿断言。它能**在故障发生的那一拍**定位，而且比"输出不对"早得多 |
| 105 | ⭐⭐ **探针要打到"操作数"那一层，才分得清"顺序错"和"值错"** | 输出文件只能看出"结果不对"；打出每个脉冲的 `(通道号, 锁存操作数, 代号)` 后，一眼看到"同样 (a,b) 结果不同" | 调试探针的层级决定定位速度：**状态级 < 结果级 < 操作数级**。当"同一份输入两次结果不同"时，唯一能定位的探针就是操作数级 |
| 106 | ⭐⭐⭐ **合并进程会丢掉"进程隔离"带来的隐式复位** | 把"每张图起一个子进程"改成"一个进程跑完所有图"（为省掉每次 10~14 s 的 overlay 加载）后，**第 2 张起全废**：帧计数 1,2,3,4，一致率 0.1~7%，出错行从 v=0 开始 | 原来每张一个进程 → overlay 重新加载 → **PL 被硬复位** —— 这个复位是"白来的"，谁都没写。合并进程后它消失了，而 `remap_core` 是单帧设计（`rows_written`/`frame_cnt` 只有复位才清零）。**教训：优化掉"重复的初始化"之前，先问它是不是顺带做了别的必需的事**（这里是复位）。对策：①显式补复位；②**加自检把这类问题变成响的** —— 软复位会清 `frame_cnt`（`axis_remap_top.v:207`），所以"复用 PL 时每张都应报帧计数 1"，报 >1 直接判 FAIL，不再靠"结果看起来不对"去猜 |
| 107 | ⭐⭐ **危险路径要配"自愈兜底"，别让用户白跑一轮硬件** | 修 106 时，用的"软复位"这条路文档标注"板上尚未充分验证"—— 万一没生效，用户又要跑一次板子才发现 | 凡是"修在板下无法验证的路径上"的改动，都给它一个**确定可靠的退路**并自动走：这里检测到复位没生效（帧计数≠1）就**自动重新加载 overlay 重跑本张**（慢 11 s，但可靠）。比起"报错让用户再跑一轮"，多 20 行代码更划算 |
| 108 | ⭐⭐⭐ **别把系统送上"文档自己都标注未验证"的路径** | 把"每张一个子进程"改成"一个进程跑 4 张"后，第 2 张起 DMA 超时 / `channel not started`。而 `--repeat` 的帮助文字原文就写着"**这条路径在板上还未经充分验证**"—— 批量模式等于把每次运行都送上了它 | **改代码前先搜"这条路径的既有说明"**：项目里凡是被标注过"未验证/踩过坑/慎用"的地方，都是**别人的血泪**，不要顺手绕过去。这里真正的雷是**同一进程内复用同一个 DMA 对象反复 transfer**（第 2 张超时后，`_dma_run` 的后台线程被遗弃但仍占着 DMA → 第 3/4 张连锁失败）。正解是先把 RTL 的多帧支持做对（可在仿真验证），再让上层享受 |
| 109 | ⭐⭐⭐ **收益要跟代价同量级才动手** | 为省**演示时约 35 s 墙上时间**，烧掉了用户**两轮真机上板**（每轮=上电+传文件+点 notebook+发日志），最后整体复原 | 动手前问一句：**"这属于这个阶段的目标吗？"** —— 这次答案是"不属于"（提速目标是**每帧成本**，不是脚本启动开销）。**拿不准时，先把收益/代价写出来对比再决定**；宁可少做一件事，也别拿真机轮次去赌边角收益 |
| 110 | ⭐⭐⭐ **证明"优化后结果不变"时，必须把【过滤器】也算进不变式** | 把 `findContours` 的 `RETR_LIST` 换成 `RETR_EXTERNAL`（只取最外层）：推理"挑选规则是取面积最大的，而面积最大的必然是最外层的（嵌套轮廓面积必小于父轮廓）"—— 看着无懈可击，675×900 下 7 个用例也**确实逐点相同**。但换到 900×1200 就崩：test-9 有效候选从 9 个变 **0 个**，直接找不到文档 | **漏的一环**：那个最外层候选常常是"整幅画面/桌面边界"，会被 `touches_border` **否掉**；此时真正的目标是**嵌套在它里面的子轮廓**，而 EXTERNAL 已经把它删了。⇒ 不变式的正确写法是"**目标对象 ∀ 竞争者，谁被删了会不会改变过滤结果**"，不是"目标对象还在不在集合里"。**并且一定要在【真实工作分辨率】下验证** —— 低分辨率下侥幸通过会给出虚假信心 |
| 111 | ⭐⭐ **"设想中的优化"也要量，别按直觉下手** | 想用 numpy 逐轮廓算 bbox 面积做预筛，替代对全部 6000 个轮廓调 `cv2.contourArea` —— 直觉上"Python 循环比 C 调用快"，实测**反而慢 2.4×**（0.42×） | 一次 C 调用（`cv2.contourArea`）打不过"Python 循环 6000 次 + 每轮几次 numpy 调用"。**跨语言边界的调用次数才是关键**，不是单次计算量。凡是"我觉得这样更快"的改动，都先写 20 行探针量一遍 |
| 112 | ⭐⭐⭐ **降采样提速的判据不能是"与旧版差多少"** | 金字塔找四角与全分辨率版差 0.89~5.65 px。若拿"偏差 < 0.5 px"当判据 → 永远过不了，好方案被毙掉 | **"与旧版不同" ≠ "更差"** —— 旧版自己就有系统偏差（`approxPolyDP` 在**膨胀过**的 Canny 边缘上取顶点 → 系统性外扩）。正确做法：找**与实现无关的客观指标**。本项目现成有 `measure_grid.py`（格子边长均匀/直线度/直角/方正度），拿两种结果各自校正出图再量 —— 实测 24 项里快 14/平 6/略差 4，全部在标准内 ⇒ 判"等效" |
| 113 | ⭐⭐⭐ **非交互环境的降级兜底，绝不能依赖人工交互** | 轮廓法失败 → 降级到"弹窗让人点四个角"。在没鼠标/没显示的环境（**Jupyter、板上、CI、无人演示**）里 `cv2.namedWindow + waitKey` 会**一直等下去：不报错、不返回、日志一个字都没有**（实验被卡 10 分钟才发现） | 兜底路径进交互前**先判断环境**（`sys.stdin.isatty()` + `os.name=="nt" or $DISPLAY`），不能交互就**明确报错返回**，把原因交给上层。⚠️ 这类挂死最难查：**看起来像"程序在算"**，实际是在等人。凡是"降级到人工"的设计，都要问一句"无人值守时会怎样" |
| 114 | ⭐⭐⭐ **两份同名副本 + Python 的导入优先级 = 验证白做** | 改了 `src/ps/find_homography.py`（正本），本地跑 `board/pynq/rectify_board.py` 验证"通过"—— 其实它 `from find_homography import ...` 会**优先从脚本所在目录导入**，跑的是**部署副本那份旧代码**。验证结论完全无效 | 板子上必须是扁平目录（没有 `src/ps/`），所以副本无法避免；但**同步必须自动化、不能靠手敲 `cp`**（手敲还会把副本特有的文件头冲掉）。已做成 `build/make_package.py` 的确定性步骤。**验证前先确认"我改的那份，就是即将被执行的那份"** —— 一条 `grep 特征串 两份文件` 就能确认 |
| 115 | ⭐⭐⭐ **拿"与旧版的差异"当判据 = 拿一把有偏的尺子** | 做找四角提速时，只能报"新方法 vs 旧方法差 0.89~5.65 px"—— 这个数**既不能证明更好也不能证明更差**（旧版自己系统性外扩）。补了**真值判据**后结论反转：**我们上板用的旧方案才是最不准的**（对真值 1.70 px），新方案 0.89 px，**又快又准** | 判据必须是"**与真值/客观真值比**"，不是"与上一版比"。凡是"改算法"的优化，先问：**我有真值吗？** 本次的真值其实一直躺在代码里 —— `make_scene()` 本来就 `return img, quad`，只是调用处写成 `img, _ =` 丢掉了。⚠️ 另一面：**改算法后旧版不再是基准**，回归要用【判据不变】的项目（逐字节/客观指标），不能用"与旧版一致" |
| 116 | ⭐⭐⭐ **"真值"本身没定义清楚，会把真实差距掩盖掉** | 合成场景用 `polylines(..., 30, 3)` 画了 **3px 粗**的边框、且**骑在真值边界上** ⇒ "真值"有外沿/中心/内沿三种解释（差 ~3px）。结果三种检测器**全停在 ~3.5px 不动**，我一度误判成"某个偏差源没消除" | 造合成数据时，**真值必须是一个无歧义的位置**：边界要用**硬刃边**（亮暗直接相接、无中间层），内部纹理离边界留够距离。⚠️ 判断信号：如果**换了几种方法、误差都卡在同一个数上不动** —— 先怀疑尺子，别怀疑方法 |
