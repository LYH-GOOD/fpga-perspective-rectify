# 提示词工作流 · 按任务类型的专项模板

## 为什么有这一份

用大模型做 FPGA 工程，**通用套路**（怎么授权、怎么让它别乱改）已经有一份了。
但**具体某类技术任务该怎么问**，一直没有沉淀 —— 结果是同一个错误反复问、反复错：

- 问「帮我优化一下这个 kernel」→ 优化了一个只占整帧 **1%** 的东西；
- 问「这个数准吗」→ 拿到 **5.85 / 11.9 / 21.25 / 22.7** 四个互相矛盾的帧率，每个都能"自圆其说"；
- 问「这个开关打开了应该有效果吧」→ 那个开关**默认 `false`，从来没执行过**；
- 让 AI 加个检查 → 检查**永远通过**，因为它不区分「真的跑了」和「看起来跑了」。

**这五类任务的问法不一样，问错了返工以天计。** 下面每条都是一个能直接抄的模板。

## 每一项的四元组

| # | 模板 | 类型 | 适用范围 | 已验证的效果 | 失效条件 |
|---|---|---|---|---|---|
| 1 | 从算法描述推导**软硬件划分** | **通用** | 拿到一个新算法，要决定哪些放 PL、哪些留 PS | 按此切分后实测 PL 只占整帧 **1%**，据此**正确地**决定不优化 PL | 算法控制密集 / 数据相关分支多（本来就不适合 PL） |
| 2 | 根据**综合报告定位瓶颈** | **通用** | 综合/实现报告出来，要判断"该往哪使劲" | 一次问答排除掉「加宽 / 提频 / 压 a」三个方向，**省下一轮为期一周的重做** | 报告被截断（只贴 summary）；是 HLS 报告而非 Vivado 报告（格式完全不同） |
| 3 | 让它先把**判据做红** | **通用** | 让它新增任何检查 / 测试 / 校验脚本之前 | 抓到过「114 passed」其实两版测试文件逐字节相同的假绿；检查器误报从 448 条降到 0 | 缺陷无法人为制造（只在硬件上出现） |
| 4 | 让它报**口径**，不是报数 | **通用** | 任何"快了 / 慢了 / 提升了 N%"之前 | 四个矛盾帧率收敛成一个口径，跨版本比较第一次有意义 | 日志里没有累计计数器 ⇒ 先加一个 |
| 5 | 让它先证明**这条路径会跑到** | **通用** | 改开关 / 改一行"看起来在跑"的代码之前 | 发现一个开关**从没打开过**，一开就省 **76.75 ms/帧** | 纯初始化路径（每次启动必然执行一次） |

> **换题能不能用**：五个模板全部**与题目无关** —— 它们约束的是「怎么问」，不是「问什么算法」。
> **换板能不能用**：能。模板 1 换成任何「有硬件加速器的平台」都成立。
> **本文件不含**：通用协作套路（授权、防乱改、怎么攒记录）—— 那些在 P1 那份里。

## 模板 1 · 从算法描述推导软硬件划分

**什么时候用**：拿到一个新算法，要决定哪几步放 PL、哪几步留 PS。

```
这是算法的逐步描述：
<逐步写清楚每一步在做什么、输入输出多大、每帧要执行几次>
实时性要求：<每帧要在 XX ms 内完成，或 XX fps>

请给出 PS/PL 划分方案。要求：
1. 把每一步列成表，每行写：每帧执行次数 × 单次数据量
2. 每个候选分别估三件事：搬进 PL 要多久（DMA）、算要多久、搬出来要多久
3. 标出这一步是「每帧都跑」还是「只在启动时跑一次」
4. 最后给建议，并回答：如果这一步不搬，会损失什么？
不要一上来就说「放 PL 更快」——先给数。
```

**为什么这么问** —— 三条都是被实测打出来的：

| 现象 | 后果 |
|---|---|
| 不算「每帧几次」 | 有个候选被排到优化第一名，实际**每次启动只跑一次**（`find_paper_quad` 只在 `budget is None` 时调用），优化它一分钱不值 |
| 只算「算要多久」，不算 DMA | 掩膜 98 KB 若走 AXI-Lite 要 **24576 次事务**，必然拖垮帧率；大数据必须走 DMA |
| 不标「每帧 / 只启动一次」 | 同上 |

**本项目的实测结果**（可作为量级参照）：

| 项 | 实测 |
|---|---|
| PL 四角点 kernel，1024×768 | **65.5 ms** ⇒ 15.3 fps |
| PS 侧整套校正 | **12,590 ms** |
| ⇒ PL 占比 | **约 1%** |

**⇒ 结论：瓶颈在 PS，不在 PL。** 这个结论**只有把分母写出来才成立** —— 单看「65.5 ms」会以为 PL 很慢。

**失效条件**：算法里有大量数据相关分支、或需要不规则访存 ⇒ PL 会非常难写，这条模板的收益为负。此时应改成「先做 PS 版跑通，再考虑热点」。

## 模板 2 · 根据综合报告定位瓶颈

**什么时候用**：报告出来了，要知道**该往哪个方向使劲**、以及**哪个方向根本不值**。

```
这是 Vivado 的综合/实现报告：<报告路径或关键段>
请回答四个问题，**先不要给优化建议**：
1. 列出全部资源占用率，指出最接近 100% 的是哪一项
2. 时序违例的第一条路径是哪条？起点、终点分别是什么？
3. 如果要把当前设计加速 X 倍，哪一项资源会先爆？
4. 按「改一项要多久」给方向排序，并说明**每一项的理论上限是多少**
```

**为什么这么问**：不加「先别给建议」，AI 会直接列一堆优化手段，而**你不知道它列的是不是瓶颈**。

**本项目的实测结果**：

| 观察 | 结论 |
|---|---|
| BRAM **86.1%** / LUT **28.6%** | **约束是 BRAM 不是 LUT** —— 往 LUT 里塞东西是安全的，往 BRAM 里塞是危险的 |
| 且相机实测 **30.71 fps**〔2026-10-31 更正；旧记「24.0」是当时照度下的读数〕 | **资源占满也买不到帧率** —— 上限在相机不在 PL |
| m_axi 32→64 位 | 只降 **6.55%**、端到端 **0.33%** ⇒ 证伪「口宽瓶颈」 |
| 4.16 cycles/byte，比 II=1 慢 4.16×；**R²=1.00000** | 成本**纯粹按每像素线性增长** ⇒ 不是启动开销、不是边界效应 |

**这轮问答的真实收益**：把「加宽总线 / 提高时钟 / 压并行度」三个方向一次性排除，
**省下的是下一轮为期一周的重复实验** —— 因为这三条**每一条听起来都很对**。

**失效条件**：
- 报告只贴了 summary、没贴 utilization 表 ⇒ 模板 1、3 问不出东西
- 是 **HLS** 报告不是 Vivado 报告 ⇒ 顶层报告名是 `<top>_csynth.rpt`（**不是** `csynth.rpt`），列宽也不同，正则要重写

## 模板 3 · 让它先把判据做红

**什么时候用**：它要新增任何检查 / 测试 / 校验脚本 / 门禁之前。**无例外。**

```
你要加的这个检查，先证明它能判红：
1. 把<要检的缺陷>故意造出来一次，跑一遍，把输出贴给我
2. 再撤掉缺陷，跑一遍，把输出贴给我
3. 两次的输出必须不一样 —— 一样就说明这个检查是空转的
做完再往下走。
```

**为什么这么问** —— 空转门在本项目出现过**至少 5 次**：

| 案例 | 怎么空转的 |
|---|---|
| `114 passed` | 两版测试文件**逐字节相同**，测的是同一份代码 |
| HLS csim 反空转门 | 判据是「输出里有 `TB_FAIL`」，而两个方向都是 `TB_FAIL cannot open in.bin` |
| WNS 正则 | 正则写错 ⇒ 永远匹配上 ⇒ 永远判绿 |
| TB 的 C4/C5 | 检查项压根没接上被测信号 |
| 自查脚本悬空检查 | 判据不懂 BD 查询语义，报出 **76 条假阳性**，等于没有 |

**2026-10-22 一天之内抓到两个空转门** —— 这就是为什么它必须写在模板里，而不是靠记性。

**配套要求**（写检查脚本时一起提）：
```
判据必须区分「真的发生了」和「只是提到了」：
- 被回显的代码/提示文本，不算结果
- 解析不到 / 全 0，一律判红，不许默默当通过
- 「跳过 / 不适用」的分支必须打印出来，不许静默跳过还打 ✅
```

**失效条件**：缺陷无法人为制造（如只在硅片上出现、只在特定板卡上出现）。此时退而求其次：**要求它写出"如果这个检查是空转的，会出现什么现象"**，并把这个现象记进报告。

## 模板 4 · 让它报口径，不是报数

**什么时候用**：任何「快了 / 慢了 / 提升了 N%」之前。

```
报数之前先说清楚四件事，说不清就不要报：
1. 口径是什么 —— 具体到「哪一行日志的哪个计数器」
2. 分母是什么 —— 几帧 / 几次调用 / 几条线程
3. 系统饱和了吗 —— 如果不饱和，这个数分辨不出差异
4. 这一轮和上一轮是不是同口径
```

**为什么这么问**：本项目**同一天报过 5.85 / 11.9 / 21.25 / 22.7 四个帧率**，
每一个都能在自己的口径下自圆其说。根因是四个计数器各算各的（有一个还是"慢帧选择性采样"）。

**两个必须提醒 AI 的陷阱**：

| 陷阱 | 实测 |
|---|---|
| **台架耗时 ≠ 整机边际成本** | 同一段代码：台架 30.4 ms，整机边际 **66.1 ms**（2.2×） |
| **未饱和时 fps 没有分辨率** | 相机间隔 163 ms、处理只要 80 ms ⇒ **干得最多的那一版反而最快** |

**失效条件**：日志里没有累计计数器 ⇒ **先让它加一个**（成本约半小时），否则后面所有比较都不可比。

## 模板 5 · 让它先证明这条路径会跑到

**什么时候用**：改一个开关、改一行"看起来在跑"的代码之前。

```
在改之前先回答：
1. 这一行 / 这个开关，在当前配置下真的会被执行吗？给出判据。
2. 改完之后，日志里哪一行的哪个计数应该发生变化？变化多少？
3. 如果它没变，说明什么？
```

**为什么这么问** —— 本项目最贵的一次「根本没跑」：

| 现象 | 真相 |
|---|---|
| 花了一周优化 C 核 | `box` 参数**默认 `false`** ⇒ C 核**从来没被调用过** |
| 打开后 | 省 **76.75 ms/帧**，5.85 → ~10 fps |

同类的还有：
- 把日志开关设成 `0` 想关掉日志，而代码里是 `max(1, int(...))` ⇒ **想关反而全开**
- 改了一个"预算"参数，但内层用的是**另一套默认值**把它覆盖了 ⇒ 三档参数改下来 **fps 全是 23.3，一点没动**

**效果**：不看计数器就下结论，会得出「改了这个参数没用」的**完全错误的结论**。

**失效条件**：纯初始化路径（每次启动必然执行一次）—— 这类不需要问，但也不该拿它当性能瓶颈。

## 反模式：本队实际踩过的问法

| 反模式 | 实际后果 | 改成 |
|---|---|---|
| 「帮我优化一下这个 kernel」 | 优化了一个只占整帧 **1%** 的东西 | 先走模板 1，问「瓶颈在哪一段、占多少」 |
| 「这个数准吗」 | 得到四个互相矛盾的帧率 | 走模板 4，先定口径 |
| 「这里应该没问题吧」 | AI 会顺着你说"没问题" | 走模板 5，要判据 |
| 「从没做过吧？」 | AI 会附和"对，没做过" —— 而 3 小时前刚跑过 | 先让它**搜三处证据**再说 |
| 「两个版本差多少」 | 不说口径 ⇒ 5.85 vs 22.7 这种比较 | 走模板 4 |
| 只贴报错最后一行 | 缺上下文，方向猜错 | 贴完整输出 + 什么操作触发的 |

## 来源验证

| 模板 | 从哪些失败/观察总结 | 怎么验证有效 |
|---|---|---|
| 1 软硬件划分 | PL 65.5 ms 被误当成"很慢"；「mask 前端搬 PL」被排第一而它只在启动跑；C 核因默认 `false` 从未执行 | 把分母写出来后，PL 只占 **1%** ⇒ 决策由"优化 PL"改为"不动 PL" |
| 2 综合报告定位 | 三个"听起来都对"的方向（加宽/提频/压并行）实际全无效 | 加宽实测只降 6.55%、端到端 0.33%；R²=1.00000 证明成本纯每像素 |
| 3 判据做红 | 一天抓到两个空转门；`114 passed` 是逐字节相同的假绿；自查脚本 76 条假阳性 | 每个检查器都做一次「造缺陷 → 必须红 → 撤掉 → 必须绿」 |
| 4 报口径 | 一天四个帧率；台架 30.4 vs 边际 66.1；未饱和时干得最多的反而最快 | 改用单一累计计数器斜率并切段后，跨版本比较才成立 |
| 5 路径可达 | 开关默认 false ⇒ 一周白干；`max(1,…)` 把"关"翻成"开"；内层默认值覆盖外层预算 ⇒ 三档全 23.3 | 打开开关实测省 76.75 ms/帧；改内层后尾巴砍 45% |

> **共同点**：五个模板**没有一个是想出来的** —— 每一个都对应一次以天计的真实返工，
> 而且都能指向一个具体的、可复现的实测数字。
