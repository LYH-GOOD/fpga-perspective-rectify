# 测量与对照

## 为什么有这一份

**[14-coding-pitfalls](14-coding-pitfalls.md) 讲「怎么写得对」，[12-verification-before-completion](12-verification-before-completion.md) 讲「能不能验收」——
但没讲「怎么量得对」。** 本项目约 16 条事故属于同一类：**代码没错、也没崩，是我量的那个数根本不是我以为的数。**

代价以「天」计：2026-10-29 一天之内报过 `5.85 / 11.9 / 21.25 / 22.7` 四个互相矛盾的帧率；
「把 mask 前端搬 PL」被排成性能优化第一名，实际那条路径只在启动时跑；
按「3 次/帧」估出来的收益比实测大了 15 倍。

## 每一项的四元组

| 项 | 类型 | 适用范围（什么时候读） | 已验证的效果 | 失效条件 |
|---|---|---|---|---|
| M1–M12 | **通用** | 任何**拿数据做决策**的项目；说「快了 / 慢了 / 提升了 N%」之前 | 同一套口径把一天四个矛盾帧率收敛成一个数；此后所有跨版本比较都只用这一条 | 日志里**没有**累计计数器时（M1 需要换成该项目的等价物） |
| 三个实例 | **通用** | 想确认这些规矩不是空话时 | 每个实例都对应一次真实的、以天计的返工 | 无 |
| 「这个数能不能信」6 问 | **通用** | 任何数字进报告之前 | — | 无 |

> **换题能不能用**：能。这一份**不含**任何本项目的算法内容，讲的全是「怎么量才不被骗」。
> **换板能不能用**：能。PC / 板卡 / 云端都适用。
> **本文件不含**：具体某个函数该怎么优化 —— 那是领域层的事。

## 什么时候用

- 要**说「快了 / 慢了 / 提升了 N%」**之前 —— 无例外
- 要**做 A/B**（开/关一个开关、两个版本、两块板）
- 要**拆阶段耗时**、画成本占比
- 要**外推**（这个尺寸 → 那个尺寸、PC → 板、单帧 → 整机）
- 要**引用一个历史数字**（哪怕是自己上周测的）

## M 组：12 条规矩

| # | 规矩 | 失效条件 | 为什么（全部实测栽过） |
|---|---|---|---|
| M1 | **一次比较只能有一个口径，且要写下来** | 日志里没有累计计数器 ⇒ 先加一个，或换等价的累计量 | 本项目 fps 有四个口径（`V64_FRAME` / `current_fps` / `hdmi_submit_fps` / `hdmi_panel_fps`），**四个都不能用**。唯一可用的是 `HDMI_PROGRESS.frames` **累计值的斜率**，且必须在 `frames` **回退处切成段**。2026-10-29 一天踩四次 |
| M2 | **分母写清楚：几条线程、几帧、几次调用** | 无 | 「mask 段占 59.8%」的分母如果是多线程，倍数会从 37× 飘到 132×。分母不写，这个百分数就是不可比的 |
| M3 | **台架耗时 ≠ 整机边际成本** | 系统未饱和时两者差别更大，此时**只能用整机口径**（见 M4） | 同一段代码：台架 **30.4 ms**，整机边际 **66.1 ms**（**2.2×**）。只认「改开关、跑两趟整机、比 fps」，且必须 OFF/ON/OFF/ON 交错 |
| M4 | **fps 只在饱和时有分辨率** | ⚠️ **处理快于取帧间隔时（未饱和），fps 分辨不出差异** —— 这时「没变化」不代表「没效果」 | 相机间隔 163 ms、处理只要 80 ms ⇒ **干得最多的那一版反而最快** |
| M5 | **交错 + 轮转，不许「先跑完 A 再跑 B」** | 只能跑一次的长时实验 —— 此时应改用**过程内分段**而非 A/B | 顺序跑会把布局、缓存、热漂移全混进差值。正确做法：OFF/ON/OFF/ON 交错多轮，**取配对差** |
| M6 | **配对差取中位；但整本账只能用「均值」闭合** | 无 | **中位数不可加**。曾用中位数逐段相加，虚报出一个 10.5 ms 的"黑洞"，查了半天发现是加法本身错的 |
| M7 | **不做跨架构倍率外推** | 两边环境变量全部隔离、且各测一遍之后，倍率才有意义 | 板 vs PC 量到过 **29.3×**、**54.7×** —— 两次分母不同（混库版本变量未分离）。倍数本身不可移植 |
| M8 | **任何投影乘数必须当场标成「假设」** | 无 | 「R64 每帧 3 次」是假设，实际 **0.05 次/帧**（差 15 倍），据此排的优化优先级整条作废；「82 ms」也是假设乘数投影出来的 |
| M9 | **两版结果一致 ≠ 正确；两趟基线差很多 ≠ 可比较** | 无 | v7/v9 在真机上"多数帧一致"，但两版各有独有的翻车帧；另一次两趟 OFF 之间差 4 倍 ⇒ 端到端 A/B **直接判定为不可做**，不是"再跑一次看看" |
| M10 | **阴性结果必须写下来** | 无 | m_axi 加宽 32→64：只降 6.55%、端到端 0.33%；PL 锐化旁路：只省 0.9 ms/帧。不记，下一个人（包括未来的你）会再花一周重做一遍 |
| M11 | **两份日志 ≠ 前后对照** | 两份日志起始时间不同、且各有独立启动标记时，才可当对照 | 交接包里的 `log2` 是 `log1` 的**前缀续写**，不是两次独立实验。先验「它们是不是重叠的」，再谈差异 |
| M12 | **自指的统计会被测量动作本身改变** | 测量动作不影响被测量时（如离线数已归档的文件） | 数目录文件数、数日志行数——**你自己写日志就会改它**。这类量只写「清单在哪个脚本里验」，**不记具体数字** |

## 一张表：这个数能不能信

问完这 6 句再往报告里写：

| 问 | 不合格的样子 |
|---|---|
| ① 口径是什么？写下来了吗？ | 「帧率 21」——哪个帧率？ |
| ② 分母是什么？ | 「占 60%」——谁的 60%？几条线程？ |
| ③ 饱和了吗？ | 处理 80 ms、间隔 163 ms，却拿 fps 比处理时间 |
| ④ 交错跑了吗？跑了几轮？ | A 跑完再跑 B，一轮定论 |
| ⑤ 这个数是我刚测的，还是引的旧结论？ | 引用上周的数字，而配置早改了 |
| ⑥ 有没有可能是「没跑到」而不是「没效果」？ | 开关默认 false，改完没看计数器（见 [14](14-coding-pitfalls.md) 的 I 组） |

**六条里任何一条答不上来，这个数就只能当「印象」，不能进结论。**

## 三个最贵的实例

### 例 1 · 一天四个帧率（M1）

同一天先后报出 `5.85`、`11.9`、`21.25`、`22.7` 四个数，每一个都能在自己的口径下"自圆其说"。
根因：`V64_FRAME` 是**慢帧选择性采样**、`current_fps` 是瞬时值、`hdmi_submit_fps` 与 `hdmi_panel_fps` 各算各的。

**正确做法**：

```python
# 只此一条：HDMI_PROGRESS.frames 的累计值，在回退处切段
segs, cur = [], []
for t, n in rows:              # t=时间戳, n=HDMI_PROGRESS.frames
    if cur and n < cur[-1][1]: # frames 回退 ⇒ 新的一段
        segs.append(cur); cur = []
    cur.append((t, n))
segs.append(cur)
fps = [(len(s) - 1) / (s[-1][0] - s[0][0]) for s in segs if len(s) > 1]
```

### 例 2 · 优化了"不是瓶颈的那一段"（M3 + M4）

把 PL 侧砍到 1/4，fps 只从 23.2 涨到 25.2 —— 因为 **`prep_wait` 反涨 4.71 ms**。
瓶颈一旦低于 `ps_prepare_s`，它就换人了。**优化之前先确认"现在谁最慢"，优化之后重新确认一遍。**

### 例 3 · 假设乘数造成的 15 倍误差（M8）

「R64 每帧调用 3 次」写进方案时没有任何标注，据此算出"合并能省很多"。
实测 **0.05 次/帧、1.17 ms/帧** ⇒ 合并只值 **0.4 ms/帧**。

**规矩**：投影里每一个不是当场测出来的数，**原样标 `[假设]`**，并在拿到实测值后回头划掉。

## 落盘要求

按本项目的单文件报告规矩（[14](14-coding-pitfalls.md) H 组）：

- 计时脚本必须把**每次运行的原始行**写进报告（不是只写均值）
- 报告头写死：时间 / 主机 / 脚本 sha16 / **本轮的口径是什么**
- **阴性结果也要进报告**，不能只在对话里说一句
- 一轮实验的**假设清单**要和结果放同一份报告里，否则下一个人分不清哪个数是测的、哪个是猜的
