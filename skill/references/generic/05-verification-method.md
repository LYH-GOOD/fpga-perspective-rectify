# 通用技能 ⑤：验证方法论

> **适用范围**：任何有"黄金参考"的硬件/嵌入式设计（RTL、HLS、DSP、驱动）。
> **与具体题目无关** —— 讲的是"怎么设计判据、怎么构造用例、怎么证明修好了"。
>
> **失效条件**：没有可比对参考的系统（纯探索性原型）用不上。

---

## 为什么这一篇最重要

本项目**一共出过 3 个"上板才暴露"的 bug**，而它们的共同点是：

> **全都通过了当时存在的全部测试。**

分别是：

| bug | 表现 | 为什么躲过了所有测试 |
|---|---|---|
| 行计数少算半行 | 第 0 行部分像素错 57 灰阶 | 只在"核刚开工、顶在写前沿"这个**边界**暴露 |
| 流控下界取错端 | 下半个图拖影 | 只在**文档有旋转**时才触发；旧测试用的图都是正放的 |
| 帧末不排空 | DMA 永久挂起 | 只在**输入没被吃光**时触发；旧测试的输入恰好都被吃完 |

**三个都是"边界条件"，三个都"恰好"没被覆盖。**

所以这一篇不讲"要写测试"（那是废话），讲**判据怎么设计才不会漏**。

## 一、判据：把"信号"和"噪声"分开

### 踩过的坑

判据原来是"与 OpenCV 参考的最大差异 ≤ 1 灰阶"——
**这个判据永远不可能满足**，因为定点运算和浮点运算在高对比度边缘上
必然有 1~3 灰阶的固有舍入差。

后果：真 bug（差异 57）和固有舍入（差异 3）**混在同一个数字里**，
只能靠人肉判断"57 是不是有点大"。**一个永远差一点的判据，等于没有判据。**

### 正确做法：双参考，各管一件事

| 参考 | 回答的问题 | 判据 |
|---|---|---|
| **逐位定点模型** | **实现对不对** | **必须 = 0**（逐字节一致）|
| 浮点/OpenCV 参考 | **效果好不好** | 只看趋势 |

```python
d_fixed = |FPGA输出 - 定点模型|      # 判据：必须 0
d_cv    = |FPGA输出 - OpenCV|        # 参考：1~3 灰阶正常
```

> ⭐ **通用原则**：判据要能把"实现错误"和"固有误差"分开。
> 拿一个"永远差一点点"的东西当判据，只会让所有人学会忽略它。

**怎么做逐位模型**：拿 RTL 的算法写成 Python 逐位复刻（同样的整数位宽、
同样的截断方式、同样的舍入）。本项目叫 `golden_remap_fixed()`，
**与真实 RTL 仿真逐字节一致**，这是它能当判据的前提。

## 二、用例：要"必然触发"，不要"碰运气"

### 反面教材

"我再跑一遍真实数据看看" —— 这是**碰运气**。上面 3 个 bug 就是靠这种方式漏掉的。

### 正确做法：**写出判据，再按判据反推参数**

本项目的例子（流控下界那个 bug）：

1. 先解析推出：**出错条件 = 极值行 + 缓冲深度 < 总行数**
2. 按这个条件**构造一个小尺寸 TB**：
   "输出只覆盖图的上半部分、输入给整张、缓冲深度刚好不够"
3. 结果：修复前 **FAIL（精确复现）**，修复后 **PASS**

```
输入 48 行，输出只 24 行，缓冲深度 16
→ 最后一行需要的 y + 16 = 39 < 48  ← 必然触发
```

### 边界清单（照着过一遍）

| 边界 | 为什么 |
|---|---|
| **第 0 行 / 第 0 帧 / 复位后第一次** | race 高发区。本项目 2 个 bug 都在这 |
| **输入刚好够 / 刚好不够** | 流控的临界 |
| **连续多次操作**（第 2、3 次） | 有内部状态的系统，第二次是**全新场景** |
| **反压**（下游 ready 周期性拉低）| `ready` 恒高 = 没测反压 |
| **参数取极值**（最大/最小尺寸、最大旋转）| 小尺寸测试覆盖不到大尺寸的行为 |

## 三、修好了怎么证明：**把修复撤掉，看能不能复现**

这是本项目最有效的一条纪律。

```
改完 → 跑测试通过   ← 这只能说明"没坏"，不能说明"修对了"
```

**要做的是反向验证**：

```bash
# 1. 撤掉修复
sed -i 's/新逻辑/旧逻辑/' rtl/xxx.v
# 2. 跑同一个用例 → 必须 FAIL，而且症状要和上板现象对得上
# 3. 恢复修复 → 必须 PASS
```

本项目的三次应用，效果都很直接：

| bug | 撤掉修复后 | 与上板现象 |
|---|---|---|
| 行计数 | 280 个像素错，**全在第 0 行**，最大 60 灰阶 | 上板是"第 0 行、57 灰阶" ✓ 对上 |
| 流控下界 | 出错行 510~758 | 解析预测 494~803 ✓ 对上 |
| 帧末排空 | 输入只被吃 38/48 行 | 上板"DMA 挂起 + 核空闲" ✓ 对上 |

> ⭐ **"修复前后症状一致"才是真定位**。如果撤掉修复复现不出上板现象，
> 说明你找到的是**另一个** bug，或者只是掩盖了它。

## 四、自检：**同样的输入跑两次，结果必须逐字节相同**

一句话的成本，能抓住一整类 bug（"帧间状态没清干净"）。

```python
if not np.array_equal(out_run1, out_run2):
    raise RuntimeError("多次运行结果不一致 → 状态没复位")
```

本项目靠它当场发现了"核是单帧设计、第二帧起全错"。
**有内部状态的加速器都值得加这一条。**

---

## 五、能在仿真里做的 A/B，别拿到板上试

| | 仿真 | 上板 |
|---|---|---|
| 一轮耗时 | **30 秒** | 10 分钟 + 占用队友时间 |
| 能看波形 | ✅ | ❌ |
| 能撤掉修复做对比 | ✅ | 要重出比特流 |

**能用仿真的场合**：
- "这个修复到底有没有用" → 仿真里改一行重跑
- "A 方案和 B 方案哪个对" → 仿真里各跑一遍
- "错误率的量级对不对" → 见下

**错误的量级本身可以当指纹**：
本项目实测"仿真里 96% 像素错 / 板上 85% 像素错" —— **同一个根因**。
量级接近就说明根因相同，不必追求数字完全一致（板上还有 DMA 反压等仿真没建模的因素）。

## 六、⚠️ 测量会改变被测量的对象

**这是本项目最贵的一个教训。**

"给上板脚本加个性能计时"看起来无害，但它顺带让核**连跑了 4 帧** ——
而核是单帧设计，第二帧起全错。**上一版（跑一帧）明明是好的。**

```python
# 加测量前
run_fpga(...)                      # 跑 1 次
# 加测量后
for i in range(4): run_fpga(...)   # 跑 4 次 ← 改变了被测对象的工作条件
```

> ⭐ **加任何测量手段之前，先问一句："它会不会改变被测对象的状态？"**
> **重复执行 ≠ 执行多次同样的操作** —— 对有状态的系统，每次执行都是新场景。

**推论**：`--repeat` 这类"多跑几次取中位数"的选项，**默认值要选"已经验证过的那条路"**
（本项目最后把默认从 3 改成 0），风险路径要显式 opt-in。

---

## 七、改了**上游**必须复验**下游**

本项目的一次实例：改了"输出尺寸怎么决定"（用度量校正替代边长法）→
输出尺寸变了 → `DMA 传输长度必须是 4 的倍数`这个下游约束可能被破坏 →
**必须把全套回归重跑一遍**。

> 判据：**这次改动会不会影响别的模块的输入？** 会 → 全套回归。

---

## 八、交付前：顺手算一遍"下一轮会不会挂"

本项目的实例：修完队友报的 DMA 长度问题，顺手离线算了"三张照片各需要多深的行缓存"
—— 发现其中一张需要 166 行而硬件只有 64，**下一轮必挂**。一并修掉了。

> **修一个 bug 时，顺手检查相邻的约束。** 能省一轮来回（上板一轮 = 10 分钟 + 队友时间）。

## 十、⭐⭐ 判据要能看见"**多余**"，不只是"够不够"（2026-09-29）

**这是本项目最贵的一条教训（省下了很多轮板子）。**

### 现象
多帧连跑在板上挂死。查出来是：核在帧末会**多吐出几个像素**，
而且每个都带着过期的 `tlast` ⇒ 污染下一个传输。

### 为什么原来的测试**看不见**它
TB 的收数逻辑是"**收满 N 个就切窗口**"：

```verilog
while (n_rec < nfr + N_OUT) @(posedge aclk);   // 收满就停
// 然后下一帧：nfr = n_rec
```

**⇒ 多出来的像素会被算进【下一帧的窗口】⇒ 帧数据整体挪位但数量"正好" ⇒ 看起来还是对的** ✗

### 修法：加一条"帧间不许有输出"的检查

```verilog
// 本帧收满之后，再多等一段，看有没有多余像素冒出来
extra = 0;
repeat (400) begin
    @(posedge aclk);
    if (n_rec > nfr + N_OUT) extra = n_rec - (nfr + N_OUT);
end
$display("帧 %0d 收满后多等 400 拍：多出的像素 = %0d", nf+1, extra);
```

**⇒ 当场复现（54 个）** ⇒ **上板挂死变成本地可复现的问题，后续调试只花了一轮板子。**

> ⭐ **通用形式**：凡是"流式产出 N 个"的模块，判据都要问两句 ——
> **"够不够"** 和 **"有没有多"**。
> 只查前者，多余的产出会被下游当成正常数据吃掉，**而症状会出现在很远的地方**。

## 十一、⭐ 改了之后症状没变 —— 先验证"改的那份真的被执行了"（2026-09-29）

**这是"静默失败"的典型**：改完 RTL、重出比特流、重跑 —— **症状一模一样**。
此时有两种解释，且**必须区分**：

| 解释 | 对策 |
|---|---|
| (a) 修复无效 | 继续分析 |
| (b) **改的那份根本没被执行** | 先解决交付/同步 |

**本项目踩过 3 次**（RTL 没上板 / IP 仓库旧缓存 / 交付包副本漂移）。**每次都能一眼定案的手段**：

| 手段 | 说明 |
|---|---|
| ⭐ **版本寄存器** | RTL 每次实质改动就 `VERSION_MINOR +1`，程序启动时打出来 ⇒ **最便宜、最早生效** |
| **文件指纹自检** | 打包时把 `system.bit/.hwh/.py` 的 md5 **烤进 notebook**，板上重算并自动比对 |
| **全目录快照** | 把板上**每个文件的大小 + md5** 都打进日志 ⇒ **事后任何"文件对不对"的问题都能回答**，不需要提前预知要看什么 |

> ⭐ **一句话**：**"跑通了"和"改的那份跑了"是两件事。**
> 尤其在失败是**静默**的时候 —— 症状不变既可能是修复无效，也可能是修复压根没上板。

## 九、来源与验证

| 做法 | 从哪个失败总结 | 验证 |
|---|---|---|
| 双参考判据 | "最大差异 ≤1"永远不满足，真 bug 被淹没 | 改用定点模型当判据后，3 个 bug 全部显形 |
| 按判据反推用例 | 3 个 bug 都躲过了既有测试 | 新构造的 TB 在修复前 FAIL、修复后 PASS |
| 撤掉修复验证 | — | 3 次应用，症状全部与上板现象对上 |
| 两次运行一致性自检 | 核第二帧起全错 | 当场发现 |
| 测量会改变被测对象 | 加计时后连跑 4 帧全错 | 改回单帧后恢复正常 |
| 改上游复验下游 | 输出尺寸改变 | 全套回归重跑 |
| **判据要能看见"多余"** | 帧末多余 beat 在板上挂死，本地测试看不见 | 加检查后当场复现 54 个 ⇒ 后续调试只花一轮板子 |

| **§十一 从真实源码抽出被测对象** | 改了一个并发队列，不想整机上板试错 | 主机单测证明 depth=1 命中 0%、depth=2 命中 92%，与板上 14% 同量级 |

## 十一、⭐⭐ 2026-10-31：**从真实源码里把被测对象"抠出来"做主机单测**

> 场景：要改一个**并发**模块（生产者/消费者队列），改错的代价是上板跑一轮才发现卡死或顺序错。
> 但整机依赖太多（硬件、摄像头、显示），没法在主机上跑起来。

### 做法：用 `ast` 只抽出那一个类，注入替身依赖

```python
import ast
tree = ast.parse(open(SRC, encoding='utf-8').read())
node = next(n for n in tree.body if isinstance(n, ast.ClassDef) and n.name == 'PrepareQueue')
mod  = ast.Module(body=[node], type_ignores=[])
ns   = dict(threading=threading, time=time, copy_context=contextvars.copy_context,
            _bind_cpu=lambda name: None, UIReturnRequested=UIReturnRequested, os=os)
exec(compile(mod, '<PrepareQueue>', 'exec'), ns)      # ← 跑的是【真实源码】，不是抄一份
PrepareQueue = ns['PrepareQueue']
```

**为什么要 `ast` 而不是复制一份**：抄一份就只能验证"我抄对了吗"，**验证不了仓库里那份**。
`ast` 抽出来的就是仓库里正在用的代码，改一次测一次。

**替身（假 frontend）要能暴露时序**，不能只返回固定值：

```python
class Frontend:
    def prepare(self, index):
        time.sleep(0.020)        # 模拟真实耗时
        return Item(index)
```

**判据要直接对应"你要证明的那件事"**——本例要证明的是
"生产者能不能提前 2 帧"，于是测的是**"在第 10 ms 处 `peek()` 是否非空"**：

| 配置 | 每帧第 10 ms 处能取到下一帧吗 |
|---|---|
| depth=1 | `n n n n n n n n n n n n` → **0%** |
| depth=2 | `n Y Y Y Y Y Y Y Y Y Y Y` → **92%** |

**⭐ 这个 0% 与板上实测的 14% 同量级** ⇒ 模型抓住了真机制，不是自说自话。

### 三条配套判据（每次都要一起测）

1. **顺序**：`take()` 返回的 index 必须是 1,2,3,…（并发下最容易乱）
2. **清理**：`close()` 之后所有资源都要释放（本例检查每个 item 的 `released`）
3. **存活**：worker 线程必须退出、`error` 为 None、队列为空

> ⚠️ 主机测试**只能验正确性和时序逻辑**，凡是"快多少"的结论一律标未验证
> （见 `07-measurement-discipline.md` §10.4：x86 测不出 ARM 的 64 位除法代价）。
