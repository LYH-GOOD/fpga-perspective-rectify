# 通用技能 ①：流式握手与流控

> **适用范围**：任何带 `valid`/`ready` 握手的流式设计（AXI-Stream、Avalon-ST、自研流接口、
> FIFO 前后级、DMA 上下游）。**与具体题目无关。**
>
> **失效条件**：纯 AXI-Lite 寄存器访问、无流式数据通路的设计用不上。

---

## 为什么单独立一篇

本项目**上板出过 3 次错误，根因全部在这一篇覆盖的范围内**，而且
**3 次都躲过了全套小尺寸仿真**：

| 上板现象 | 根因 | 详见 |
|---|---|---|
| 输出图**整体错位一格** | 控制脉冲做成了寄存输出，比状态晚一拍（坑 8/9/10） | 本项目 `llm_log/2026-09-26_pl_streaming_core.md` |
| **下半个图拖影** | 流控下界在"行首"取，但最小值在"行尾"（坑 60） | `llm_log/2026-09-27_rotated_doc_smear_bug.md` |
| **DMA 永久挂起**（核却空闲） | 帧末对上游"关闸"，输入排不空（坑 79/80） | `llm_log/2026-09-27_input_drain_bug.md` |

**共同点**：都是"流量控制的边界条件错了"，而不是算法错。

## 一、四条铁律（照着写就不会出上面那些问题）

### 铁律 1：由状态直接决定的脉冲，必须**组合**驱动

```verilog
// ❌ 错：寄存输出 → 比 state 晚一拍
always @(posedge clk) if (state == S_LOAD) pulse <= 1'b1;
                            // 下游收到时，state 已经走到别处了

// ✅ 对：组合驱动
assign pulse = (state == S_LOAD);
```

**症状**：数据整体错位一个像素 / 一个节拍。**仿真可能侥幸对（last-write-wins），
综合后一定错。**

### 铁律 2：BRAM 的**使能和地址必须同拍**给出

同步读 BRAM 的语义是"时钟沿采样地址，下一拍出数据"。
如果把 `rd_en` 或地址做成寄存输出，地址就比预期晚一拍呈现 → 取到隔壁的数据。

```verilog
// ✅ 组合给出地址与使能，数据下一拍抓
always @(*) begin
    rd_en = (state == S_RD0);
    rd_addr = addr_r;
end
always @(posedge clk) if (state == S_RD1) data_r <= rd_data;   // 下一拍抓
```

**症状**：四个邻域像素整体错位一格，第一个还是陈旧值。

### 铁律 3：流控的**下界**和**上界**都要想清楚

流式架构的流控本质是"我还没用完的数据，你不能覆盖"。写成代码就是两个比较：

```verilog
// 上界（防饿死）：我需要的行，写侧到了没有
wire ok = (written > needed_max);

// 下界（防覆盖）：我要用的最老的那行，被覆盖了没有
assign in_ready = (written < needed_min + DEPTH);
```

**两个坑**：

**(a) 减法会回绕** —— 千万别写 `(written - needed_min) < DEPTH`：
当 `needed_min > written` 时它会回绕成大正数，输入被永久堵死。
**用加宽比较**：`(written_ext < needed_min_ext + DEPTH)`。

**(b) "下界"必须对本行的整个区间成立** —— 这是最阴的一个坑。
若"最小值"在行的**末端**，而你在**行首**就把它报给流控，
中间那一段流控就是**过度放行**的 → 覆盖还要用的数据。

```verilog
// ❌ 行首直接用当前值（它可能不是本行的最小值）
if (u == 0) lo <= cur;

// ✅ 用"上一行末端的值"做保守下界（若极值在行尾）
if (u == 0) lo <= (cur < prev_last) ? cur : prev_last;
```

**症状**：**画面的一部分出现拖影/重影，其余正常**。
判据可以精确算出来：`极值位置 + DEPTH < 总行数` 时才会踩 —— 所以
**同一份代码，有的输入过、有的输入挂**，最容易被误判成"偶发"。

### 铁律 4：**不允许对上游"关闸"**

反压只能用来**节流**（短时间），不能用来**断流**（永久）。

**本项目踩的原型**：处理完一帧后状态机回到 IDLE，而 IDLE 把流控下界清零了
→ `ready` 立刻变假 → **上游 DMA 永远等不到 tready → 永久挂起**。

而核自己的状态寄存器显示 `busy=0 / stuck=0 / 帧计数=1` —— 看起来"一切正常"。

```verilog
// ✅ 帧产出完毕后，输入必须能继续排空
assign in_ready = frame_done_seen || ((state != S_INIT) && (wr < lo + DEPTH));
```

> ⚠️ **视频阶段这是必踩的**：输入是连续流，没有"传输结束"这回事，
> 每帧关一次闸 = 每帧丢一次数据。

---

### 铁律 5：**帧边界的"开工条件"必须显式包含"本帧是否已开工"**

**只要状态机在一个帧里会被"复用"（一帧内多次进出同一个态），开工条件就不能只看"准备好了"。**

**真实原型**（`2026-09-30_multiframe_cfg_bug`）：

```verilog
// ❌ 帧末 A 一进 A_IDLE 就满足条件，立刻又跳 A_RL ⇒ 多跑一次 row_load
if (frame_req && rows_written > ROW0) a_state <= A_RL;

// ✅ 加一个"本帧是否已开工"的状态位
if (frame_req && frame_started && rows_written > ROW0) a_state <= A_RL;
```

`frame_started` 的定义：**"从最近一次【帧首】以来，这个子状态机还没开过工"**
—— **帧首置 1，一开工清 0**。

**为什么单帧测试抓不到**：

| 测试方式 | 结果 |
|---|---|
| **单帧** | ✅ 正常 —— 帧末就直接结束了，**没有"下一帧还在同一个态"这回事** |
| **多帧连跑** | ❌ 多一次 load ⇒ 数据错位/计数不对 |

> ⚠️ **这正是"进程模型掩盖 bug"的一个特例**（`08-mechanical-guards.md` §四）：
> **单帧一个进程** 会把帧间残留状态全部清掉 ⇒ **必须用"长驻进程连跑多帧"来测**。
>
> 💡 **写状态机时的自检问题**：
> **"这个态在一帧里会被进几次？"** —— 如果答案是"可能多次"，
> 那**每一个跳出条件都要带上"本帧是否已经做过这件事"**。

## 二、上板出错时的"分诊表"

按**状态寄存器**快速定位，不要瞎猜：

| 现场 | 含义 | 查哪里 |
|---|---|---|
| `busy=1` 且一直不结束 | 核在等一个到不了的输入 | 流控下界是否太紧 / DEPTH 是否够 |
| `busy=0 stuck=0` 但任务没完成 | **上游被堵**（关闸了）| `ready` 的表达式，尤其是帧边界 |
| 输出整体错位一格 | 控制脉冲滞后 | 铁律 1 / 2 |
| 只有部分区域错（拖影、条带）| 流控下界取值时机不对 | 铁律 3(b) |
| 第一行/第一次特别容易错 | 边界 race | 见 `05-verification-method.md` |

> ⭐ **`busy=0` 而任务没完成，是最容易被误判的一种**：
> 第一反应是"核坏了"，实际是"上游被堵"。**看到这个组合先查握手，别查核内部。**

## 三、怎么在仿真里验证这些（不必上板试）

这几条**全都能在仿真里复现**，而且**必须构造"必然触发"的用例**，
不能指望"再跑一遍真数据碰运气"：

| 要验的 | 怎么构造用例 |
|---|---|
| 流控下界取值时机 | 按判据反推参数：让极值位于行的**末端**，且 `DEPTH` 刚好接近跨度 |
| 帧末排空 | **输入比核需要的多**：输出只覆盖图的上半部分，输入给整张 |
| 组合/寄存脉冲 | 在 TB 里对比"输出与期望是否整体错位一格" |
| 反压 | TB 里让下游 `ready` **周期性拉低**（不是恒高！）|

> ⚠️ **本项目的教训**：最初所有 TB 的下游 `ready` 都是**恒高**，
> 于是"反压时坐标多推几拍"这个 bug 一直没被发现。
> **`ready` 恒高 = 没测反压。**
