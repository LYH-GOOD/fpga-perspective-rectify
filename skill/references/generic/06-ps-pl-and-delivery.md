# 通用技能 ⑥：PS/PL 协同与交付工程

> **适用范围**：PS（跑 Linux/Python）+ PL（FPGA 逻辑）协同的项目，尤其是
> **要把成果交给别人去板子上跑**的场景。
> **失效条件**：纯 PL、或只有自己一个人用的项目。

---

## 一、⭐ 交付物在别人机器上坏掉，是**最高频**的事故

本项目**在队友那边连坏 4 次**，没有一次是算法问题：

| # | 现象 | 根因 | 教训 |
|---|---|---|---|
| 1 | PYNQ 找不到 DMA | BD 里 DMA 控制口悬空（见 `04-axi-dma-and-bd.md`）| 交付前**在干净环境实测** |
| 2 | `Transfer size exceeds 16383` | DMA 长度默认值 | 默认值按**演示规模**校验 |
| 3 | `board_compare.png` 没生成 | 第一张就挂了，后面全跳过 | 脚本要**继续**而不是中断 |
| 4 | `sim` 跑不起来 | 交付包目录布局≠仓库，脚本硬编码路径 | 脚本**布局自适应** |

### 一条硬纪律：**在"干净解压"目录里重跑一遍**

```bash
rm -rf /tmp/verify && mkdir -p /tmp/verify
cd /tmp/verify && unzip -q P1.zip && cd P1
bash sim/run_sim.sh          # 全套仿真
bash sim/run_board_cfg.sh    # 上板配置一致性检查
```

> ⭐ **不是"在仓库里跑一遍"，而是"从压缩包解出来、在一个全新的目录里跑"。**
> 本项目靠这一步抓出了"向量生成步骤漏了一个脚本、靠残留文件假装通过"。

## 二、⭐ 跨平台的参数默认值必须对齐

**本项目最隐蔽的一个 bug**：

同一份算法，**PC 端脚本默认"自动推算尺寸"，板端脚本默认"写死 320×240"**。
结果：PC 上验证的一切都正常，**板上的图被纵向拉伸 32%**，而且**长期没人发现**
（因为大家只在 PC 上做质量评估）。

```python
# PC 端
ap.add_argument("--w-out", type=int, default=0)   # 0 = 自动
# 板端
ap.add_argument("--w-out", type=int, default=320) # ← 写死！两边行为分叉
```

> ⭐ **"PC 上验证过了" ≠ "板端行为一致"** —— 参数路径不同就等于没验证。
> **交付前把两端的默认值逐项对一遍。**

**延伸**：如果关键约束的**警告**写在一个端、**坑**踩在另一个端（本项目就是：
"写死尺寸会压扁"的警告写在 PC 端的函数注释里，而坑踩在板端），
那这个警告等于没写。**关键约束要写在会被违反的那一侧，或做成运行时检查。**

## 三、交付包要自检，不要指望用户从花屏反推

本项目的一条：**输出尺寸不是 4 的倍数 → DMA 报一句完全无关的错**。
后来加了显式前置检查：

```
❌ 超出 PL 硬件上限：
     · 输入宽 1500 > 1280（行缓存列地址只有 11 位，会跨行覆盖）
   对策：--max-dim 调小输入 / --out-max-dim 调小输出
```

**原则**：**硬约束要做成"上板前的显式检查"**，
不要指望用户从"图怎么花了"反推到"尺寸超了"。

## 四、⚠️ 性能计时：先问"测量会不会改变被测对象"

**本项目最贵的一课**：给上板脚本加"多跑几次取中位数"，
顺带让核**连跑了 4 帧**，而核是**单帧**设计 → 第二帧起全错，
**上一版（跑一帧）明明是好的**。

**三条纪律**：

| 纪律 | 说明 |
|---|---|
| **默认值选"已验证过的那条路"** | 新的、风险高的路径要**显式 opt-in** |
| **计时全在 PS 侧** | 在 PL 里加 ILA 会**真占 BRAM 且拖时序**；加状态寄存器要重出比特流 |
| **打印全在计时区间之外** | SSH 控制台一次 print 要几毫秒，混进去会污染数字 |

**并且要在 README 里写明这条纪律**，否则下一个人会在计时区间里加 print。

## 五、日志：让"发结果"变成一句话

**痛点**：队友在 Jupyter 里跑，结果只在网页上，想发出来要截图或逐格复制。

**做法**：给脚本加 `--log FILE`，把 `sys.stdout` 换成 tee：

```python
class Tee:
    def write(self, s):
        self._out.write(s)          # 照常显示
        if self._fh:
            self._fh.write(s)
            self._fh.flush()        # ⚠️ 每行 flush（见下）
```

| 要点 | 为什么 |
|---|---|
| **每行 flush**（不是 fsync）| 脚本崩溃时最后几行往往是**报错行**，被缓冲区吃掉就白干了 |
| 一次会话一个文件、**每次运行重写** | 文件名固定，不用记版本 |
| notebook 自己的输出也要写进去 | 脚本管不到 notebook 打印的标题/汇总 |
| 文件写失败要**静默降级** | 绝不能因为日志问题影响主流程 |

## 六、notebook 交付（如果对方在 Jupyter 里操作）

| 坑 | 对策 |
|---|---|
| 脚本末尾的 `sys.exit()` 在 Jupyter 里变成 `SystemExit` **打断整个 notebook** | 用 `subprocess.run([sys.executable, "-u", ...])`，**不要** `%run` 或直接 exec |
| `capture_output=True` 让**输出被缓存到进程结束**才吐 → 对方以为卡死 | 不加 capture，让它继承 stdout；加 `-u` 保证不缓冲 |
| 对方直接点中间某一格 | **每个 code 格自带 import 和跨格常量**，不依赖上一格 |
| 手写 `.ipynb` 的 JSON 容易出结构错 | **用脚本生成**，并在生成后对每个 code 格做 `ast.parse` 自检 |

**最后一条本项目回本了**：改了生成器之后，那条自检当场抓出两个格的语法错。

## 七、⭐ 2026-10-31：上板安装链上**四处互相咬合的哈希**

> 交付包里只要改了**一个** `.py` 或 notebook，整条安装链就会断，
> 而且报错信息只指向其中一处，很容易改了一处又断另一处。

本例的安装本会依次校验 **4 个东西**（缺一不可，顺序改了会误判）：

| # | 校验对象 | 谁写入 | 改了代码但忘了改它 → 报错 |
|---|---|---|---|
| 1 | 包内 `release_manifest.json` 里的**逐文件 sha256** | 打包脚本 | `文件版本或内容不一致：xxx.py` |
| 2 | **ZIP 文件集 = 清单文件集**（集合相等，多一个少一个都不行）| 打包脚本 | `Archive has missing or extra files` |
| 3 | 安装本里的 `ZIP_SHA256` | 打包脚本 | `No matching ZIP SHA256 found` |
| 4 | 安装本里的 `MANIFEST_SHA256`（清单自身的哈希）| 打包脚本 | `Release manifest SHA256 mismatch` |

外加 `xxx_upload_checksums.json` 这类**旁挂校验文件**（第 5 处，最容易被忘）。

**⇒ 修法：把"一次改全"写成脚本，并且带 `--check` 模式。**
上面第 1/3/4 项在本项目里是一个脚本一次改完；`--check` 用来在交付前确认没有漂移。

**另外两条"不报错但是坑"的：**

| 坑 | 现象 | 对策 |
|---|---|---|
| 安装本**永不覆盖已有目录**（自动加 `_2` `_3` 后缀）| 用户在旧目录里跑，以为装的是新的 | 安装后在日志里打印**实际安装路径**，交付说明里写清楚 |
| 打包前目录里留了**上一次的构建产物**（如 `build/`）| 重建脚本第一句就 `error: build exists` | 打包脚本显式排除（`build/`、`.Xil/`、`__pycache__/`）|

**⭐ 判据：交付前在"干净解压"目录跑一遍（§一），并且**逐文件**比对
`清单 ↔ ZIP ↔ 安装本` 三者的哈希，而不是只看"能装上去"。**
