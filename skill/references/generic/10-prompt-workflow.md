# 10 · 提示词工作流：让大模型真正去"做"RTL 工程

> **适用场景**：用大模型（Claude / GPT 等，带工具执行能力）辅助做 FPGA 工程 ——
> 写 RTL、跑仿真、驱动 Vivado、定位上板问题。
> **失效条件**：
> · 用纯聊天窗口（没有文件/命令执行能力）⇒ 模板 1/2/3/4 的效果大幅缩水，只剩"讨论"
> · 项目没有**可自动判断成功/失败**的判据 ⇒ **不要授权自主执行**（见模板 2 的前提）
>
> 本文与具体题目无关，换一个 FPGA 题目仍然成立。
> 完整的实战记录（含每次失败的原文）见领域层的案例文件。

---

## 一、⭐ 最重要的一条：约束写成**文件**，不要写在对话里

对话里的约束会随上下文滚出窗口；**文件里的约束每一次都会被读到。**

把这几样固化成文件，放在工程根目录（例如 `CLAUDE.md` / `AGENTS.md`）：

| 写什么 | 为什么 |
|---|---|
| **硬约束**（不改哪个文件、哪些是已验证配置） | 防止"顺手重构"把已验证的东西改坏 |
| **接口契约**（寄存器表、AXI 位宽、时钟频率） | 模型据此写代码，不用每次复述 |
| **验证判据**（怎么算 PASS） | 决定能不能授权自主执行 |
| **交付/打包规则** | 避免每次交付都重犯同样的错 |

**⭐ 判据一：如果你发现自己在对话里第三次重复同一个要求，就该把它写进文件了。**

## 二、四类可复用的提示词模板

### 模板 1 · 让它**动手**，而不是给建议

```
你作为资深 FPGA 工程师。现在要实现 <具体目标>。
你负责 <范围，例如"只写 PL 侧 RTL，PS 侧不碰">，在 <工具，例如"Vivado 2025.2"> 里完成。
有疑问先问我，没有就开始做。
```

**要点**：**范围**和**工具**必须写明。不写范围，通常得到一份"设计方案"而不是可运行代码。

### 模板 2 · 授权自主执行（效率提升最大的一条）

```
继续做。过程中需要什么操作自己执行，不需要每一步询问我。
```

**效果**：模型自己跑仿真 → 改 RTL → 综合 → 实现 → 出比特流 → 更新文档，不再逐步确认。

> ⚠️ **前提是项目里已经有可自动判定的 PASS/FAIL**（TB 的逐字节比对、脚本的断言）。
> **没有判据就授权自主执行 = 让模型靠猜，而且你无法验证结果。**
> **这是本工作流最重要的一条经验：自主执行的前提是"可自动验证"。**

### 模板 3 · 诊断请求（明确"只诊断、不改"）

```
出现 <现象>，原因是什么。**不要修改任何代码，只指出问题所在和修改方案**：
<完整报错原文>
```

**要点**：
- **写明"不要改"** —— 否则它会一并改掉，你就失去了对照基线
- **贴完整报错**，不要只贴最后一行（缺上下文会猜错方向）

### 模板 4 · 先复现，再修

```
<现象描述>。先在 PC 上仿真同样的输入，看能否复现，把结果存到 <目录>。
复现出来之后我们再讨论改哪里。
```

**要点**：**强制"先复现、后修改"的顺序**。
很多"看起来是算法问题"的现象，复现后才发现是参数封装、调用顺序或环境问题。

## 三、⭐ 让它自己找 bug 的三个模式

### 模式 A · 让它**证明**，而不是让它**修**

```
<测试通过了>，但我怀疑没覆盖到。构造一个【必然触发】的用例。
```

"必然触发"比"多测几个"有效得多 —— 要构造它，模型必须先把触发条件想清楚。

### 模式 B · 让它**撤掉修复**，看能不能复现

```
把刚才的修复撤掉，跑同一个用例，看能不能复现出上板现象。症状要对得上。
```

这一条把"我改完了、测试过了"（只能说明没坏）
升级为"**修复前后症状一致**"（才能说明定位对了）。

### 模式 C · 给它**现场数据**，别让它猜

```
这是运行日志：<路径或内容>。看看有没有问题。
```

**通用原则**：先让程序把"现场"打出来（状态寄存器、分段耗时、出错行号），再交给模型。
**模型从数字推因果的能力，远强于从现象描述里猜。**

## 四、⚠️ 反模式

| 反模式 | 后果 | 改成 |
|---|---|---|
| "帮我优化一下" | 做一堆没要求的重构 | "只改 `<具体函数>`，其它不动，改完跑 `<测试>`" |
| "为什么这么慢" | 直接猜，且常常猜错方向 | "**先加分段计时埋点**，再按数据优化" |
| "这个能实现吗" | 得到泛泛而谈 | "实现 `<具体功能>`，**先说代价**（资源/时序/工作量）" |
| 一次问三件事 | 只答其中一件 | 一次一件，或明确编号 |
| 只贴报错最后一行 | 缺上下文，猜错方向 | 贴完整输出 + 触发操作 |

## 五、必须**人工把关**的三件事

| 事项 | 为什么 |
|---|---|
| **删除 / 覆盖文件** | 可能删掉没备份的东西。规则：复制不要移动；删除前先确认 |
| **对外发送 / 发布** | 推远端、上传服务器 —— 发出后可能被缓存或索引 |
| **改"已验证的配置"** | 默认值、参数、接口。加一个"顺手的小改动"就可能破坏原本正确的行为 |

## 六、协作记录怎么攒

如果比赛/评审要求提交"提示词、模型回答、自我纠错轨迹"，**每完成一件事写一篇**：

```markdown
# YYYY-MM-DD 主题
## 一、问题（现象 + 数据）
## 二、根因（怎么定位的）
## 三、修复
## 四、比修复更重要的东西（被证伪的假设、量错的口径）
## 【同步清单】（哪些文档跟着改了 / 明确不用改的理由）
```

**⭐ 第 4 节最值钱**：它记录的是"为什么当初判断错了"，
而这恰恰是下一次、以及别人复用你经验时最有用的部分。

## 七、已验证的效果与失败来源

| 做法 | 从哪次失败总结 | 已验证的效果 |
|---|---|---|
| 约束写进文件 | 同一个要求被重复提了三次，第三次仍被忽略 | 之后同类约束 0 次遗漏 |
| 自主执行的前置条件是"可自动验证" | 没有判据时授权，模型连续两轮改了错方向 | 配上逐字节判据后，一次授权内完成"改 RTL → 仿真 → 综合 → 实现 → 出 bit" |
| 诊断时明确"不要改" | 模型顺手改掉，失去了对照基线 | 一次"只诊断"确认无误后再改，避免了盲改 |
| 先复现再修 | 一个"看起来是算法问题"的现象，实际是参数封装 | 省掉了改错方向的一轮 |
| 撤掉修复看能否复现 | "测试通过"曾被误当成"修好了" | 3 次应用，症状全部与现场对得上 |
| 给现场数据而非描述 | "为什么这么慢"被猜成 5 秒，实测 26 秒 | 关键定位（挂起、耗时分布）全部来自现场数据 |

**失败来源**：以上每一条都对应本项目里一次真实的时间损失，
原始记录在 `report/llm_log/`，按日期可查。

## 八、一页速查

```
开工前
  约束 → 写进 CLAUDE.md / AGENTS.md，别只写在对话里
  判据 → 项目里有"自动判定 PASS/FAIL"的东西吗？没有就别授权自主执行

提问时
  要它动手 → 写清【范围】与【工具】
  要它别动 → 明确"只诊断，不要改"
  要它查 bug → 先复现，再讨论改哪里
  要它找漏测 → 让它构造【必然触发】的用例
  要它证明修对了 → 撤掉修复，看症状是否复现

给它的输入
  贴完整报错，不贴最后一行
  让程序把现场打出来（状态/耗时/行号），别用文字描述现象

永远人工把关
  删文件 / 对外发布 / 改已验证的配置
```
