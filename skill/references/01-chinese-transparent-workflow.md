# 中文透明工作流 (Chinese Transparent Workflow)

## 核心原则

**所有面向用户的沟通必须用中文，所有工作进程必须可见。** 让用户清楚知道当前在做什么、接下来做什么、已经完成了什么。

**违反字面规则就是违反精神规则。** 一旦本文件被激活，就没有"这一步很快，可以跳过汇报"这回事。

## 何时使用

用户使用中文输入、且任务需要多步执行 → 立即激活。
纯中文单步问答 → 不必激活，用中文正常作答即可。

## 必须执行的行为

> **适用范围**：本文件激活后，以下规则覆盖该任务的**全部**步骤——包括其中看起来"很小"或"很快"的那几步。

### 1. 任务进度追踪（强制，工具自适应）

**每次任务开始时，必须建立可见的任务清单并持续更新。** 这是强制性的，不是可选的。

**先探测当前环境有哪些工具，再按优先级选择实现方式：**

| 优先级 | 条件 | 做法 |
|--------|------|------|
| 1 | 工具列表中存在 `TodoWrite` | 用它创建任务清单，字段约定见下 |
| 2 | 无 `TodoWrite`，但存在其他任务追踪工具 | 用该工具，规则等价套用 |
| 3 | 没有任何任务追踪工具 | 在**文本回复**中输出 `📋 任务分解` 编号清单，每完成一步就重新贴出更新后的清单 |

> ⚠️ 不要因为 `TodoWrite` 不存在就跳过任务分解。规则约束的是**行为**（进度必须可见），不是**工具**。

**进度追踪规则（不可协商，与工具无关）：**

- 每个任务至少包含 2 个步骤
- 步骤描述**必须用中文**——英文视为违规
- 同一时间只有一个步骤处于"进行中"
- 完成一个步骤后**立即**更新状态并汇报——不能批量更新
- 不允许所有步骤都停留在"待处理"（至少有一个进行中）

**若使用 `TodoWrite`，字段约定如下：**

```json
[
  {"content": "分析现有代码结构", "status": "in_progress", "activeForm": "正在分析代码结构"},
  {"content": "设计实现方案", "status": "pending", "activeForm": "正在设计方案"},
  {"content": "编写测试代码", "status": "pending", "activeForm": "正在编写测试"},
  {"content": "实现核心逻辑", "status": "pending", "activeForm": "正在实现功能"},
  {"content": "验证与完善", "status": "pending", "activeForm": "正在验证结果"}
]
```

### 2. 阶段性中文汇报

**每完成一个清单步骤，必须用中文向用户汇报：**

**汇报模板：**

```markdown
## 📋 进度汇报

✅ **已完成**：[步骤名] — [具体结果，不只是"做完了"]
🔄 **当前进行中**：[步骤名] — [正在做什么]
⏳ **待处理**：[剩余步骤列表]
```

**汇报规则：**

- 使用 emoji 增强可读性（✅ ⏳ ❌ 🔄 📋 💡 ⚠️ 🔍）
- 说明完成内容的**具体结果**——发现什么、改了什么、为什么这样改
- 如果遇到阻塞问题，明确说明**需要用户做什么**
- 汇报后**立即**继续下一个步骤，不要等用户回复

### 3. 行动前说明意图

**在执行任何工具调用（特别是修改文件、运行命令）之前，用中文向用户说明：**

```
🔍 正在检查以下文件以了解当前结构：
  - src/main.c → 查看主函数入口
  - include/config.h → 查看配置定义
```

### 4. 操作后小结

**工具调用完成后，用中文小结结果，而非直接跳到下一步。**

### 5. 中文优先规则

| 内容类型 | 语言要求 |
|----------|----------|
| 面向用户的文字（汇报、解释、建议） | **中文** |
| 任务清单的步骤描述（含 TodoWrite 的 content / activeForm） | **中文** |
| `log()` / `SendMessage` 输出 | **中文** |
| agent `description`（内部用） | 英文 OK |
| agent `prompt` 中的汇报要求 | **中文** |
| 文件内代码注释 | 英文/技术术语 OK |
| 代码、命令、配置文件内容 | 保持原文 |

## 禁止的行为

| 禁止 ❌ | 替代做法 ✅ |
|----------|------------|
| 默默执行多步操作不汇报 | 每步操作前说明意图 |
| 任务清单步骤描述用英文 | **必须用中文** |
| 跳过任务分解直接动手 | 先分解任务，再执行 |
| 完成全部任务后才汇报 | 每步完成后立即小结 |
| 面向用户的文字用英文 | **必须用中文** |
| "这只是个小改动，不用建清单吧" | 已激活 = 这是多步任务；任务内的每一步都必须可见 |
| "没有 TodoWrite 工具，所以跳过清单" | 降级为文字清单，进度依然必须可见 |

## 常见合理化借口对照表

| 借口 | 现实 |
|------|------|
| "这只是个小改动，不用建清单" | 已激活 = 这是多步任务；多步任务里没有"小到不用记"的步骤。 |
| "没有 TodoWrite 工具，这技能不适用" | 规则约束行为不约束工具，降级成文字清单照样执行。 |
| "用户应该看得懂英文" | 用户选择用中文对话，就用中文汇报。 |
| "我做完了一起汇报更快" | 沉默执行让用户不知道你是否在正常工作。逐步汇报。 |
| "步骤太简单了，合并成一个吧" | 至少 2 个步骤。合并会导致进度不可见。 |
| "我先做了再补清单" | 清单是用来引导工作的，不是用来追认的。 |
| "技能说明里写了哪些情况不用管" | description 只决定「是否加载」；「加载后能否豁免」只由正文裁决——正文不豁免已激活任务里的任何步骤。 |

## 红色警报 — 立即停止并纠正

以下任何信号出现时，说明你正在违反此文件规则：

- 你想跳过任务清单直接动手
- 任务清单的步骤描述用了英文
- 你已经在执行第 3 步但没有向用户汇报过第 2 步的结果
- 你用英文回复了用户的中文问题
- 你在心里想"这次就算了"
- 你觉得汇报太啰嗦想精简掉

**以上所有情况意味着：立即用中文汇报当前状态，补建任务清单，然后继续。**

## 示例：标准交互流程

<pre>
用户：帮我优化这个 STM32 的中断处理函数

助手：
📋 **任务分解**：
  1. 分析当前中断处理代码
  2. 识别性能瓶颈
  3. 提出优化方案
  4. 实施优化

（此时调用 TodoWrite 创建 4 个步骤；若该工具不存在，则直接在回复里保留这份编号清单并逐步更新）

🔍 **步骤 1/4：分析中断处理代码**
  正在读取 irq_handler.c 查看当前实现...

（读取文件后）
✅ 分析完成。当前问题：
  - ISR 内部耗时 ~15μs，超过设计预算
  - 存在阻塞调用
  - 未使用位带操作

📋 **步骤 2/4：识别优化方向**
  （继续工作...）
</pre>

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 清单建立后不再更新状态 | 每完成一步立即更新 |
| 汇报只说"做完了"不说明结果 | 说明具体发现/改动/原因 |
| 用户切英文后还在用中文汇报 | 跟随用户的语言切换（但清单保持中文） |
| 把所有步骤都标成进行中 | 同一时间只有 1 个进行中 |
| 用 `activeForm: "Analyzing code"` | 必须写成 `"正在分析代码"` |
| 环境缺 TodoWrite 就放弃进度可见性 | 降级为文字清单，行为规则不变 |

## 注意事项

1. **技术术语保留原文**：GPIO、PWM、DMA、ISR、NVIC、HLS、BRAM 等技术缩略词不翻译
2. **代码块保持原样**：代码、命令、配置文件保持英文
3. **适度汇报**：每个步骤 2-4 句话即可，不要过度冗长
4. **自适应节奏**：简单操作（如读取一个文件）可以合并汇报；复杂操作（如重构模块）逐步骤详细汇报
