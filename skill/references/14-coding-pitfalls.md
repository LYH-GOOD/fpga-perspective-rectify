# 写码细节与踩坑

## 每一项的四元组

| 项 | 类型 | 适用范围（什么时候读） | 已验证的效果 | 失效条件 |
|---|---|---|---|---|
| **A** 编码 / **B** 行尾与字节 | **通用** | 任何在 Windows 上写的 `.py` / `.bat` | 修掉 GBK 控制台崩溃后，报告脚本不再「一个字节都不出」 | 纯 Linux 环境（stdout 不是 GBK） |
| **C** 期望值 / **D** 复验独立性 | **通用** | 写任何自检脚本、复验脚本 | 抓到过「复验永远全绿」和「期望值写死 → 差点去修一份本来没错的文件」 | 无 |
| **E** 写盘闸门 | **通用** | 任何会改文件的脚本 | 抓到过归档脚本把源文件改坏 | 纯只读脚本不涉及 |
| **F** 路径与 cwd | **通用** | 路径可能含中文 / 非 ASCII 时 | 改用 `np.fromfile`+`imdecode` 后，中文路径不再静默返回 `None` | 全 ASCII 路径不受影响 |

## 为什么有这一条

用户的原始要求：

> **「把你写代码时遇到的问题还有细节处理都写进大skill里」**

这个项目从 v1 做到 v7，**真正拖慢进度的从来不是算法难，而是"工具骗了我"**：

- 判定「文件行尾正常」的 `grep` 报了 0 命中，据此排除了正确假设，**白做一整轮**；
- 复验脚本遍历「我改过哪几行」，永远全绿，**永远查不出我漏改的那一行**；
- 期望值写死「应 1 处」，实打印 4，差点去**修一份本来没错的文件**；
- 五个数字整整齐齐全是 `20.8`，看着像结论，其实是**外法向写反了**。

**共同病根：把工具的输出当成了现实。** 工具本身是未知量，它也会错。
所以这份规程的每一条，都不是"应该怎样"的道理，而是**踩过之后写下来的一句话**。

## 什么时候用

- **写任何 Python 脚本**（检查 / 同步 / 存档 / 验收 / 交付 / 诊断）—— 读 **第一部分全部**。

- **要改文件、追加记录、落盘任何东西** —— 先读 **E 组**。
- **要让产出「能被单独发出去给人看」（日志 / 报告 / 自检）** —— 先读 **H 组**（H1–H13）。
- **要写反向验证 / 变异测试** —— 先读 **案例 9**：靶子要先量过够不够得着。
- **要判"某个量稳没稳"**（内存趋势 / 耗时趋势 / 误差随迭代收敛 / loss 曲线）——
  先读 **案例 10**：窗口起点必须锚在物理事件上，不能锚在百分比上。
- **出现"数字太整齐""结果反常地好""所有输入都返回同一个值"** —— 直接跳到 **第二部分案例 7**。
- **调 Windows API / C 库（ctypes）** —— 先读 **案例 12**：返回句柄的函数必须显式声明 `restype`。
- **改完一个 `.py` 准备说"改好了"** —— 先读 **案例 13**：`py_compile` 全绿 ≠ 能跑，
  还必须**真的 import 一遍**、再**真的调一次**。
- **写"只读不写"的验证 / 诊断脚本** —— 先读 **案例 14**：`importlib` 会写 `__pycache__`，
  足以顶掉别人设的「恰好 N 个文件」闸门。要么关字节码，要么自查。
- **要报一个"某个东西不存在 / 不适用"的量**（没有 PL / 没跑那条路 / 字段缺失）——
  先读 **案例 15**：`0` / `None` / `读不到` 是**三件事**，糊成一个数是谎报。
- **存档 / 备份 / 归档一份「有专门生成脚本」的产物**（zip / 报告 / 打包目录）——
  先读 **案例 16**：一律**复制原件**，不许在存档脚本里另写一套生成逻辑。

# 第一部分 · 速查清单

## A. 编码（Windows 控制台是 GBK）—— 本项目栽得最多的一类

| # | 规矩 | 为什么 |
|---|---|---|
| A1 | **源码含中文，一律落成 UTF-8 的 `.py` 文件再 `python 文件.py`，永不用 `python -c`** | `-c` 的代码串按系统 locale(gbk) 解码，中文直接 `SyntaxError` |
| A2 | 入口写 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` —— **stderr 也要设** | 只管 stdout 的话，一抛 traceback 中文又崩（traceback 走 stderr） |
| A3 | 把 `reconfigure` 包在 `try/except Exception: pass` 里 | 有些环境没有 `reconfigure`（老 Python / 被重定向的流） |
| A4 | **非 GBK 字符打进 GBK 控制台是「硬崩」不是「乱码」** —— `UnicodeEncodeError`，退出码 1 | 别做视觉检查，要做**可编码性断言** |
| A5 | **给子进程显式传 `PYTHONIOENCODING=utf-8`**，并同步声明父进程按什么解 | 管道编码跟 locale 走，不跟父进程走；两边没约定就会解出**假 FAIL** |
| A6 | 验收必须跑**裸环境**：`env -u PYTHONUTF8 -u PYTHONIOENCODING -u PYTHONLEGACYWINDOWSSTDIO` | 这些变量会把**被测对象自身的 bug** 盖住，实验条件污染结论 |
| A7 | **危险操作先出报告再动手**（`rmtree` 排在 `print` 之后） | GBK 崩在 `rmtree` 中途 = **半完成的破坏 + 报告不可信** |
| A8 | 诊断脚本**把结果写文件**，控制台只打 ASCII 摘要 | 否则诊断本身又崩一次，把第一次的结论也带走 |

**A6 的界线**：区分「**被测对象的缺陷**」与「**测量工具自身的编码缺陷**」——
前者**不许**用环境变量绕过。（`PYTHONUTF8=1` 曾把 `app.py` 里一个 `⏹` 在启动时崩服务的问题整整掩盖一轮。）

## B. 行尾与字节 —— 「用错工具就会得到假结论」

| # | 规矩 | 为什么 |
|---|---|---|
| B1 | **判断行尾必须数字节**：`open(p,"rb").read()` 后 `raw.count(b"\r")` / `raw.count(b"\n")` | `grep -n $'\r'` 报 0 是**假的**（见案例 5） |
| B2 | **shell 管道数的行尾一律丢弃** —— `od -An -c \| tr -cd '\n' \| wc -c` 报 LF=4466，Python 实为 1801 | `od` 把字节渲染成转义，`\r\n` 与字面 `\n` 混在一起 |
| B3 | **改文件一律 `open(p,"rb")` 读、`open(p,"wb")` 写** | 文本模式会做 universal newline 转换，写回时按平台默认补 |
| B4 | **不要在 `raw.split("\n")` 出来的行上做 `endswith` / `==` 锚点** | CRLF 文件每行残留 `\r`，锚点**恒为假** ⇒ 报「找不到锚点」，看着像文件被改坏了 |
| B5 | 要在文本上做替换，**直接在整份文本上做子串替换** | 避开 B4 |
| B6 | 孤立 LF 计数用 `n_lf - n_cr`，但**记住它对逆序 `\n\r` 是盲的**（净贡献 0 ⇒ 完全隐形） | 上一轮报「孤立 LF 2→2 一个没变 ✅」就是假结论 |
| B7 | 追加 / 补行尾前，先 `print(repr(raw[-20:]))` 看清**现状以什么结尾**，再决定补什么 | 给「孤立 LF 结尾」补 CR 时补在 LF **后面** ⇒ 造出 `\n\r` |
| B8 | 改前改后都比对 `count(b"\r")` 与 `count(b"\n")` 三元组 | 只比总数看不出结构被破坏 |
| B9 | 要查 B6 说的那种逆序 `\n\r`，**必须用 `re.finditer(rb"\n\r(?!\n)", raw)`**，不能 `raw.find(b"\n\r")` | 后者会把**每个 CRLF 空行**都算上（`\r\n\r\n` 的第 2、3 字节正是 `\n\r`）—— 实测同一份 `INDEX.md`：宽松判据报 **8 处**、严格判据报 **1 处**，差的 **7 处全是空行误报**。⇒ **B6 是漏报、B9 是误报，同一现象的两种判据各自会错**；报告行尾异常前先问「这个数字是怎么数出来的」 |
| B10 | 用 shell 数**转义竖线**（= 反斜杠紧跟竖线）**必须用 `grep -oF`**（固定字符串模式） | `grep -o` 的默认正则里，**反斜杠 + 竖线**在 GNU BRE 下是**交替操作符**，不是那两个字符 —— 于是「数转义竖线」得到一个**漂亮的假 0**；同源的 `sed` 替换更狠：判据退化成零宽匹配，把替换文本插进**每一个字符之间**（实测输出 `@ESC@\|@ESC@-@ESC@-…`）。实测同一份 INDEX：错判据报「转义 **0** / 裸 **217**」，真值是「转义 **31** / 裸 **186**」—— 差别足以让人去**修一份本来完好的文件**。⇒ 在 shell 里匹配**含反斜杠的字面串**一律加 `-F`，或退回 Python 的 `(?<!\\)`；报数字前先拿**已知答案的样本**对撞一次 |

## C. 期望值 —— 「写死」与「照抄」都会造出假结论

| # | 规矩 | 为什么 |
|---|---|---|
| C1 | **期望值必须由公式现算**，不许拍脑袋写数字 | 写死「残留 v6 应 1」实打印 4 ⇒ 差点去修一份**本来没错**的文件 |
| C2 | **也不许照抄上一轮** —— 每轮先测现状再定期望 | 上一轮期望「CR +2」是因为文件以孤立 LF 结尾；本轮末尾已是 CRLF ⇒ 应 **+1** |
| C3 | 把这个推导**写进注释**（含分支条件） | 否则下一轮还会照抄 |
| C4 | **期望值离谱时改公式，绝不改数字去凑** | 一阶式是 `Δ ≪ W−K` 时的截断，Δ 大时必然偏小 |
| C5 | 给出数值建议前，**把算式与阈值一起打印出来对撞一次** | 曾经心算 `1600×1200 = 1.92MP < 1.2MP`，实际 1.92 **远大于** 1.2，方向反了 |
| C6 | 计数型结论必须附**可重跑的命令与原始输出** | 印象里写「18 failed/15 passed」，实测 **19/17** |
| C7 | **自指的统计没有期望值** —— 统计对象会被「写日志 / 建回退点 / 生成快照」这些动作**本身**改变（典型：本目录文件数） | 曾写 `N_FILES = len(os.listdir(HERE)) + (1 if DRY else 0)`：那个 `+1` 是在补「dry-run 不建回退点、而 shell 重定向已经先建了日志」—— 口径**依赖调用方式**，同一脚本 dry-run 与 apply 得数不同。⇒ 这类量**别记数字**，只写「清单在哪个脚本里验」 |

## D. 复验的独立性 —— 「验证工具本身也需要被验证」

> 本项目在这一类上栽了 **18 次**（截至 2026-09-27 上一次统计）。以下每一条都是从其中一次里来的；
> **D21–D22 是此后新增的 2 次**，未计入那个 18。

| # | 规矩 | 为什么 |
|---|---|---|
| D1 | **判据用「内容模式」从磁盘重新判，绝不遍历「我改了哪几行」** | 编辑清单是**我的假设**；用它当判据 = 用答案对答案 ⇒ 永远全绿，且**查不出漏改的那一行** |
| D2 | **文档里写的期望 sha，必须拿真实文件 `open(p,"rb")` 现算一遍** | 文档是**声明**，磁盘是**现实**；不接到现实上就是自说自话 |
| D3 | **字节数 / 行尾从头量，不看任何脚本的自报** | 脚本自报来自它自己的中间变量，可能与落盘结果不一致 |
| D4 | 复验里**断言前提**：`assert real_board == real_base == V7, "前提就塌了"` | 前提不成立时，后面所有结论都没有意义 |
| D5 | **独立实现的副本，先跑 Δ=0 自检**：`max\|副本 − 生产\| == 0`，不过就 `sys.exit("结论一律作废")` | 副本是「我的理解」；抄错了后面全部数据作废 |
| D6 | **只比哈希查不出「抄错」** —— 内容抄错但内部自洽的副本能全绿通过 | 哈希只证明「两份相同」，不证明「内容正确」；要做**语义对拍**（同输入、逐位比输出） |
| D7 | **新判据上线前，先对「已知良好」的对象跑一遍**（应全绿），再拿去判未知对象 | 判据自身的行为是**未知量** |
| D8 | **拿两个判据对照前，先把口径写成一行文字对齐** | 「转义的 `\|` 不算裸 `\|`」没对齐 ⇒ 把 4 行完好内容误报成异常 |
| D9 | **检查器太粗 ≠ 文件有病** —— 先判「FAIL 出在哪一边」 | 曾照一个 off-by-one 的检查器去「修」**完好**的 INDEX，会亲手破坏它 |
| D10 | **列数 / 基准从被测文件自身取**（`NEED = len(BARE.findall(表头行))`），不手写常量 | 手写常量就是 off-by-one 的温床 |
| D11 | **数字太整齐 / 高度一致时，先怀疑工具** | 五张图每条边都返回同一个 `20.8` ⇒ 是 bug，不是结论 |
| D12 | **扫描全库禁用 `check(True` / `ck(True`** —— 断言条件必须可证伪 | 恒真断言 = 把「待验证的事实」降级成「一段说明文字」 |
| D13 | **有 if/else 分支的判据，两条都要实测跑过** | 只验证「通过路径」⇒ 另一条代码路径从没被执行 |
| D14 | 脚本结尾固定打印一节 **「本脚本无法验证的事项」** | 只报「验了什么」会制造过度信任 |
| D15 | 清点类工具**和被测代码一样需要先自检**（用已知成员对拍 + 逐个人工看点位） | 同一张清点表写错过 3 次：漏检、把 token 空格 join 后正则变成 `Image . open (` 报 **0 个**、docstring 是 STRING token 抹不掉 |
| D16 | **同一进程里 `import` 同名模块两次，拿到的是 `sys.modules` 里**那一份** —— 要比两个版本，必须让它们**不同名**：`importlib.util.spec_from_file_location("rectify_v7", path)` 各加载一次，并在输出里**打印两份的 `__file__`** | 直接 `sys.path.insert` + `import rectify` 会让「v7 vs v8」静默变成「v8 vs v8」⇒ **逐位相同必然成立**、对照彻底失效，而报告会显示满屏 ✓ —— **这是最危险的一种全绿**。与 F 组「打印实际加载路径」相邻但不同：那条管「加载到的是不是我要的」，这条管「两个版本有没有真的变成两份」 |
| D17 | **先冻结产物，再跑唯一一次验收** —— 不要「改一个字 → sha 变 → 重跑 → 又发现表述不准 → 再改 → 再重跑」 | 实测：改 docstring ⇒ sha 变 ⇒ 报告里记的 sha 对不上 ⇒ 得重跑；重跑后又发现表述不精确 ⇒ 再改又要重跑。**空转两轮，且报告与文件始终错位**。⇒ 文字全改完 → 文件冻死（记下 sha 与字节数）→ **然后只跑一次** ⇒ 报告与产物严格一一对应 |
| D18 | 改完 `.py`，**三道都要过**：`py_compile` → **真的 import 一遍** → **真的调一次** | `py_compile` 只做语法分析、**不解析名字** ⇒ 漏 `import time` 也能全绿，一跑就 `NameError`（案例 13）。import 也还不够 —— 没被调用到的分支里的错照样不报 |
| D19 | **注入式测试的假值必须按真实量级定标**（先量一个基准，再按比例注入）；断言也要跟着改成相对判据 | 写死的 `0.1234` 秒在那台机器上比整帧还长 ⇒ 测出 `ps_sec = -0.01` 这种物理上不可能的组合，红了但**红的不是被测代码**（案例 15-b/d） |
| D20 | 输出里**「0」与「不适用」必须能区分**：真是 0 就写 `0`（**并附原因**），根本不存在就写 `None`→「不适用」，读不到就写「读不到」 | 三者糊成一个 `0.00` 就是谎报（案例 15-a）。配套：真值下不可能出现的情况（如用时为负）**不许 `max(0, …)` 夹掉** —— 夹掉就把「测量坏了」这个信息藏了；要如实报负数 **+ 点亮一条会被印出来的警告** |
| D21 | ★ **新版本落地后，第一件事是比 `test_*.py` 的 sha16 与上一版是否相同** —— 相同就说明**测试没跟着功能走**，那几个 `PASSED` 与本次改动**无关** | 本项目已发生 **2 次**：`v9/test_rectify.py` 与 v8 **逐字节相同**（`7f2550923b28545d`，`105 passed`，新增 **0** 条）、`v11` 初版与 v10 **逐字节相同**（`263847d0b2101a9e`，`114 passed`，新增 **0** 条）。两次都**全绿**。★ 反直觉推论：**「补 NOTES」本身就是一次缺陷检查** —— 它逼你把「新增了什么测试」写成文字，**写不出来的那一项就是漏掉的那一项**（v9 当时没写 NOTES ⇒ 没查到，详见案例 17） |
| D22 | ★ **要写进文档 / 汇报的条数与 sha，一律现测**（`pytest --collect-only -q` 数用例、`sha256sum` 取哈希、`stat -c %s` 取字节），**不许沿用上一版文档或上一次汇报里的数** | 实测：`v11/NOTES.md` 写「v10 的 113 条 + 新增 15 条 = 128」，`--collect-only` 一跑是 **v10 = 114、v11 = 128（增量 +14）** ⇒ **两个数都对不上实物**；且同一份笔记的 §3.1 里已写明那份测试文件收的是 **114** 条，**前后自相矛盾**。⇒ 数字被引用一次就会被引用第二次，错的那个会传下去 |

## E. 写盘类脚本的闸门 —— 成本极低，拦住的事故极大

| # | 规矩 | 为什么 |
|---|---|---|
| E1 | **任一锚点不命中恰好 1 处 ⇒ 整份文件一个字节都不写**，退出码 1 | 命中 2 处时会静默改错地方 |
| E2 | **`dry-run` 是默认**，只有带 `--apply` 才落盘，且预览要打全 | 默认即写盘的脚本，任何误运行都造成不可逆改动 |
| E3 | **写盘前先存 `.改前` 回退点；复验脚本断言它存在且 sha 与记录一致** | 「能回退」必须**真做得到**才算数 |
| E4 | **脚本结尾显式 `sys.exit(1 if fails else 0)`** | 曾出现 `KeyError: 'apply'` 却返回退出码 **0** ⇒ 差一点把「已通过」写进验收记录 |
| E5 | **每次替换前 `assert src.count(old) == 1`** | `str.replace` 找不到目标时**不报错、原样返回** ⇒ 变异没打中，结论变成「测试漏了」，与真相相反 |
| E6 | **追加行前先查重**：`if row[:60] in txt: sys.exit(3)` | 无幂等保护会追加两次 |
| E7 | **追加 Markdown 表格行前断言 `n_pipe - n_esc == 6`**（5 列 ⇒ 6 个裸 `\|`） | 裸 `\|` 会**静默劈开整行**，索引结构错位 |
| E8 | **多文件脚本要先全部算完再统一写**；做不到就在文档里明写「部分落盘是可能的」 | 两个文件分开写盘，一份过一份不过时，过的那份**已经落盘了** |
| E9 | **变异测试用 `exec()` 内存副本，磁盘源码 sha 全程不变**（并在脚本里复核） | 直接在磁盘上改，中途崩了就留下被改过的源文件 |
| E10 | 变异脚本**可被 import 而不产生副作用** —— 逻辑包进 `main(argv)`，入口放 `if __name__ == "__main__":` | 否则「一 import 就把源文件改了」 |
| E11 | **变异测试必须两侧证明**：变异后**红** + 还原后**绿**，每个状态记 sha | 只测「变异后红」无法区分「测试抓得住」与「测试本来就红」 |
| E12 | 生成代码类文本时，先静态扫一遍 `%` 的配对 —— `%run` 要写成 `%%run` | 单个 `%` 被格式串吃掉 ⇒ `TypeError` |
| E13 | 用 `getattr` 探测能力，**不要用 `try/except` 吞异常去「兼容」** | 异常分辨不出「预期的不支持」与「真的坏了」 |
| E14 | **"只读"脚本跑完必须证明自己真的没写**：跑前跑后 **文件清单 + 非文件项 + 每个 sha** 三项都不想变。要在被测目录里 `importlib` 加载 `.py` 时，**先 `sys.dont_write_bytecode = True`**（必须在 load 之前） | CPython 会写 `__pycache__/*.pyc` —— 那就是"多出来的非文件项"。实测它顶掉了**另一个脚本**的「恰好 9 个文件」闸门，报错还落在别人头上（案例 14） |
| E15 | **产物有专门生成脚本时，存档 / 备份一律"复制原件"**：`shutil.copy2` + 断言复制后 sha 与源逐字节相同；并**把"该有的结构"也断言出来**（如"9 个文件 **+ `_READ_ME_FIRST.txt`**"），不是数自己打了几个 | 存档脚本自己 `zipfile` 重打一份 ⇒ 顶层 9 条目 vs 交付件的 `_board_pkg/` 前缀 + `README`，**371164 vs 367965 字节、sha 不同**，而"9 个文件都在"这个闸门**自己全绿**（案例 16） |

## F. 路径与工作目录

| # | 规矩 | 为什么 |
|---|---|---|
| F1 | **所有路径从 `HERE = os.path.dirname(os.path.abspath(__file__))` 派生**，绝不依赖 cwd | 脚本换个目录跑就找不到文件 |
| F2 | **上跳层数逐脚本核对**，不照抄（同项目里有 `..\..` 也有 `..\..\..`） | 抄错就指到别的目录 |
| F3 | 写完路径后立刻 `print` 出解析结果，或对关键文件 `assert os.path.exists(...)` | 让错路径当场暴露，而不是等到写盘 |
| F4 | **被测模块用绝对路径加载**，并在输出里**打印实际加载到的文件路径** | 同名模块多份副本时，`sys.path.insert` 顺序决定胜者；曾标签写 v1、实际跑 v2 |
| F5 | 需要 `os.chdir` 时用 `try/finally` 还原，或干脆不 `chdir`（全用绝对路径） | cwd 是进程级全局状态 |
| F6 | 相对链接要 `os.path.normpath` 后 `os.path.exists` 判一次 | 层级数靠手算，易错 |
| F7 | **拷完必须逐字节核对 sha，并把 sha 打出来给 INDEX 引用** | 「拷过去」≠「拷对了」 |
| F8 | 快照**只留不可重建的源与证据**，显式列出「⛔ 不拷」清单 + 断言它们**没有**出现 | 可重建物（`__pycache__` / `.pytest_cache` / zip）有保质期，进快照只制造混乱 |
| F9 | **每次都显式写绝对路径，不要假设上一条 bash 命令的 cwd 还在** | **建议新增（未见记载）** |
| F10 | **按时间戳找文件不可信**（复制 / 解压会重置 mtime）；要么按 sha，要么按显式清单 | **建议新增（未见记载）** |
| F11 | ★ **校验 / 自检脚本里「向上找目标文件」，不许硬编码 `dirname` 层数** —— 改成逐级向上探测，**并把找过的完整清单打进报告** | `_lint_iterations.py` 第一版把父目录写死成一层 ⇒ `FileNotFoundError`：它算出来的是 `project\ITERATIONS.md`，而文件实际在 `qian\ITERATIONS.md`（**差一层**）。★ 脚本该往哪层找，判断依据是**脚本自己写在哪儿**，不是它"看起来应该"在哪儿 |
| F12 | ★ **在文档里写「某脚本在 `X\` 下」之前，必须先 `ls` 核实** —— 不许凭印象或凭"和它同类所以在一起"去写 | 补 `v9/NOTES.md` 时把 `_probe_mask_gate.py` / `_dbg_mask.py` 写成在 `_平面校正验证\_eval\` 下，**实际两个都在 `project\_视频校正\`**；全库 `find` 后才改对 **3 处 + 1 处含糊引用**。★ 这两个脚本是 v9 唯一证据（判据 4/4）的出处 ⇒ 路径写错 = **结论无法复核** |

### G-2 阈值与掩膜

| # | 规矩 | 为什么 |
|---|---|---|
| G7 | **用 Otsu 前先算可分性 / 类间间隙**，不可分就抬阈值或换判据 | Otsu 只最大化**全局**类间方差，不保证切在「纸 / 桌」边界上 |
| G8 | **单峰直方图上 Otsu 无意义** —— 它会硬切一刀，切出的「前景」就是整幅图 | 纯背景图必须能返回「无目标」 |
| G9 | **阈值只在 Otsu 高侧抬一级**，抬完复查「不贴边界了」，不做递归 | 抬多级会开始侵蚀目标本体 |
| G10 | **提白纸固定用 `min(R,G,B)`**，不是灰度也不是 HSV 饱和度 | min 通道把彩色桌面压暗、把「三通道同时高」的白纸留下；灰度里纸与浅色桌面的亮度差不足 |
| G11 | **填洞用 `floodFill` 从边界灌背景，不用形态学闭运算** | 闭运算会把纸张缺角 / 凹边一起糊掉，形状判据随之失真 |
| G12 | 掩膜常量**成组记录**并写下同批其他旋钮的值 | 单个旋钮的「最优」常以别的旋钮为代价 |

### G-3 判据的设计与适用边界

| # | 规矩 | 为什么 |
|---|---|---|
| G13 | **判「对象对不对」用结构性判据**（贴不贴图像边界 / 连通域），**不用面积这类总量判据** | 面积比是总量指标：目标只占连通域一小块时总量掉不下去，而**结构性错误纹丝没动** |
| G14 | **见到「外接框贴满幅宽 + 填充率极低」⇒ 直接判为「检测对象错了」**，别去调框的位置 | 这是对象错误的**指纹** |
| G15 | **判据必须非退化**：写判据时先给一个**必然失败**的输入，验证它真会失败 | 恒真 / 恒假的判据等于没有 |
| G16 | **阈值来源必须独立于被评对象** —— 不许用从数据里反推的量去设阈值 | 那是循环论证 ⇒ 恒真 |
| G17 | **诊断量与判据阈值分栏存放，物理隔离** | 同一栏里放着放着就会被当阈值用 |
| G18 | **真值带不确定度的判据不许设硬阈值** ⇒ 标为「参照，**永不** PASS/FAIL」 | 手量真值本身有 0.4% 分歧、真值自身就带 10.095° 透视 |
| G19 | **松门槛要如实标注「很松」，不许当强证据** | 如「≤ 2× 最大误差棒」实测 9.088% vs 实际 span 1.582% |
| G20 | **判据失败时先做「对象是否正确」的排除，再讨论精度** | 把「检测到错对象」写成「按得不够准」，**会掩盖根因** |
| G21 | **一个测试只能有一个自变量** | 面积缩放测试里 `halfwidth ∝ hypot(W,H)` 是混淆变量 ⇒ 一个会**随机通过**的测试 |
| G22 | **先证明被测代码真的走到了目标路径**（留日志 / 计数），再谈稳不稳 | 「稳 ≠ 对」：某探针从未进入目标分支，测出来的「稳定」毫无意义 |
| G23 | **无真值的度量不拿来做结论**；真值不可得就明写「仅作参考，不判」 | 没有真值的指标无法排除混淆因素，只能产生「看着像结论」的数字 |
| G24 | **选基准前先验证基准是被测系统的合法不动点** | 基准违反不动点 ⇒ 谁把墨压暗谁被罚 ⇒ **结论方向整个反过来**（第 17 次） |
| G25 | **代理指标必须同坐标系、同变换、同量纲** | 跨变换比较大小 ⇒ 量纲随变换而变 |
| G26 | **先坐实机制，再动手**；没有机制解释的指标只是安慰剂 | 五条「猜机制 + 造代理指标」的假设**全部被证伪** |
| G27 | **用合成真值当前提前，必须先断言合成真值本身合格** | 合成图里墨的灰度给成 150（应为 0）⇒ 结论方向整个反了 |

### G-4 排障顺序

| # | 规矩 | 为什么 |
|---|---|---|
| G28 | **排障顺序固定为：掩膜结构 → 路径选择 → 几何公式** | 根因通常在「对象判定」层，不在「阈值数值」层 |
| G29 | **再跑飞先查「对象判定」判据，不要先动 Otsu** | 同 G28 |
| G30 | **根因定位到函数级之后再改，改动面越小越好** | v7 修法只动掩膜，几何一行未碰（`diff` = 4 块 / 62 行）⇒ 便于归因 |
| G31 | **修复的验收必须含「无回归」证据**，不能只报「坏的好了」 | 要报「修好几张 / 回归几张 / 其余变化 0.0px」 |
| G32 | **性能结论要带「哪一步占多少」的分步计时**，不报总时间 | v4 推翻了 v3 的叙事：慢的原因是**重复计算**（`np.min` 每次采样重算全图 = 89%），不是算子复杂度 |
| G33 | **纯性能改动的验收标准是「逐字节相同」**（MD5 / `np.array_equal` / `==`，不用 approx） | 把一个模糊的「优化」变成二值、不可辩解的门槛 |
| G34 | **加速比必须带「是哪一层」**：单项加速比 ≠ 它所在函数的整体加速比。两个数都对，**混着引用就是错的** ⇒ 把**两个都**写进 NOTES 并显式标「别看错」 | 同一处优化：`np.min(img,axis=2)` → `np.minimum` 链，**这一项** 15.980→1.110 ms = 快 **14.40×**；而 `_paper_mask` **整体**只 27.19→12.58 ms = 快 **2.16×**（余下各步合计才 ~11 ms，本来就没多少可省）。对外只报「快 14 倍」= 把整函数的成绩记在单项头上 |
| G35 | **改动正确 ≠ 改动有效** —— 每次改动都要给「改前 / 改后同指标对照」 | 逻辑上正确的改动可能对结果毫无影响 |
| G36 | **已证伪的假设不要重开** —— 在注释里写「永久封盘」 | 如 `_bilinear` 看起来像半像素 bug，它不是，别再改 |

### G-5 光照 / 数值

| # | 规矩 | 为什么 |
|---|---|---|
| G37 | 光照模型 `obs = g·T + d`，补偿 `T = (obs − K)/(W − K) × 255`；**报公式必须同时给 K/W 的物理含义与估计方式** | K = 暗场（墨），W = 亮场（纸白） |
| G38 | **分母上必须设下限**（本项目 `MIN_DEN = 6.0`） | `ε_out = ε_field × 255/(W−K)`；W−K≈10 时放大 **25×**，越小区间越不可用 |
| G39 | **阈值只能用不依赖待求量的尺子**（如分位数 `PAPER_PCT` / `INK_PCT`） | 自指阈值：用 `f < 0.5*(w+k)` 判墨而 k 正是待求量 ⇒ 78% 的格子被判错 |
| G40 | **旋钮取值要有多个独立证据，且把反直觉那条写下来** | σ 的网格伪影测试：**σ 越小反而越均匀**（与直觉相反） |
| G41 | **扫描最优 ≠ 该选它** —— 每个旋钮都要列**代价栏** | 扫描最优的 `INK_GATE=0.35` 把 okK 压到 17%、K 场 100% 靠 inpaint 填 |
| G42 | **不动点检验不需要真值，是唯一可靠的**；实测「补偿后再估一遍」差约 1 个灰度级 ⇒ **不是不动点** | 不要在补偿上套迭代 —— 写进 docstring 封盘 |
| G43 | **不确定度一律用相对量表述** `\|a₁/a₀ − 1\|` | 只有相对量才能跨条件比 |
| G44 | **不合分布的合计取 `max` 而不是求和**，规则写死在函数里并注明理由 | 各分量不是独立同分布，求和会虚高 |
| G45 | **模型分歧 ≠ 误差棒** —— 单独一栏，绝不并入 | `fallback_cost` 13.171%~23.057% 来自「两个模型分歧」，不是测量误差 |

### G-6 几何（本项目实测的具体坑）

| # | 规矩 |
|---|---|
| G53 | **消失点必须两次叉积**：`cross(cross(p1,p2), cross(p3,p4))`；一次 `cross(点,点)` 给的是**过两点的直线**，公式会「看起来对、结果全偏」 |
| G54 | **用 ω 做度量前先把齐次向量按 `vᵀωv = 1` 标定**；不归一 ⇒ 最大误差 **53.1%** |
| G55 | **角点 / 齐次量一律 float64**，不做降精度 —— float32 在 1000px 处绝对精度约 1.2e-4，误差**静默**进几何解算 |
| G56 | **排序与起点是两件事**：先绕质心极角排序，再 `argmin(x+y)` 定起点。四个独立 argmin/argmax 会在 **roll≈45° 时全倾角下全错**（随机四边形 **92.3%** 错） |
| G57 | **直线拟合用 TLS（总最小二乘），不用 `y=kx+b`** —— 近竖直边数值爆炸 |
| G58 | **拟合前先查有效点数与退化**（共线 / 重合）—— `_fit_line_tls` 会 `IndexError` |
| G59 | **别用单点定角，先拟合边线再求交** —— 角点噪声会被「直线求交」放大 |
| G60 | **输出宽高取两对边估计的几何平均，不用 max** —— max 会选中被透视放大过的近边，竖纸被拉成近似方形 |
| G61 | **近正视时消失点在无穷远，交点病态** ⇒ 设 `COT_MAX` 守门，超限走兜底路径并**标注**，不许静默出一个数 |
| G62 | **把不可判定的情形写成已知边界** —— 只有四边形时无法区分「纵向被拉长」还是「横向被压扁」，这是**信息缺失**不是缺陷，不靠加启发式「修好」 |

## H. 单文件报告 —— 「只用下载一个文件就行」（2026-09-27 起，**长期规矩**）

用户的原始要求：

> **「你这个代码有没有写自动生成日志之类的，就不需要我手动给你粘贴好多东西了，
> 只用下载一个文件就行（以后写代码都要）」**

⚠️ 「**以后写代码都要**」是**标准规矩**，不是一次性需求 —— 写脚本 / 写服务 / 写自检，
**默认都要自带一个能被单独发出去的报告文件**。

| # | 规矩 | 为什么 |
|---|---|---|
| H1 | **每份产出都自产一个单文件报告**，用户只下载这一个文件 | 手工 Ctrl+A 会漏 —— 终端一屏放不下，最该看的那几行通常不在当前屏 |
| H2 | **报告 == 屏幕，一字不差，谁都不截断** | 「报告」是屏幕的副本，不是屏幕的摘要。一旦它开始挑内容，用户就分不清漏了什么 |
| H3 | **头部自描述**：什么时候跑的 / 哪台机器 / 每个关键文件的 sha16 | 一个被单独发出来的文件必须**自己证明自己是谁**；否则「数字对不上」时无法判断比的是哪两份 |
| H4 | **每一次 `write` 都要落盘**（`with open(...)` 或显式 `flush()`） | 崩在中途时，没有 flush 的那些行**根本不存在** —— 而崩溃现场恰恰是最需要它的时刻 |
| H5 | **Tee 必须建在任何可能抛异常的语句之前** —— 连 `import numpy as np` 都要挪到它后面（加 `# noqa: E402`） | 例如 Numpy 2.x 改了 `np.cross` 签名，import 期就可能炸；炸在 Tee 之前 ⇒ 报告里**一个字都没有** |
| H6 | **Tee 里替换 `sys.stdout` 时必须取当前的 `sys.stdout`**，**不能**用 `sys.__stdout__` | Jupyter `%run` 下 `sys.stdout` 是 ipykernel 的 OutStream，与 `__stdout__` 不是同一个 —— 用 `__stdout__` 会把内容写进 **Jupyter 服务端终端**，用户在 notebook 里什么都看不到 |
| H7 | **不要假设 stdout 有 `reconfigure`**：`io.TextIOBase` 的子类**没有**这个方法（PC 实测 `hasattr` 为 `False`，`dir()` 里也没有）⇒ Jupyter 下必抛 `AttributeError`。写成 `try: … except Exception: pass` | 本项目栽过两次：一次是 `print` 里带 `⇒`，一次就是这个 |
| H8 | **报告要能一键下载**：HTTP 服务上给一个端点，响应带 `Content-Disposition: attachment; filename="<固定名>"`，内容 **== 日志全文**（不是摘要、不是尾部 N 行）；并且**在出错提示旁边也给一次入口** | 用户正拿着一段报错的那一刻告诉他「点这个下载」才有用；放到页面底部，他多半已经把报错复制走了 —— **而复制走的往往只有第一行** |
| H9 | **失败时进日志的必须是全文**，禁止 `str(payload).split("\n")[0][:80]` 这类截断 | 被砍掉的**恰好**是 `traceback_tail` 和多行拒绝理由 —— 最该看的部分 |
| H10 | **日志超限就在下次启动时轮转**（`app.log` → `app.log.old`，旧的只留一份），**不按天切目录** | 「只下载一个文件」这个承诺不能被日志增长毁掉；用户要的是**一个文件**，不是**一个目录** |
| H11 | **验证脚本绝不在交付目录里原地跑** —— 拷进 `tempfile.mkdtemp()` 沙箱再跑，收尾逐项核对交付目录的名字 / 大小 / mtime 未变 | 自检脚本自己会写报告文件、Python 会写 `__pycache__` ⇒ 交付包被弄脏。**同一个坑本项目踩过两次**（第一次 `__pycache__`，第二次 `selfcheck_report.txt`） |
| H12 | **轮转只能在「块与块之间」做**（如每笔请求的开头），不能放进 `_log()` 里 | 在一笔记录写到一半时换文件，会把它劈成两半 —— 而这正是「一个文件就能看懂」最怕的事 |
| H13 | **H8 的等式要能验**：端点读的文件 == 日志文件，且**读端点本身不写日志** | 否则「下载到的内容 == 日志全文」这条断言自己就不成立（下载动作会把日志改长） |
| H14 | ★ **落盘顺序：先写报告、再写屏幕**（`_fh.write` 在 `sys.stdout.write` **之前**） | 屏幕那一侧一旦抛异常（编码、管道断裂、Jupyter 的 OutStream），**报告连那一行都没有** —— 而 H2 承诺的是「报告 == 屏幕」，屏幕崩了恰恰是最需要报告全须全尾的时候。2026-09-27 实测：原写法让报告**当场断在第 18 行**；同一脚本改顺序后报告 38 条判据一条不少 |
| H15 | ★ **屏幕侧按 UTF-8 字节直写**：`buf = getattr(stream, "buffer", None)` → `buf.write(text.encode("utf-8"))`，取不到 `.buffer` 才退回 `stream.write` | 本机控制台是 **GBK**（`sys.stdout.encoding == 'gbk'`）。**`⚠`(U+26A0) / `▶`(U+25B6) / `⛔` 都不在 CP936 里** ⇒ `sys.stdout.write(str)` 直接抛 `UnicodeEncodeError`，**且常在 except 里再崩一次** ⇒ 表现为「stdout 一个字节都不出」+ rc≠0。本项目栽过两次（`engine.py --info` 的 `COMPENSATE_WARN`、探针的 `▶`）。**在 CP936 里的**：`★ 「」 （） ⇒ —— ✓ ✗ → ← ↑ ↓ ① ② ③` —— 判据不是「看起来特不特殊」，而是**能不能被 CP936 编码**。读侧本来全是 UTF-8 ⇒ 字节写是**与读侧精确对齐**，不是权宜之计。⚠️ `app.py` 的 `sys.stdout.reconfigure(...)` 兜底**不继承给子进程**，别拿「服务里没崩」推「这条命令不会崩」 |
| H16 | ★ **报告里描述性的「读法 / 结论」必须由数据分支产出，不许硬编码一种** —— 判据可以在 docstring 里事先写死（那是防止事后凑判据），但**读法句必须跟着刚印出的数字走** | 2026-09-28 B 探针（`_contact_cut_probe.py` §3b）第一版把读法**写死**成「单调帧数接近全部 ⇒ 削纸」，而全量 190 帧实测 **0/27 帧单调**、**27/27 帧有 ≥0.05 大跳变** ⇒ **报告里那句话与它自己刚印出的数字完全相反**。这类错误的杀伤力在于：读者（包括未来的我自己）会**直接照那句读法下结论**，而不会回去核对上面的表。**同一类事故已出现三次**（另见 H 组的「失败 0」假绿、闸 2 注释里被证伪的「余量约 9 倍」）⇒ 凡是会产出「读法 / 结论 / 判定」字样的地方，一律写成 `if 条件: emit(A) elif 条件: emit(B) else: emit(C)`，**不许**只 `emit(A)` |

## I. 开关与死代码 —— 「根本没跑」（2026-11-01 追加）

> **A~H 组讲的都是「跑是跑了，但跑错了」。这一组是「压根没跑」** ——
> 代码正确、语法过关、测试通过、日志正常，就是那条路径一次都没执行。
> 它比跑错更隐蔽：**你不改，它不报错；你改了，它也不给反馈**。

| # | 规矩 | 为什么（全部是本项目实测） |
|---|---|---|
| I1 | **新写的加速路径 / 新参数，先在日志里打一行「本条路径执行了 N 次」，N>0 才算接上** | 2026-10-28 查清：`box` 默认 `false`、只有 `radius≥3` 才开 ⇒ **C 核从没被调用过**。打开后 5.85 → ~10 fps，省 **76.75 ms/帧**。代码写得再对，没跑到就是 0 |
| I2 | **改外层参数前，先确认内层没有缺省值把它覆盖掉** | `_lk_current` 用 `LKPhaseBudget` 的缺省（cpu .12 / wall .40）盖掉了外层的 `recovery_budget_ms`。改一行确实"修好"了、尾巴砍掉 45%，但 fps 在 **120 / 80 / 40 三档全是 23.3 不动** —— 因为真正生效的是内层 |
| I3 | **用 0 表示「关」的开关，先查有没有 `max(1, …)` / `or 1` 这类兜底** | `P11_LOG_EVERY=0` 被 `max(1,int(...))` 翻成 **1** ⇒ 想关日志反而变成**每帧全记**。「0」和「未设置」在这类代码里必须分开判 |
| I4 | **只在启动 / 首帧跑的路径，不能算进每帧成本** | `find_paper_quad` 在实时路径里只在 `budget is None`（启动）时调用，正常帧根本不走。把它排成「性能优化第一名」是**排错了对象**（2026-10-30 更正） |
| I5 | **「这条路跑到了吗」用计数判，不用耗时判** | PL 流式锐化真旁路：`SEL_NOW` 只见 `[1]/[0]`、**0 次 `ap_start`** ⇒ 功能验到底了，实际只省 0.9 ms/帧。若不是去数 `ap_start`，会得出「旁路没用」的相反结论，然后在错误方向上反复优化 |

**一句话判据**：改完跑一趟，**看日志里这条路径的计数变了没有**。

- 计数不动 ⇒ 代码没跑到。这时**不管耗时变快还是变慢，那个数都是假的**。
- 耗时变快了但计数器没动 ⇒ 你改的是别的东西，或者只是噪声。
- **成本极低**：一行 `log('路径X 命中 %d 次', n)`，比事后花半天查「为什么优化没效果」便宜两个数量级。

**配套落点**：凡是「加了个开关让它更快」的改动，**验收标准不是 fps，而是计数器**。
fps 对了但计数器是 0，那是巧合；计数器 >0 再看 fps，才算真接上。

## 案例 1 · Otsu 选了 132，而需要的边界是 170~190

> **本项目的头号事故：算法把对象整个认错了，还产出了一张「看起来跑通了」的废图。**

**现象**：test-7 的输出被拉成 **1:2.32** 的长条。

**根因链（五步，每一步都能单独写进规程）**：

```
① _paper_mask 的全局 Otsu 阈值 = 132   （而「纸 / 桌」边界需要 170~190）
② ⇒ 桌面高光区与纸连通，最大连通域外接框 x[0,1024] 横跨整幅、填充率仅 21.3%
③ ⇒ quad_quality 只比「角度方正度」⇒ 选中兜底路径 B（12.80° < 路径A 12.93°）
④ ⇒ extreme_quad 的对角极值落在检测图右下角 (1023,1365) / 左下角 (0,1365)
⑤ ⇒ 输出 1:2.32
```

**为什么 Otsu 会选 132**：Otsu 只最大化**全局**类间方差，**不保证切在「纸 / 桌」边界上**。
桌面高光区自成一峰、且与纸的暗部重叠，最优方差切面落在**桌面内部**（132），不是纸边。

**★ 关键细节**：v1 就提出过 Otsu 可分性闸门（`min_gap` 一类），**v7 仍让 132 通过** ——
**「提过闸门」不等于「闸门拦住了」**。闸门必须落在**真正执行的那条路径**上，并在通过 / 拒绝时留可见日志，否则等于没有。

**修法**：新增 `_touches_border()` + 在 Otsu 高侧**再切一刀**（只抬一级）。
`diff v6 v7` = **4 个 diff 块 / 62 行**；`find_document_quad` / `extreme_quad` / `quad_quality` / `rectify` **一行未动**。

**效果**：修好 2 张（test-6 变化 201.6px、test-7 变化 373.4px）/**回归 0 张**/另 7 张 **0.0px**。

**★ 沉淀出的规矩**：**排障顺序固定为「掩膜结构 → 路径选择 → 几何公式」。**
再跑飞**先查对象判定，不要先动 Otsu** —— 根因在「对象判定」层，不在「阈值数值」层。

## 案例 2 · 「抬后/抬前面积比 ≥ 0.5」拦不住故障

> **第一版补丁被实测否决 —— 这是本项目「改动正确 ≠ 改动有效」最贵的一次。**

**当时的修法**：给 Otsu 抬阈值加一条护栏 —— 「抬后 / 抬前面积比 ≥ 0.5」。

**实测结果**：

| 图 | 面积比 | 溜过了吗 | 实际输出 |
|---|---|---|---|
| test-2 | **0.637** | ✅ 溜过 | 0.7103 → **0.3359** |
| test-3 | **0.831** | ✅ 溜过 | 0.7112 → **0.1723** |

**为什么拦不住**：面积比是**总量**指标。桌面亮区只占连通域的**一小块**，抬阈值后总量掉不到 0.5；
而「横跨全幅」这个**结构性**错误**纹丝没动**。

**换成「贴边界」判据后**：9 张分类全对，② 贴边 **7/9 → 9/9**。

**★ 沉淀出的规矩**：
- **阈值型守卫在结构性故障面前天然失灵**，别拿它兜底；
- 判「对象对不对」要用**结构性判据**（贴不贴图像边界 / 连通域），不用面积这类**总量**判据；
- **见到「外接框贴满幅宽 + 填充率极低」⇒ 直接判为「检测对象错了」，别去调框的位置。**

**这条判据的来源**：目标（纸）是**被画面包住**的物体，绝不会贴到画面边；
贴边 ⇒ 它一路延伸出画面 ⇒ 那是背景。

## 案例 3 · 期望值：写死错一次，照抄又错一次

> **同一类错误，一周内制造了两次方向相反的假结论。**

### 第一次：写死

复验脚本里写死「**残留 v6 应 1 处**」。实打印 **4**（横幅 1 + 新说明 2 + 历史原文 1）⇒ 脚本判「不符」。

**差一点去「修」一份本来没错的文件。**

**真相**：新写的说明文字里本来就会提到 v6 ⇒ **期望值不是常量，是一个算式的值**。

**修法**：改成 `横幅数 + 新说明数 + 保留历史数` **现算**。

### 第二次：照抄

往 `INDEX.md` 追加一行时，上一轮的期望是「**CR +2 / 孤立 LF −1**」，我照抄了 ⇒ 又是假警报。

**真相**：上一轮文件**以孤立 LF 结尾**（要先补一个 CR 再追加）⇒ 补 CR 的分支会触发；
本轮实测末尾**已经是 `|\r\n`** ⇒ **那段逻辑根本不触发** ⇒ 期望应是 **CR +1**。

**★ 沉淀出的规矩**：
1. **期望值必须由公式现算**，不许写死；
2. **也不许照抄上一轮** —— 每轮先测现状再定期望，因为**分支条件不同，期望就不同**；
3. 把这个推导**写进注释**，否则下一轮还会照抄；
4. 期望值离谱时**改公式不改数字**。

## 案例 4 · 拿自己的编辑清单去对 = 用答案对答案

> 本项目在「验证工具本身有错」这一类上栽了 **18 次**，这是**共同根因**。

**反例**：复验脚本遍历「我改了哪几行」—— 这是**我的假设**，不是现实。
用它当判据 ⇒ **永远全绿，且永远查不出我漏改的那一行**。

**正解**：从磁盘**按内容模式重新判**：

```python
LIVE_PAT = re.compile(
    r"Expected|check\(|ck\(|若前 16 位|上板时|一字不改|一个字都不改|"
    r"sha256 = |rectify_sha256")
bad = [i+1 for i, ln in enumerate(lines)
       if LIVE_PAT.search(ln) and V6 in ln and "01 起目录搬基准" not in ln]
```

正则里的每条特征词**独立挑出来**，不抄编辑脚本的锚点；命中行**逐行打印**出来供人复核。

**配套的三条**（缺一条独立性就垮）：

| # | 动作 | 为什么 |
|---|---|---|
| ① | 判定用**内容模式**，不读编辑清单 | 用答案对答案 = 自证 |
| ② | 文档里写的期望 sha，**拿真实文件 `open(p,"rb")` 现算一遍** | 文档是**声明**，磁盘是**现实**；这是把文档接到现实上的**唯一动作** |
| ③ | 字节数 / 行尾**从头量**，不看编辑脚本自报 | 脚本自报来自它自己的中间变量 |

**★ 本轮最大的收获正是靠这条发现的**：handoff 列了 5 处要改的行，**漏了第 1642 行**，
而它比第 1641 行**更危险** —— 它断言 `h == _pynq_parity_check/rectify.py`，
而 parity 那份是 **v6 历史快照**，v7 起来后**必然不等** ⇒ 照它跑**会红**，
还会把人引向「**基准被偷改了**」的**错误结论**。

> **用清单去对，就只会验清单上有的东西。**

## 案例 5 · `grep -n $'\r'` 报 0 命中 → 排除 CR → 白做一整轮

**现象**：`_存档\INDEX.md` 第 37/38 行被从中间劈开，表格断行。

**当时的推理**：怀疑是 `\r` 造成的 ⇒ 跑 `grep -n $'\r' INDEX.md` ⇒ **报 0 命中** ⇒ **排除 CR 假设** ⇒ 往别的方向查了**整整一轮**。

**真相**：`grep` 对 CR 的处理**不可信**（strip / 行分割行为）。它报 0 不代表文件里没有 CR。
数出来是：**0x0D 有 46 个 / 0x0A 有 48 个**。

**同类第二个坑**：脚本按 `raw.split("\n")` 切行 ⇒ 每行末尾残留 `\r` ⇒ 锚点 `endswith` **永远为假**
⇒ 脚本报「找不到锚点」，**看起来像文件被改坏了**。

**同类第三个坑**：`od -An -c | tr -cd '\n' | wc -c` 数出「LF = 4466 / 2096」，
而 Python 字节计数实为 **1801 / 606**。

**★ 沉淀出的规矩**：
1. **判断行尾必须数字节**（`raw.count(b"\r")`），不许用 `grep`；
2. **shell 管道数的行尾一律丢弃**，一律以 Python `bytes.count()` 为准；
3. **不要在 split 出来的行上做锚点**，直接在整份文本上做子串替换；
4. 改文件一律 `rb` 读 / `wb` 写。

**★ 还有一个隐形盲区**：`count(\n) - count(\r)` 这个孤立 LF 计数法，
对**逆序的 `\n\r`** 净贡献为 **0** ⇒ **在计数上完全隐形**。
上一轮报「孤立 LF 2→2 一个没变 ✅」就是**假结论**——字节 77271 附近实际藏着一处 `\n\r`。

## 案例 7 · 判据的适用边界

> **一个只会回答「偏了多少 px」的指标，永远说不出「你是不是框错了东西」。**

**现象**：`verify_photos.py` 的 ② 判据（四边形贴边）给 v6 打了 **7/9**，
于是两张失败被解释成「**没按准**」。实际是**检测到了错的对象**。

**② 的双重盲区**：

| 盲区 | 说明 |
|---|---|
| 一 | **只扫 ±20px** —— 误差更大就量不出来（test-6 的 **19.8px** 已经贴墙） |
| 二 | **只认亮度台阶** —— 亮桌面或纸内的墨影 / 阴影都能给出「像结论的数」 |
| ★ | **它永远说不出「框的是错对象」** |

**同类第二种**：`quad_quality` **只比「角度方正度」** ⇒ 路径 B（12.80°）以 0.13° 战胜路径 A（12.93°），
而 B 的对角极值恰好落在**检测图的角**上。
⇒ **路径选择必须加「对象正确性」判据**，不能只看形状分数。

**★ 第三种：数字太整齐 = 工具坏了。**
`edge_offset` 第一版把**外法向的翻转条件写反**（`dot(pts−ctr,nrm) > 0` 应为 `< 0`），
于是朝纸**内**扫了 20px ⇒ 每张图每条边都返回「最后一点仍是白」，
**五个数字整整齐齐全是 20.8**。

> **数字太整齐 / 高度一致时，先怀疑工具** —— 数字应当是参差的。
> **「看着像结论，其实是 bug」。**

**★ 沉淀出的规矩**：
1. 判据失败时**先做「对象是否正确」的排除**，再讨论精度；
2. 拿 `false` 当「不好」之前，先问「这个指标**能不能**表达我要问的问题」；
3. ②这类有盲区的判据**只作旁证**，主证据用**无阈值判据**
   （本项目最终用的是：① 四个角是否贴图像边界(1.5px 内) ② 输出宽高比 vs A4 真值 —— **两条都要**）。

## 案例 8 · 写盘类脚本的最后两道闸门

> 成本极低，拦住的事故极大。

### 闸门一：锚点必须恰好命中 1 处

**现象**：锚点在文件里出现 **2 处**时，静态改错地方（或两处都改）。
字符串替换**不区分「第几处」**。

**规矩**：**任一锚点不命中恰好 1 处 ⇒ 整份文件一个字节都不写**，退出码 1。

```python
if src.count(old) != 1:
    print("✗ 锚点命中 %d 处（应恰好 1）⇒ 不动，退出" % src.count(old))
    sys.exit(1)
```

### 闸门二：退出码必须显式

**现象**：一次变异运行抛 `KeyError: 'apply'`，却**返回退出码 0**
⇒ 差一点把「**已通过**」写进验收记录。

**规矩**：脚本结尾显式 `sys.exit(1 if fails else 0)`，并断言**确实发生了预期数量的改动**。

> **「跑完了」不等于「做到了」。** 一个「看起来成功、其实什么都没做」的脚本，
> 比一个报错的脚本危险得多 —— 报错会拦住你，静默成功会**带着你往前走**。

### 配套：dry-run 是默认

```python
APPLY = "--apply" in sys.argv     # 默认 dry-run
```

默认即写盘的脚本，任何一次误运行都造成**不可逆**改动。
配套动作：**写盘前先存 `.改前` 回退点，且复验脚本要断言回退点存在、sha 与记录一致** ——
「**能回退**」这句话，必须**真做得到**才算数。

## 案例 9 · 反向验证的靶子选错了 ⇒ 一条**空判据**（2026-09-27）

> 一条失败的判据**不会自己告诉你它是空判据** —— 它会和真判据一样显示 ✓。

### 现象

给「失败时日志记全文」（H9）写反向验证：把代码改回旧的
`str(payload).split("\n")[0][:80]` 截断写法，断言测试**会红**。跑了 —— **没红**。

### 先量，再选靶子

量出三个失败用例的响应体：

| 用例 | 层 | 行数 | 最长行 | 旧写法 `[:80]` 丢不丢 |
|---|---|---|---|---|
| 半截文件（夹具前 30%） | 引擎层 400 | 1 | **39** | 一个字都不丢 |
| 空 body | 判闸层 400 | 1 | **28** | 一个字都不丢 |
| 真实基准图 test-1.jpg（24.47 MP） | 判闸层 413 | 1 | **113** | ★ 砍掉 33 个字符 |

⇒ **只有第三条够得着刀口。** 前两条的正文比 80 短，旧代码在它们身上**什么都没丢**，
拿它们做反向验证必然假红 —— 而假红会把人送去修改**本来没错的代码**。

### 这里有两个方向相反的错误，都要避开

| 错误 | 长什么样 |
|---|---|
| **靶子够不着** | 断言「旧代码会丢内容」，但用例的正文只有 39 字符 ⇒ 假红 |
| **改判据直到它红** | 为了让它红，去放宽 / 收紧断言 ⇒ 测试变成装饰品 |

### 正确做法

1. **先量再断言**：写一个 `_diag_*` 脚本把每条用例的「行数 / 最长行」打出来，
   **选长度 > 刀口的那条**当靶子，并在代码注释里写清是哪一条、为什么。
2. **判据不写死是哪一条**：遍历**全部**失败用例，要求「**至少有一条**丢了行」，
   并把每条的实际结果打出来（丢了几行 / 一行都没丢）。

```python
lost = []
for key, label in FAIL_CASES:
    m = missing_lines(g[key][1], g["log"])
    if m:
        lost.append((label, m))
        print("     %s：旧写法下丢了 %d 行，例如 %r" % (label, len(m), m[0][:56]))
    else:
        print("     %s：旧写法下**一行都没丢**（正文比 80 短）" % label)
check(bool(lost), "★ 旧写法确实丢了内容 ⇒ 这条判据有鉴别力")
if not lost:
    print("     ⚠️ 一条都没丢 = 这份测试**没在测任何东西**")
```

3. **假红之后的下一句话不能说「那我去改判据」** —— 要问「**这条用例够得着刀口吗**」。

> 判据的**鉴别力**不是设计出来的，是**量出来的**。
> 写反向验证之前先打印一条数：**我的靶子离刀口有多远？**

## 案例 10 · 趋势判据的窗口锚「百分比」而不锚「物理事件」⇒ 同一代码只换 N，结论方向相反（2026-09-27）

> 窗口的**起点**必须由一个**物理事件**决定，不能由一个**拍脑袋的百分比**决定。
> 百分比在小 N 下会把整段窗口落在"还没稳定"的那一段里 —— 而它**看起来完全正常**。

### 现象：三次独立跑，每次都自洽，但方向相反

判「常驻引擎会不会内存泄漏」，指标是 RSS 对帧号拟合出的斜率（kB/帧）。

| 跑法 | 三次独立跑的结果 | 结论 |
|---|---|---|
| `--frames 20` | **327 / 179 / 108** kB/帧 | ✗ **会 OOM** |
| `--frames 60` | 16.66 / 7.82 / **−1.92** kB/帧 | ✓ **稳** |

**同一份代码、同一套阈值、同一个输入集**，只换 N —— 结论 180° 相反。
更要命的是：`--frames 20` 那三次连**彼此之间**都对不上（327 vs 108，差 3 倍）
⇒ **小样本连重复性都没有**，可它照样给你一个斩钉截铁的 ✓/✗。

### 真因：窗口是「后半 50%」，而前 27 帧整个是爬升段

把 60 帧的 RSS 逐帧打出来看形状：

```
前 ~27 帧：52 → 60 MB      ← 爬升（每张图第一次解码 + 分配器 arena 生长）
之后 30+ 帧：58.5~61.5 MB  ← 横盘，还带一个与"当前哪张图"同周期的 9 帧小波动
```

`--frames 20` 的「后半 50%」= 第 10~20 帧 —— **整段落在爬升期里面**。
它量的不是"泄漏速率"，是"暖机有多陡"。
`--frames 60` 的「后半 50%」= 第 30~60 帧 —— 才是横盘段，量的才是泄漏。

### 正确做法

**1. 窗口起点锚在物理事件上，百分比只当"下限"。**

```python
warm = len(blobs)                    # 物理事件：每张图都至少解码过一次 ⇒ 暖机结束
cut  = max(int(n * TAIL_FRAC), warm) # 百分比只是下限，暖机永远优先
MIN_PTS = 8                          # 拟合窗口少于这么多点 ⇒ 不出结论
```

**2. 点数不足就"不出结论"，不给弱结论。**

```python
if k is None or len(xs) < MIN_PTS:
    E("  ✗ **不出结论** —— 拟合窗口只有 %d 个点，至少要 %d 个才拟合得出趋势。"
      % (len(xs), MIN_PTS))
    E("     ⇒ 加跑：--frames %d" % max(60, frames * 3))
elif abs(k) < SLOPE_OK:
    ...
```

「样本不够」的正确输出是**"样本不够"**，不是"斜率 327，看着像会 OOM"。
弱结论会被下游当成结论用。

**3. 旧窗口的结论要并排印出来，不许暗中换判据。**

```python
cut_old = int(n * TAIL_FRAC)         # 旧规则留着，**并排显示**
if cut_old < warm and ko is not None:
    E("  ⚠️ **旧规则**（后半 %d%%）的窗口是第 %d..%d 帧 —— 整个落在暖机段**里面**，"
      % (int(TAIL_FRAC * 100), xo[0], xo[-1]))
if cut_old != cut:
    E("     （两个窗口不同：旧=%d..%d，新=%d..%d —— 新窗口才对。）"
      % (xo[0], xo[-1], xs[0], xs[-1]))
```

改判据这件事本身是对的，但**必须留下"我改过什么"的痕迹** ——
否则下次有人拿旧报告对比，会以为是算法变了。

### 这一条的适用范围远不止内存

任何**"某个量随时间/迭代变化，要判它稳没稳"**的判据都吃这一条：
内存趋势、耗时趋势、误差随迭代收敛、loss 曲线、温度漂移……

**动手写这种判据之前先问三句：**

1. 这段数据里，**稳定态是从哪个事件之后才开始的**？（→ 窗口起点）
2. 我现在的窗口**够不够长到只包含稳定态**？（→ `MIN_PTS`）
3. 样本不够时，我的代码**会说什么**？（→ 不许是 ✓ 也不许是 ✗）

> 另一件必须记下的事：**这次是自己推翻自己**。
> 上一轮拿 `--frames 20` 的 327 kB/帧写了「会 OOM」，还据此设计了应对方案。
> 推翻它的不是新数据，是**把窗口起点接到物理事件上**重看同一批数据。
> ⇒ 结论反常（太好/太坏）时，先怀疑**窗口**，再怀疑**系统**。

### 同一天，同一个坑的**第二张脸** —— 暖机段不在帧号上，在**一次请求内部**

写板包干跑脚本时，给「meta 自报的 `rss_mb`」做**独立复测**：
从外面用同一个 WinAPI 测同一个 pid 的工作集，两个数应当只差时序抖动。
第一版拿**第一次请求**去比：

```
外部测得 pid 13688 工作集 : 58.7 MB
meta 自报 rss_mb          : 50.6 MB     ← 差 8.1 MB，FAIL
```

差 8 MB 看着像「**测错进程了**」—— 那正是案例 12 ctypes 零扩展的症状。
但同一份报告里连跑 12 帧的逐帧表，两个数吻合到 **0.1~0.5 MB**
⇒ API 没错、进程也没错。

真因：**自报值是在「响应序列化之前」采的** —— 之后还要分配 PNG、JSON、HTTP 头那几块。
这 8 MB 是**一次性**的（cv2 首次解码 + 分配器 arena 首次生长），第二枪起就没有了。

⇒ **判据窗口里又混进了暖机段。** 和上面那个百分比是**同一件事**，
只是这次的暖机段不在「帧号」轴上，在「**同一次请求内部**」。

> **两个采样点做比对时，先问：这两个点之间，系统还有什么一次性的活没干完？**

修法不是把 8 MB 容差放宽（那会**正好掩盖**"真的测错进程"这一类故障），
而是**把比对挪到暖机之后**，容差保持 0.5 MB 那个量级不许动。

## 案例 11 · 两个「判据自己写错」的坑（2026-09-27）

> 案例 9 讲的是**靶子够不着刀口**；这一条讲**刀本身装反了**。
> 两者都表现为「跑了、没报错、结论有数字」—— 区别是案例 9 假红，这条**假绿**。

### 11-a 阈值是双侧的，判据却写成了单侧（漏 `abs()`）

```python
SLOPE_OK   = 20.0     # |k| < 20   ⇒ 稳
SLOPE_WARN = 200.0    # |k| >= 200 ⇒ 会 OOM

elif k < SLOPE_WARN:          # ✗ 斜率 = −908（RSS 在**降**）落进「可疑」
elif abs(k) < SLOPE_WARN:     # ✓ 正负都是"偏离稳定"，都得取绝对值
```

实测抓到的那次：斜率 **−908 kB/帧**（内存明显在**下降**）被判成「⚠️ 可疑」。
−908 显然既不是"稳"也不是"可疑"，它是**第三种情况**（可能是一次性大释放）。

**规矩：凡是拿"偏离量"去比阈值，先问一句「这个量可能为负吗？」**
可能为负 ⇒ 判据里必须有 `abs()`，或者**正负分开写成两条**（"在涨"和"在降"是两件事）。

### 11-b `"%f" % None` —— "算不出来"的分支没接

跑 `--frames 5` 时拟合窗口是空的 ⇒ `kp = None` ⇒ `"%f" % None` → `TypeError` **崩掉整个脚本**。

```python
E("  py 块数  : ... 斜率 %s 块/帧"
  % ("—" if kp is None else "%.1f" % kp))     # ✓ 先接住 None，再格式化
```

**规矩：凡"算出来的数"进格式化字符串，先想它有没有"算不出来"的分支。**
斜率、比值、均值、方差 —— 分母为 0 / 点数不够 / 全被过滤掉，都会算出 `None`。

**附带记一笔：这个崩溃是"边界测试"真跑出来的**（`--frames 1 / 5 / 16` 三个边界一次跑完）。
而且报告里 **traceback 完整未截断**（H9 生效），两分钟就定位到行号。
⇒ 边界测试 + 不截断的失败记录，这一对组合的价值在这次体现得很清楚。

## 案例 12 · ctypes 静默返回 0 —— 「不报错但全错」的 Windows 版（2026-09-27）

> 症状：**函数调用成功，输出全是 0。** 和案例 6 是同一个家族，但根因在 FFI 边界上。

### 现象

写 `_rss_kb()` 读当前进程内存，Windows 分支走 `GetProcessMemoryInfo`。
调用返回"成功"，但拿到的内存数是 **0**。

### 根因：`GetCurrentProcess` 的返回值被零扩展了

```python
hp = ctypes.windll.kernel32.GetCurrentProcess()   # ✗ 默认 restype = c_int
```

`GetCurrentProcess()` 返回的是**伪句柄** `(HANDLE)-1`，在 64 位下是 `0xFFFFFFFFFFFFFFFF`。
`ctypes` 默认按 `c_int`（32 位）解释 ⇒ 截成 `0xFFFFFFFF` ⇒ 再**零扩展**成
`0x00000000FFFFFFFF` —— 这已经不是那个伪句柄了。
`GetProcessMemoryInfo` 收下这个无效句柄，**不抛异常、不设错误码，静静返回 0**。

### 修法：凡是"返回句柄 / 指针"的 FFI 函数，显式声明 restype

```python
k32 = ctypes.windll.kernel32
k32.GetCurrentProcess.restype  = ctypes.c_void_p        # ★ 少这行 ⇒ 拿到的数是 0
k32.GetCurrentProcess.argtypes = []

psapi = ctypes.windll.psapi
psapi.GetProcessMemoryInfo.restype  = ctypes.wintypes.BOOL
psapi.GetProcessMemoryInfo.argtypes = [ctypes.c_void_p, ctypes.c_void_p,
                                       ctypes.wintypes.DWORD]
```

**判据：只要一个 FFI 函数的返回值**语义上是"句柄 / 指针 / 地址"**，就必须显式写 `restype`。**
`argtypes` 同理 —— 收了句柄的那个参数必须声明成 `c_void_p`，否则它也会在边界上被截。

### 配套规矩：读不到就**说读不到**，不许静默降级成 0

```python
def _rss_kb():
    """→ (当前kB, 峰值kB, 来源或**失败原因**)"""
    ...
    return None, None, "GetProcessMemoryInfo 返回 0（句柄可能无效）：%s" % err
```

`0` 和 `读不到` 是**两回事**。如果 `_rss_kb()` 失败时返回 `0`，
下游会把它当成"内存占用 0 MB"一路传下去 —— 报告里那个数**看着完全正常**。

### ⚠️ 这一条是**第二次**踩

同一个 `GetCurrentProcess` 零扩展的坑，先在泄漏诊断脚本里踩过一次、修好了，
**写 `app.py` 时又踩了一遍**。

> ⇒ 教训不是"下次注意"，是：**这类修法必须写进清单（就是这一段），
> 不能只留在"我上次修过的那个脚本"里。**
> 一个坑修在脚本里 = 修一次；修在清单里 = 修每一次。

## 案例 13 · 编译通过 ≠ 能跑：`time.time()` 忘了 `import time`（2026-09-27）

### 现象

给 PS 版 `engine.py` 加计时，写了 `t_all = time.time()`，**那个文件从来没 `import time`**
（它原来一行计时都没有）。跑 `python -m py_compile engine.py` —— **全绿**。
`py_compile` 只做语法分析，**不解析名字**：`time` 是个合法标识符，语法上一点问题没有。

真跑就是 `NameError: name 'time' is not defined`。

### 为什么这条值得单列

`NameError` 属于「**静态检查抓不到、一跑就死**」那一类。同类还有：拼错的模块级函数名、
只在某个分支里用到的未定义变量、`from X import Y` 里 Y 不存在（这个 import 期就炸，还算好）。

> ⇒ **规矩：改完 Python 文件，`py_compile` 只是第一道；第二道必须是"真的 import 一遍"。**
> 成本几秒，抓的正是 `py_compile` 放过的那一类。
> 在本项目里就是：`importlib.util.spec_from_file_location` + `exec_module`
> （见 `project\_pynq_pl\_pc_check_time_split.py` 的 `load_mod()`）。
>
> ⚠️ 但 **import 也还不够** —— 函数体里那条路径没被调用到，照样不报错。
> 第三道是**真的调一次**。三层都便宜，别省。

## 案例 14 · 验证脚本把**被测产物**弄脏了（2026-09-27）

### 现象

新写的验证脚本用 `importlib` 从 `_board_pkg_pl\engine.py` 加载模块。
跑完，另一个脚本（`_pc_dryrun_resident_pl.py`）的 F9 闸门红了：

```
[FAIL] 没有多出非文件项（原来 ['__pycache__']，现在 ['__pycache__']）
```

F9 的判据是 `check(not a_others, ...)` —— **要求零非文件项**。
导入一个 `.py` 会让 CPython 写 `__pycache__/*.pyc`，**这就是"多出来的非文件项"**。

### 为什么这个坑值得记

- 红的是**别人的**闸门，报错落在**另一个脚本**上 ⇒ 找错方向的话会去翻 `app.py`。
- 板包那个目录**有语义**（"恰好 9 个文件、无非文件项" = 用户要往 Jupyter 里选的清单）。
  一个"只是读一下"的脚本就能破坏它。

### 修法（两条都要）

```python
# ① 在被测目录里加载模块之前，先关掉字节码写入
sys.dont_write_bytecode = True      # ★ 必须在 load 之前
```

② **让脚本自己守这条闸门** —— 开头记下目录快照（文件清单 + 非文件项 + 每个 sha），
结尾再对一遍。这样下次谁再犯，**是它自己红，不是别人红**。

> ⇒ 规矩：**任何"只看不写"的脚本，跑完必须证明自己真的没写。**
> 判据：跑前跑后**文件清单 + 非文件项 + 全部 sha** 三项都不想变。

## 案例 15 · 「不适用」「0」「读不到」是三件事（2026-09-27）

需求：把每帧耗时拆成 **PS 用时 / PL 用时** 两栏。

### 15-a 四种形态必须分别渲染，⛔ 不许糊成一个数

| 实际情况 | 该印什么 | ⛔ 不许印 |
|---|---|---|
| PL 真跑了 | `PL 0.11 秒（kernel 0.10 + 搬运 0.02）` | — |
| PL 存在，但**本帧**退化走了 PS | `PL 0.00 秒（本帧没走 PL）—— 本帧未走 PL：ps_fallback_xxx` | 光一个 `0.00`（读的人会以为 PL 坏了） |
| 跑的是 **PS 版引擎**，根本没有 PL | `PL **不适用** —— PS 版引擎没有 PL 通路` | `PL 0.00 秒`（把"没有"谎报成"跑了 0 秒"） |
| 旧引擎没这组字段 | `用时拆不了 —— 引擎没给 ps_sec / pl_sec` | `0.00`（凭空编数） |

- 「有 PL 但没跑」写 `0.0` **可以**，因为那**是真值**（这一帧 PL 一秒没跑）——
  但**必须配一句原因**。有解释的 0 ≠ 静默降级的 0。
- 「根本没有 PL」写 `0.0` **不行**，必须 `None` → 渲染成「不适用」。
- 这两种混起来是**同一个字段名两种含义**，和 `_mem_line()` 那个坑同一个族（见案例 12 配套段）。

### 15-b 注入式测试的假值**必须按真实量级定标**

PC 上没有 pynq ⇒ PL 版必然走 fallback ⇒ 「PL 真跑了」那条分支**零覆盖**。
补法是注入假用时。第一版写死了 `kernel=0.1234 搬运=0.0100`，结果：

```
实得：total=0.123 pl=0.133 ps=-0.01        ← ps 变负数了
```

不是算术错，是**注入的 0.133 秒比这台 PC 整帧的 0.123 秒还长** —— 物理上不可能的组合。

### 15-c ★ 负数不该被夹掉，该被**点亮**

`pl_sec` 是从 `quad()` 里量的、`total_sec` 圈住整个函数，而 `quad()` 是它的子区间
⇒ **真值下 `pl_sec` 恒 ≤ `total`，`ps_sec` 不可能为负**。真为负 = 两个测量点不自洽。

> ⛔ **不要 `max(0, ...)` 夹掉** —— 夹掉就把"测量坏了"这个信息藏了，
> 而藏掉的后果是：以后真出这个 bug 时，看到的是一个**看着正常的 0**。
>
> ⇒ 如实报负数 + 点亮一条警告（`meta["pl_warn"]`），**并且让渲染层把它印出来**
> （只写进 meta 等于没写 —— 它被 `shown` 元组挡在字段清单外面）。
> 配套：加一条**边界测试**，专门注入超额值，断言「**确实报负数**」+「警告被点亮」。

### 15-d 修好之后，原来那条测试断言要跟着改

第一版那条断言是 `ps > pl * 10`（想验"PS 是主力"）—— 它本身没错，
但它**只在"注入值相对整帧合理"时才成立**，等于把测试和"写死的常数"绑在一起了。
改成 `base = 先真跑一枪量 total` → `注入值 = total 的比例` ⇒ 断言与机器速度无关。

## 案例 16 · 存档脚本**自己重打**产物 ⇒ 造出一个「像交付物、其实不是」的东西（2026-09-27）

### 现象

存档脚本要收一份板包 zip 进 `_存档\`。第一版是**自己重打**的：

```python
with zipfile.ZipFile(DST_ZIP, "w", zipfile.ZIP_DEFLATED) as z:
    for fn in sorted(os.listdir(PKG_DIR)):
        z.write(os.path.join(PKG_DIR, fn), fn)      # ← 顶层文件名，9 个条目
```

脚本跑绿了（"9 个文件、条目可读回"全过）。但**和交付那份对不上**：

| | 交付件（`_pack_上板zip.py` 打的） | 存档脚本重打的 |
|---|---|---|
| 条目 | `_board_pkg/` 前缀下 **9 个文件 + `_READ_ME_FIRST.txt`** | 顶层 **9 个文件** |
| 字节 | **371164** | 367965 |
| sha16 | `8c195b875a51f3a4` | `babe67694328c043` |

那个 `_READ_ME_FIRST.txt` 不是可有可无的：里面是**另一台电脑上传前核对用的 sha256 表**
+ 网卡 IP 设置 + 上板步骤 + 「传之前先删 `__pycache__`」。

### 为什么这个坑值得记

- 重打的那份**自己看着全绿** —— "9 个文件都在、sha 都对"，闸门检查的是**它自己定义的结构**，
  当然全过。**闸门验的是"我打的对不对"，不是"这是不是该交的那份"。**
- 它**不是错误产物**（解压出来文件都对、能用），所以不会报错、不会崩，
  只会让存档里静静躺着一个 **和交付物 sha 不同**的东西 ——
  等哪天有人拿存档去核对交付件，就得重新查一遍"到底哪份才算数"。
- 同族问题：**产物一旦有专门的生成脚本，任何人都不要另写一套生成逻辑。**
  （姊妹案例 14：验证脚本往被测产物里写东西。）

### 修法

```python
# ★ 存档存**原件**：复制那一个文件，并证明复制后逐字节相同
shutil.copy2(SRC_ZIP, DST_ZIP)
assert sha16(SRC_ZIP) == sha16(DST_ZIP)
```

外加**把"该有的东西"也断言出来**，而不是只数自己打了几个：

- 条目数 = 9 个文件 **+ `_READ_ME_FIRST.txt`**（缺了就 FAIL，明说"那就不是 `_pack_上板zip.py` 打的"）
- 包内每个文件的 sha **与磁盘上的源逐个相等**（不是"包内自洽"就行）

> ⇒ 规矩：**产物有专门生成脚本时，别处一律"复制原件"，不许重打。**
> 判据：存档里那份的 **sha 与交付件逐字节相同**，且**结构由交付件决定、不由存档脚本决定**。

## 案例 17 · 两版测试文件**逐字节相同** ⇒ `114 passed` 是**假绿**（2026-09-27）

### 现象

v11 落地时，`test_rectify.py` **一个字都没改**，pytest 却报了 `114 passed`：

| 项 | v10 | v11（初版） |
|---|---|---|
| `test_rectify.py` sha16 | `263847d0b2101a9e` | **`263847d0b2101a9e`** |
| `pytest --collect-only -q` 用例数 | 114 | **114** |
| 新增用例 | — | **0 条** |

**同一份文件**，所以这不是"两版测试恰好都通过"，而是**根本没有测试这一版的新功能**。
v11 新增的边缘判据（`edge_color_ratio`）在那 114 条里**没有任何一条**会因为逻辑写反而失败。

### ★ 这不是第一次

| 版本 | `test_rectify.py` sha16 | 与上一版的关系 | 当时是否发现 |
|---|---|---|---|
| **v9** | `7f2550923b28545d` | ★ **与 v8 逐字节相同**（`105 passed`，新增 0 条） | **否** —— 补 `v9/NOTES.md` 时才查出 |
| **v11** | `263847d0b2101a9e` | ★ **与 v10 逐字节相同**（`114 passed`，新增 0 条） | **是** —— 补 L 节 14 条后 114 → 128 |

**为什么 v9 那次没被抓到**：v9 落地时**没有 NOTES**，没有任何环节要求"说清楚新增了什么测试"。
⇒ ★ **「补 NOTES」本身就是一次缺陷检查** —— 写不出「新增了哪几条测试」的那一版，就是假绿的那一版。
v9 的 NOTES 是 20:44 落地后、23:05 才补的，**假绿正是补写时查出来的**。

### 怎么改

新版本落地后，**先比测试文件的 sha，再看绿不绿**：

```bash
sha256sum <上一版>/test_rectify.py <本版>/test_rectify.py | cut -c1-16
pytest --collect-only -q <本版>/test_rectify.py | tail -1     # 数用例，不只看 passed
```

相同 ⇒ 那几个绿勾与本次改动**无关**，必须补测试再宣称通过。
（v11 的修法是把功能确实补上：L 节 14 条，114 → **128**。）

### 与 D6 的关系

D6 管的是**同一份代码的两份副本**（`sys.path` 里谁赢）；本条管的是**两代产物**的测试文件。
两处**哈希相同都是警报，不是安慰** —— 一个说明"验错了对象"，一个说明"根本没验"。
