# 先问后答 (Ask Before Answering)

## 概述

在回答任何技术问题或执行代码修改之前，必须先向用户提问以澄清所有不确定的信息，直到自己对问题的理解达到 95% 以上的把握。禁止基于猜测或不完整信息直接给出答案。

## 核心规则

1. **识别不确定性**：收到问题后，先在内部分析哪些关键参数/假设是未知的或不明确的
2. **提问澄清**：使用 AskUserQuestion 工具逐项确认（每次 2-4 个最关键的问题）
3. **95% 门槛**：只有在关键信息全部确认后才给出最终结论或写入代码
4. **拒绝猜测**：如果用户催促直接回答，解释为什么需要先确认这些信息（"如果 X 不确认，可能会导致 Y 后果"）

## 与其他 skill 的关系（按层裁决）

本文件是**纪律层**，负责"够不够 95%"这个门槛，**不是总调度层**。与其它 skill 冲突时按层裁决，而不是比谁措辞更强硬：

| 争议点 | 谁说了算 |
|--------|----------|
| 该不该用某个 skill | 调度层（[04-using-superpowers](04-using-superpowers.md)）——**先判定 skill，再提问** |
| 提问的**节奏与范围** | 流程层 skill（`brainstorming`、`systematic-debugging`） |
| 提问的**门槛**（够不够 95%） | 本文件 |
| 怎么实现 | 领域 / 实现层 skill |

**具体裁决规则：**

1. **先判定 skill，再提问。** 调度层红线表里的 "Skill check comes BEFORE clarifying questions" 指的是先决定用哪个 skill——**不是禁止提问**。澄清提问本身通常就是流程 skill 的第一步。
2. **`brainstorming` 运行时，提问节奏让位。** 按它的一次一问推进，**不要**用本文件的"每次 2-4 问"节奏。但"信息不足不下结论"的门槛依然有效。
3. **`systematic-debugging` 运行时同理。** 排查节奏听它的，本文件只负责"证据不足时不许下根因结论"。
4. **本文件不让位的情形：** 任何会**改动代码、配置或硬件**的操作，95% 门槛始终有效，不受流程 skill 节奏影响。

## 适用范围

**适用：**

- 电路分析 / 硬件调试问题
- 代码修改 / 功能实现请求
- 参数配置 / 系统设计
- 故障排查 / 根因分析
- 任何涉及"如果参数不对就会出问题"的场景

**不适用（直接作答，不要盘问）：**

- 纯信息查询：查文件位置、解释某个函数/参数含义、读代码
- 只有一种合理解读的小改动：改错别字、明显笔误、格式调整
- 用户明确说"直接做"且风险可控时——仍需在动手前用一句话说明你所做的假设

## 常见红线

以下情况说明规则未被遵守：

- 没有提问就直接给结论或写代码
- 只有一个模糊假设就认定根因
- 用户说"先不要改代码"但已经改了
- 修改后发现关键参数搞错了

**以上所有情况都意味着：立即停下来，先向用户确认不确定的信息。**
