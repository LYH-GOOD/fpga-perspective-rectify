## sample_frames.jsonl —— 给 `log_frame_stats.py` 用

一份**合成的**逐帧日志，故意做成两个会话、两种情况，用来演示脚本能分辨什么。

**怎么跑：**

```bash
cd skill
python3 scripts/log_frame_stats.py examples/sample_frames.jsonl --sample 4
```

**应该看到（这就是判据）：**

```
  会话    记录      帧    上游fps    本机fps    周期ms     丢帧率    每帧跳
   0    21     80    30.00    25.00    40.0   16.7%   1.20
   1    13     48    16.67    16.67    60.0    0.0%   1.00
```

**这两个会话分别演示什么：**

| 会话 | 上游 | 本机 | 丢帧率 | 说明 |
|---|---:|---:|---:|---|
| 0 | 30.00 fps | 25.00 fps | **16.7%** | **我们比上游慢** ⇒ 每 6 帧丢 1 帧，`每帧跳 1.20` |
| 1 | 16.67 fps | 16.67 fps | **0%** | **已经吃满上游** ⇒ `每帧跳 1.00` |

**怎么读这两个数**：

- **丢帧率 > 0** ⇒ 瓶颈在我们这边，去查单帧耗时
- **丢帧率 ≈ 0 且 `每帧跳` ≈ 1.00** ⇒ 已到上游上限，**再优化也没用**，该换输入或换档位
- **`每帧跳` > 1** ⇒ 平均每处理 1 帧，上游已经走过 1.几 帧

⚠️ 本样例是 `--sample 4`（每 4 帧记一条）。**你的日志如果不是这个采样比，必须改这个参数**，
否则算出来的帧率会差整数倍 —— 这是最容易犯的错。

## 换成你自己的日志要改什么

脚本默认按这几个字段名取数，改成你的即可（都在命令行上，不用读源码）：

| 参数 | 默认 | 你的日志里叫什么？ |
|---|---|---|
| `--time` | `capture_ready_at` | 每帧的**单调时钟**（秒），不能用墙上时间 |
| `--seq` | `camera_sequence` | 上游（相机/传感器）的**帧序号**；没有就写 `--seq none` |
| `--cost` | `service_s` | 单帧耗时；没有就写 `--cost none` |
| `--key` | `index` | 用于自动推断采样比的主键 |
| `--sample` | 0（自动） | 日志每 N 帧记一条 |

## 判据的"好"与"坏"长什么样（配合 05-verification-method）

本项目实测过一组对照，值得先看一眼再设计自己的判据：

| 判据 | 长什么样 | 结果 |
|---|---|---|
| ❌ **"最大差异 ≤ 1 灰阶"** | 看着很严 | **永远不满足** —— 定点与浮点的固有差就在这个量级，真 bug 被淹没在噪声里 |
| ❌ **"跑通了、有输出"** | 最容易写 | 帧末多余像素、错位一格，全都通不过它 |
| ✅ **对着"独立定点模型"逐字节比** | 要多写一个模型 | 3 个 bug 全部显形，且**差异像素恒为 0** 是可断言的 |
| ✅ **撤掉修复能否复现** | 要多跑一遍 | 把"改完不坏了"升级成"定位对了" |

**⇒ 判据的价值不在"严"，在"能不能分辨"。** 详见 `references/generic/05-verification-method.md`。
