# 领域技能 ①：流式图像几何变换的架构约束

> **适用范围**：任何"逐像素几何变换 + 不落 DDR"的流式架构
> （remap / warp / 去畸变 / 极线校正 / 双目对齐）。
> **失效条件**：允许整帧缓存的架构（那就不受这里的约束了）。

---

## 一、核心结论：决定行缓存深度的是**旋转**，不是倾角

**这是本项目推翻蓝图估算、实测得出的一条。**

```
所需行缓存 ≈ W_out × tan(θ)
    θ = 文档在【画面里】的旋转角（不是相机相对纸面的倾角！）
```

| 情形 | 需要多少行 |
|---|---|
| 纯倾斜（θ = 0°，文档在画面里是正的）| **2 行** |
| 倾角 60° + 面内旋转 3° | 61 行 |
| 倾角 60° + 面内旋转 10° | **196 行** |

**为什么反直觉**：直觉上"越倾斜越需要缓存"，但实际上
**纯倾斜时文档的横线在图像里仍然是横线**，一行所需的输入只跨越极少的行。
真正拉开跨度的是**旋转**。

> ⚠️ 蓝图原来估"8~16 行"，隐含假设是"文档在画面里是正的"，**实测差 30 倍**。
>
> **对演示的硬约束：相机必须端平。**
> 或者：把输出尺寸调小（跨度与 `W_out` 成正比）。

---

## 二、⭐ 这个约束会在两个地方咬人

### (a) 深度不够 → 死锁（画面冻结）

跨度 > 缓冲深度时，核会停在"等一个永远到不了的输入行"。

**要做的**：
1. 核里加一个 `stuck` 状态位（等超过 N 拍就置位）——**别让用户对着冻结的画面猜**
2. PS 侧**上板前就算出所需跨度**并拦下，给出对策

```python
# 用 H 逐行采样算精确跨度（别用经验公式）
need, at_row = required_line_rows(H_out2in, W_out, H_out)
if need > ROWS:
    print("❌ 超过行缓存深度 —— 核会死锁")
    print("   对策：1) 相机端平  2) --out-max-dim 调小")
```

### (b) ⭐ **输出尺寸变大会吃掉行缓存余量**

跨度与 `W_out` 成正比。本项目把输出从 320 宽改成"按文档长宽比自动推算"（约 600 宽）后，
**跨度从 51 行涨到 166 行**，余量从 80% 掉到 35%。

> **改输出尺寸不是"画质调优"，是改了流控的工作点。改完必须重算跨度。**

## 三、⭐ 流控下界的取值时机（本项目的核心 bug）

### 现象
**画面的一部分出现拖影/重影，其余正常**，且这部分的位置随输入几何变化。

### 根因
一行所需的输入区间是 `[y_min(v), y_max(v)]`。流控要用 `y_min` 保护"还没用完的数据"。
但**如果 `y_min` 落在这一行的末端**，而行首就把它报给流控 ——
中间那一段流控都是**过度放行**的，会覆盖还要用的行。

### 判据（可精确预测，用来验证你是否也踩了）

```
会踩 ⟺ 某一行的极值 + 缓冲深度 < 输入总行数
```

本项目实测：同一份代码，4 张图里**只有 1 张**满足这个条件，其余 3 张
**只是恰好余量够（31~60 行）**。

> ⚠️ **"恰好能过"和"设计上能过"要分清。** 余量这么小的"通过"，要当成警告看。

### 修法
用**上一行对应端**的值做保守下界：

```verilog
if (u == 0)  lo <= (cur < prev_last) ? cur : prev_last;
else if (cur < lo) lo <= cur;
```

它随 v 单调递增，所以**不会像"只减不增"那样把输入永久堵死**（那是另一个坑）。

## 四、坐标递推：在**精确整数域**累加，只在最后舍入一次

```verilog
// ❌ 每步都移位 → 误差累积：1280 步 = 640 LSB ≈ 0.01 px
acc += (a11 * STEP) >> 16;

// ✅ 累加未移位的精确量，最后一次性右移
XN += a11 <<< 5;
...  // 最后
xn = XN >>> 16;
```

**实测本方案精度反而更好**（0.0186 px vs 0.0329 px），因为只在最后舍入一次。

> 附带好处：**精确整数递推可以换成闭式来做向量化**——
> `XN(u) = XN0 + u*(a11<<5)` 与递推**逐位等价**，这让 PS 侧的黄金模型
> 从"纯 Python 40 秒"变成"numpy 0.07 秒"（见 `06-ps-pl-and-delivery.md`）。

---

## 五、定点精度：**坐标归一化**是必须的

单应矩阵的 `h31/h32` 量级只有 `1e-4`，而 Q16.16 的分辨率是 `1.5e-5` ——
**只剩约 3 位有效数字**。再乘上坐标（最大 1279）进分母，误差被放大上千倍。

**实测：不归一化误差 11.57 px，归一化后 0.033 px —— 差 351 倍。**

做法：把输出坐标 `u,v` 先除以一个 2 的幂的尺度（本项目 `NORM_SCALE = 2048`），
参数相应放大。**必须是 2 的幂**，这样换算只用移位、不引入舍入。

## 六、帧边界：核**不允许对上游"关闸"**

详见 `../generic/01-stream-handshake.md` 铁律 4。这里只说对本领域的特殊性：

**视频阶段这是必踩的** —— 输入是连续流，没有"传输结束"这回事。
每帧关一次闸 = 每帧丢一次数据。

**修法**：加一个粘滞位，帧产出完毕后让输入能继续排空。

### ⭐⭐ 补：光"不关闸"还不够 —— 帧末必须**停产出**（2026-09-29 实测）

"不关闸"只解决了一半。真正会炸的是**另一半**：核在帧末会**继续产出**。

**根因**：核的"帧末"是靠 `out_v/out_u` 走到末行末列判出来的。
帧末这两个寄存器**停在末尾不归零** ⇒ **往后每一个像素都被判成"帧末"** ⇒
每个都带上 `tlast` ⇒ 变成一串**多余的、带过期帧末标记的 beat**。

**两种后果**（同一个根因）：

| 场景 | 后果 |
|---|---|
| 帧间**不复位** | 悬着的多余 beat 被**下一个传输**当成第一个字节吃掉 ⇒ 整条流挪位（实测 1 像素差）|
| 帧间**做复位** | 复位把 `tvalid` 从 1 直接撤到 0、**没有握手** ⇒ AXI-Stream 协议违例 ⇒ 互联里 beat 状态被破坏 ⇒ 新传输收 1 字节就判"包结束" ⇒ **挂死** |

**修法：帧门（frame_req）** —— 一帧输入只出一帧：

```verilog
// 帧首（in_sof）开闸、输出完成（最后一个像素被收下）关闸
always @(posedge clk) begin
    if (!rst_n)                 frame_req <= 1'b0;
    else if (wr_fire && in_sof) frame_req <= 1'b1;
    else if (fs_set)            frame_req <= 1'b0;
end
```

⚠️ **必须四处齐全，缺一处都会以"看起来无关"的方式失败**（本项目逐个踩过）：

| # | 漏了会怎样 |
|---|---|
| ① A 级必须能**回到 IDLE** | 原来帧末直接从 `A_CLAMP` 跳 `A_RL` 重头再来 ⇒ **门根本没机会关** |
| ② `b_start` / `c_take` 都要带 `frame_req` | 只关 A 不够 —— A **已产出的结果还在流水线里继续流**（实测多出 54 个 beat）|
| ③ 关闸那拍要**显式丢掉** A/B 的残留 | 否则 `a_valid` 恒 1 ⇒ `in_ready` 恒 0 ⇒ **下一帧的输入进不来（死锁）** |
| ④ `a_free` 也要带 `frame_req` | 否则 `!a_valid` 又成立 ⇒ A 再产一个"没人取"的结果 ⇒ 同样死锁 |

**判据（很关键）**：给仿真加一条
**"帧收满之后再多等一段，看有没有多余像素冒出来"** ——
原来的 TB 只收满 `N_OUT` 就切窗口，**多出来的会被算进下一帧的窗口、看起来还是对的** ✗
加完之后**当场复现（54 个）** ⇒ 上板挂死变成本地可复现的问题，后续调试**只花了一轮板子**。

> ⭐ 通用结论：**判据必须能看见"多余"，而不只是"够不够"。**

## 七、加颜色时，行缓存的**存储组织**决定一切（2026-09-29 实测）

### 核心不变量：**"1 次 BRAM 读 = 1 个完整像素"**

行缓存的读带宽是流的物理下限（本项目 B 级 4 次读/输出像素——四邻域）。
**只要"一个像素装得进一个 BRAM 字"，彩色就不比灰度多花一拍。**

| 做法 | 1 读给几像素 | 后果 |
|---|---|---|
| **一个像素一个字**（本例 RGB565，16 bit，落 RAMB36 的 `2K×18`）| **1** | ✅ 每像素拍数不变 |
| 24 bit/像素（装不进 18 bit 字）| 要么 2 次读、要么打包 | ❌ 拍数变多或加 mux |
| N 像素打包进 72 bit 字（省 BRAM）| 3~6 | ❌ 读回来要按列选 1 个 ⇒ **多一级 mux** |

⇒ **打包在"省 BRAM"上不划算**（打包的效率优势只体现在字节对齐时），
**而在读侧一定要还回来**。**判据：先选"一个像素一个字"的宽度，再谈压缩。**

### 开销公式里有一个**独立杠杆**：行距（stride）

```
行缓存开销 = ROWS × 行距 × 位宽
```

**行距不必等于"支持的最大宽度"** —— 它只要 ≥ 实际输入宽度。
本项目把行距从 1280 降到 1024（2 的幂 ⇒ `slot × 行距` 退化成位拼接，
地址路上连乘法器都不需要），**省下 25%**，于是 ROWS 从 128 涨回 192。

⚠️ **代价是"最大输入宽度"变成硬限制**，必须在 PS 侧做成**上板前的显式检查**
（本项目已有先例：位截断导致的静默花屏）。

### 位深选谁：按"够用的行数"倒推，不要凭感觉

本项目**实测**（`XC7Z020`，140 块 RAMB36；行距 1024、ROWS 192；
用 `build/probe_linebuf_bram.tcl` 单独综合 `line_buf` 量出来的）：

| 格式 | 位/像素 | RAMB36 | 占比 | 理论下限 | 够最大跨度 166 行吗 |
|---|---|---|---|---|---|
| RGB565 | 16 | **96** | 69% | 96 ✓ | ✅ |
| RGB666 | 18 | **108** | 77% | 96 ✗ 多 12 块 | ✅ 但不划算 |
| RGB888 | 24 | **144** | — | 128 | ✗ **超过芯片的 140** |

⚠️ **注意 18 位那行**：BRAM 字宽本来就是 18 位，所以"16 位白扔了 2 位、
改 18 位应该不花钱"看起来天经地义 —— **实测是 108 而不是 96**。
**综合器的存储推断不是算术题，必须量。**

⇒ **选 RGB565，理由不是画质而是速度**：16 位和 24 位都落在理论下限上、
18 位多 12 块，而**余量就是时序余量**（本项目在 80 块时就因布线拥塞把
100 MHz 压到了 83.33 MHz）。**先算"需要几行"，再选位深，最后按"哪一档最省 BRAM"定** ——
反过来做（先选 RGB888 再发现装不下）会白绕一圈。

### ⚠️ 多通道打包：通道顺序是被【位宽分配】隐式决定的

`RGB565 = {R[7:3], G[7:2], B[7:3]}` ⇒ **中字节拿 6 位**。
如果按字节序打包，就要求 **byte1 必须是绿色**，否则绿被塞进 5 位的槽，
症状是**偏色**（不报错、不崩溃、极难反推）。

⇒ 两条纪律：
1. **位宽不平衡时，通道顺序不是任意的** —— 必须在代码注释里写死这个约定
2. 改用"每通道位宽相同"（6/6/6）会让这条隐式约定**静默失效** ⇒ 改位宽必须同步检查字节序

（本项目恰好满足：OpenCV 读图就是 BGR ⇒ byte1 = G ⇒ 天然对上，PS 侧零重排。
**但那是巧合，不是设计** —— 所以注释里专门写明了。）

### ⚠️ 一个只在换位宽时才暴露的坑：**"2 的幂"是个隐藏前提**

`ROWS=256` 时 `row mod ROWS` 写成 `row[7:0]` 位切片，零成本且不可能写错 ——
于是**没人记得这是个特例**。换成 `ROWS=192` 后位切片不再等于取模，
症状是"**画面局部错位、其余正常**"，与本领域另一个经典 bug（流控下界取错端）**长得一模一样**。

⇒ **凡是"因为某个常量恰好是 2 的幂而免费"的写法，注释里必须把前提写出来。**
非 2 的幂的取模如果落在**地址通路**上，要用"分解成小质数 × 2 的幂"的快速形式
（本例 `192 = 3×64` ⇒ 只需一个 6×7 常量乘法），**别让综合器生成通用除数** ——
它会串两个乘法器，而地址路超时的表现是"根本出不了比特流"。

## 九、来源与验证

| 结论 | 怎么得出的 |
|---|---|
| 深度由旋转决定 | 离线测量脚本（逐行采样求跨度），推翻蓝图估算 |
| 输出尺寸吃掉余量 | 改自适应尺寸后跨度 51→166，实测 |
| 流控下界时机 | 解析预测出错区间 494~803，实测 510~758，**吻合** |
| 精确整数递推 | 实测精度 0.0186 px vs 0.0329 px |
| 归一化 | 实测 11.57 px → 0.033 px |
| 帧末排空 | 构造"输入比需要的多"的 TB，修复前 FAIL |
| **"1 读 = 1 像素"是彩色的前提** | 上板 `DMA 47.0 ms` ≈ `538,896 px × 7.16 拍 ÷ 83.333 MHz`（差 1.5%）⇒ 瓶颈是核；于是"读次数不变 ⇒ 拍数不变" |
| **行距是独立杠杆** | 单独综合 `line_buf`（`build/probe_linebuf_bram.tcl`）：行距 1280→1024 使 ROWS 从 128 涨到 192。**探针自检**：灰度现状测出 80 块 = 整工程实测 82 块 |
| **非 2 的幂取模落在地址路上要分解** | 192 = 3×64 ⇒ 108 LUT + **0 DSP**（Vivado 单独综合实测），不是两个乘法器串联 |
| **"2 的幂"是隐藏前提** | `ROWS=192` 后位切片不再等于取模；症状与"流控下界"bug 相同 ⇒ 反向验证时恰好在那条判据上 FAIL |
