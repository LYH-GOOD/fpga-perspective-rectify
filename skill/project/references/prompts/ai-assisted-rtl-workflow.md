# 提示词工作流：用大模型做 FPGA 工程

> **适用范围**：用大模型（本项目用 Claude Code）辅助写 RTL / 仿真 / PS 侧代码。
> **使用方法**：下面的模板可直接套用，替换 `<>` 里的内容。
> **失效条件**：换到能力较弱的模型时，需要把"自主执行"类提示词收回成"逐步确认"。
>
> **来源**：本项目从 0 到上板跑通的全过程（16 篇协作记录，见 `report/llm_log/`）。

---

## 一、⭐ 最重要的一条：**约束要写成"文件"，不是"对话"**

**踩过的坑**：同一个约定（比如"参数必须 Q16.16 且坐标归一化"）在对话里说过，
但换个会话就丢了，AI 又开始用浮点。

**做法**：把**不变量**写进项目根目录的 `CLAUDE.md`，让它**每次自动加载**：

```markdown
# CLAUDE.md · 项目全局指令
## 三条铁律（不可违反）
1. 主干像素流不落 DDR
2. 输出像素反查输入（H⁻¹），不是正向映射
3. 定点方案必须坐标归一化（NORM_SCALE 是 2 的幂）

## 接口与工程约定
| 约定 | 说明 |
...

## 边界与诚实红线
- 不编造细节；不确定就说不确定
- 区分"经验判断"与"需实测"
```

**效果**：AI 每次开口前都带着这些约束，**不用重复交代**。

> **通用原则**：**凡是"说了三次以上"的事，就该写进文件。**
> 对话是有窗口的，文件不是。

## 二、四类可复用的提示词模板

### 模板 1：让 AI 去"动手"，而不是"给建议"

```
你作为资深 FPGA 工程师，根据我们项目总路线，我现在决定要先实现<目标>，
你负责<范围>的设计，在 <工具> 里完成。你对此还有什么疑问可以问我，
没有的话就去 <工具> 里开始工作。
```

**要点**：明确**范围**（"只负责 PL 部分，PS 有人写"）和**工具**（"在 Vivado 里"）。
不说范围，AI 会给你一份"设计方案"而不是可运行的代码。

### 模板 2：授权自主执行（**本项目效率提升最大的一条**）

```
继续做。做的过程中需要什么指令自己进行，不需要询问我。
```

**效果**：AI 自己去跑仿真、开 Vivado、改代码、验证，不再每步都问。
本项目的**一次授权的自主循环**里完成了：改 RTL → 跑 TB → 综合 → 实现 → 出比特流 → 更新文档。

> ⚠️ **前提**：项目里已经有**可自动判断成功/失败的东西**（仿真 PASS/FAIL、逐字节比对）。
> **没有判据就不要授权自主执行** —— AI 只能靠猜，你也无法验证结果。
>
> **这是本技能包最重要的一条经验**：**自主执行的前提是"可自动验证"。**

### 模板 3：诊断请求（**要"只诊断不改"，防 AI 顺手改坏**）

```
在队友电脑上出现<现象>，这是什么原因。**不要更改代码，只说出错误之处和改正方案**：
<完整报错原文>
```

**要点**：
- **明确"不要改"** —— 否则 AI 会一并改掉，你失去对照
- **贴完整报错**，不要只贴最后一行（AI 需要上下文）

**效果**：本项目用这个模板收到过一次"只诊断"的分析，确认无误后再让它改，
避免了一次**盲改**。

### 模板 4：让 AI 先复现，再修

```
<现象描述>。你先在 PC 上仿真一下同样的输入，看看 PC 仿真是否有问题，
把结果存到 <目录> 里我看看。等 PC 仿真完了再考虑修改代码。
```

**要点**：**强制"先复现、后修改"的顺序**。

**效果**：本项目靠这个模板把一个"看起来是算法问题"的现象，
定位成"PS 侧参数封装错了" —— 如果直接让 AI 改算法，会改错方向。

## 三、⭐ 让 AI 自己找 bug 的三个提示词模式

### 模式 A：让它**证明**，而不是让它**修**

```
<测试通过了>，但我怀疑没覆盖到。你能构造一个【必然触发】的用例吗？
```

本项目用这个模式构造出了：
- "输入比核需要的多"的 TB（抓出帧末不排空）
- "输出只覆盖上半部分"的小尺寸（抓出流控下界时机）

### 模式 B：让它**撤掉修复**看能不能复现

```
把刚才的修复撤掉，跑同一个用例，看能不能复现出上板现象。症状要对得上。
```

**为什么有效**：这一条把"我改完了，测试过了"（只能说明没坏）
升级成"**修复前后症状一致**"（才能说明定位对了）。

### 模式 C：给它**现场数据**，而不是让它猜

```
这是运行日志：<贴文件路径或内容>。你看看还有没有什么问题。
```

本项目的**关键突破**都来自"给现场数据"：
- DMA 挂起时读出的 `busy=0 / stuck=0 / 帧计数=1` → 30 秒定位到"上游被堵"
- 性能表的分段数据 → 一眼看出 71% 花在加载 overlay

> **通用原则**：**让程序把"现场"打出来**（状态寄存器、分段耗时、出错行号），
> 再交给 AI。**AI 从数字里推因果的能力，远强于从现象描述里猜。**

## 四、⚠️ 反模式：这些问法会让 AI 跑偏

| 反模式 | 后果 | 改成 |
|---|---|---|
| "帮我优化一下" | AI 会做一堆你没要求的重构 | "只改<具体函数>，其他不要动，改完跑<某测试>" |
| "为什么这么慢" | AI 会猜（本项目它猜"每张 5 秒"，实测 26 秒）| "**先加分段计时埋点**，再根据数据优化" |
| "这个能实现吗" | 得到一段泛泛而谈 | "实现<具体功能>，**先告诉我代价**（资源/时序/工作量），再决定" |
| 一次问三件事 | 只答了其中一件 | 一次一件事，或明确编号 |
| 只贴报错最后一行 | 缺上下文，AI 猜错方向 | 贴完整输出 + 什么操作触发的 |

## 五、**必须人工把关**的三件事（不要让 AI 自己决定）

| 事项 | 为什么 |
|---|---|
| **删除/覆盖文件** | AI 可能删掉你没备份的东西。本项目要求"复制不要移动"、删前先说 |
| **对外发送/发布** | 推送到远端、上传到服务器 —— 一旦发出可能被缓存/索引 |
| **改"已验证的配置"** | 默认值、参数、接口。**本项目吃过亏**：加性能计时顺带改了执行次数，破坏了原本正确的行为 |

## 六、协作记录怎么攒（竞赛要求）

竞赛明确要求提交**"提示词、模型回答、自我纠错轨迹"**。本项目的做法：

**每完成一件事就写一篇 `report/llm_log/YYYY-MM-DD_<主题>.md`**：

```markdown
# 协作记录 · <日期> · <主题>
## 一、问题（现象 + 数据）
## 二、根因（怎么定位的）
## 三、修复
## 四、⭐ 比修复更重要的东西（如果有）
## 五、踩坑清单（技能包原料）
```

**要点**：
1. **失败和走弯路都写**，不只写成功 —— 那才是"纠错轨迹"
2. **带上数字**（实测值、对比值），不要只写"优化了"
3. **末尾固定加"踩坑清单"** —— 技能包就是从这些清单里提炼的（本项目攒了 89 条）
4. **命令输出末尾附【协作记录摘要】**（问题/结论/待办/踩坑各 1-2 行），
   便于后续汇总

> 本项目 16 篇记录、2430 行，**技能包和这份提示词文档全部是从里面提炼的** ——
> **记录不是负担，是资产的原料。**

## 八、⭐ 两条"元提问"（2026-09-29 新增，性价比最高）

前面几类是"怎么让它把活干对"；这两类是**"怎么让它别把活干错"** ——
都是在**动手之前**问的，一次提问省掉一轮返工。

### 模板 5：让它论证"这个改动以后会不会返工"

```
你现在要改的这个确定对以后【<下一阶段目标>】有作用吗？
如果有作用就做，如果以后【<下一阶段>】还要再大改动之类的就没必要再做了
```

**为什么有效**：它逼 AI 给出**"这次的改动和后续改动是否正交"**的论证。

本项目的实例（最终阶段是**视频实时**）：
- AI 的回答是："**该做**。它是视频的承重件；而视频阶段其余工作（彩色、读口加宽、
  H 摊销）改的是数据通路宽度/读时序/PS 侧，与帧边界逻辑**正交**；
  **HDMI 换 DMA 反而更容易**（现在的软复位是 DMA 专用 hack，换 HDMI 本来就得拆）。"
- 并且它补了一条**反向论证**："不做的话，视频时还是得做，只是会和彩色+行缓存
  **三件事一起改** —— 那时出问题就分不清是哪一件。"

> ⭐ 判断"该不该现在做"要看**它和后续改动是否正交**，
> 而不是看它当下解决的 symptom 大不大。

### 模板 6：明确"信息通道"，并要求制度化

```
我一般只会给你发【<你的输出日志>】，
你如果想获得什么信息，就都要把输出结果放到【<日志>】里，
【<日志>】的设置要一直同步更新
```

**为什么有效**：它把"AI 需要什么信息"从**一次性要求**变成**设计约束**。

本项目的实例：一句话暴露了一个流程漏洞 ——
`--log` 只捕获**子进程**的输出，而 **notebook 自己 `print` 的东西跑在 Jupyter 内核里、
根本没进日志**（实测：日志里"指纹检查""结论表"一次都没出现过）。
修法不是"记得手写"，而是**在 notebook 第 0 格装内核级 tee**（机制，不靠纪律），
并顺手加了"**板上全目录 md5 快照**" ——
⭐ 它的价值在于**不需要提前预知要看什么**：事后任何"文件对不对"的问题都能回答。

> ⭐ 推论：**对方能看到什么，必须在设计阶段就定死。**
> 而且"能看什么"要**靠机制保证**，不能靠"记得写"。
