# 基于 FPGA 的视频透视自适应校正系统

**Real-Time Adaptive Perspective Rectification System for Video**

---

## 项目简介

书本、纸张等平面目标在倾斜或旋转拍摄时会产生透视畸变，版面歪斜、文字拉伸，不能直接当作正视画面来阅读、归档或送入识别算法。而现有的"拍照后逐张处理"方式，在背景杂乱或目标移动时仍需人工框选四角，难以适应连续拍摄的场景。

本作品构建了一套基于 PYNQ 平台的实时图像自适应校正系统来解决这个问题。系统以目标的物理外边缘作为定位依据，把传统视觉和 AI 分成两个阶段配合使用：常规情况下先由传统算法检测轮廓、拟合四条边，并校验它们之间的几何关系。只有在常规搜索找不到有效目标时——比如目标边缘不清晰、颜色与环境接近，或边缘有轻微遮挡、反光——才调用轻量化分割 AI 模型给出候选区域和初始四角。候选四角通过当前帧验证之后，交由跟踪模块接管，此后不再逐帧运行神经网络。

在软硬件分工上，控制、定位和跟踪放在处理系统（PS）侧运行，像素重映射、锐化和分段线性光补则由可编程逻辑（PL）侧承担。系统还通过相机复用、帧序号校验、异步任务和单一显示提交者这几种机制，减少了模式切换时的重复初始化，也避免了多路输出造成的画面不一致。界面上提供自动定位、AI 校正、手动四角、分辨率选择和增强参数调节等操作。当定位短暂失效时，系统会在限定时间之内继续用最后可信的四角去处理当前相机画面，而不是把画面冻结在旧图上。

系统已在 PYNQ-Z2 上完成部署并通过板端实测，累计运行数十小时、经历千余次交互会话未出现崩溃，能够持续稳定地完成实时校正与显示。

## 复现步骤

一次完整的复现不是从第一行代码写到最后一行，而是三条线各自推进、中途两次汇合。下面按推进顺序列出每一步要做什么，以及**什么条件满足了才算这一步真正做完**——放行条件不满足，不进入下一步。

### 主线：算法与硬件，分五段推进

**① 定型｜先回答"做什么"**

在三个候选方案之间做五维对比，选定平面自适应校正这条路线，并把方案定稿。

> 放行条件：路线唯一确定，四份定稿齐备。

**② 打通｜再回答"能不能跑"**

从零建起 PL 校正核，覆盖块设计、流式重映射与坐标发生器，直到整条链路在板上第一次跑通。

> 放行条件：测试平台逐字节通过，板上出首帧。

**③ 求对｜回答"算得对不对"**

加入帧身份校验与色彩通路，把找四角从 PC 端搬到板上，用实拍样本检验。

> 放行条件：实拍样本判废率归零。

**④ 求快｜回答"连不连续"**

把取帧、解算、重映射、显示四段做成重叠流水，并压掉显示合成的开销。

> 放行条件：四段确实重叠，显示合成不再是瓶颈。

**⑤ 攻坚｜回答"够不够快"**

对校正核逐轮压缩每像素拍数，同时缩减 600P 预览开销，最后完成交付打包。

> 放行条件：打包完整，可交付。

### 第二条线：交互与跟踪，在主线打通之后加入

这一线关心的不是"算得对不对"，而是"在人手里用起来连不连续"。

**① 可操作**——把触摸操作做成闭环。

**② 可恢复**——让系统在静止与跟丢两种状态下都能自行恢复。

**③ 可交付**——同帧成对显示，双档位切换不断流。

### 第三条线：模型，在收口阶段加入

**① 补数据**——先补齐训练数据。

**② 接入**——把轻量分割网络接进定位环节，只提供初始四角，拿到之后立即交回传统跟踪，不进入逐帧通路。

### 两次交汇

**交汇一**：主线并入第二条线的代码库。此后"够不够快"与"连不连续"在同一份代码上同时推进。

**交汇二**：三条线合成同一个版本号。交付版本从这时起才正式存在。

### 贯穿全程的纪律

每一段的放行条件都是同一条：**先在测试平台上逐字节通过，再上板实测**。任一条不满足，不进入下一段。

## 目录结构

```
fpga-perspective-rectify/
├── README.md     项目简介与复现步骤
├── src/          设计源码（RTL / HLS / PS 侧软件）
├── sim/          仿真或验证脚本与结果
├── build/        可复现的构建脚本 + 综合与实现报告
├── board/        上板工程、运行脚本与实测输出
├── data/         测试数据与参考结果
├── skill/        技能包（大模型协作中沉淀的可复用经验）
└── report/       设计报告 + 大模型协作记录
```
